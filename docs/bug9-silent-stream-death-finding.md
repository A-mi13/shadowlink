## Гипотеза корня (НЕ доказана до конца — нужно исследование кода)

Тихий долго-живущий стрим убивается вместе со слотом:
1. Слот молчит 10-15с (тихий стрим: юзер ждёт, нет байт ни вверх ни вниз).
2. TSPU/middlebox режет тихий долгий direct-TCP к голому origin (104.222.177.67) → close 1006.
   (`mode=direct` — это direct, не через CF; CF в РФ блокируется, direct намеренный.)
3. Слот → reconnect с backoff 5-9с.
4. Пул проседает (alive=11 dead=3), стримы с мёртвого слота ищут живой → `no ready slot` (все мертвы/в backoff).
5. Стрим НЕ мигрирует (некуда) → умирает → агент/сессия обрывается, не восстанавливается.

## Направления для исследования (проверить по коду, НЕ патчить вслепую — урок Bug#8)

1. **Keepalive на слоте**: почему слот молчит 10-15с? Есть ли per-slot keepalive ticker, какой интервал,
   почему он не держит тихий слот «живым» для middlebox? `last_write_age_ms=15001` = keepalive НЕ сработал
   или интервал > времени реза middlebox. NB: NEW-1 jittered keepalive 20s±30% (CLAUDE.md) — 20с МОЖЕТ БЫТЬ
   СЛИШКОМ РЕДКО если middlebox режет на ~10-15с молчания. Это сильный кандидат в корень.
2. **Stream migration**: мигрирует ли активный-но-тихий стрим на другой слот при смерти его слота?
   Или стрим жёстко привязан к слоту и умирает с ним? Где в ws_pool.go обрабатывается handleSlotDeath
   относительно стримов слота.
3. **Backoff 5-9с**: не слишком ли долго? На это время стримы повисают без слота.
4. **Bug#6 sticky vs тихий стрим**: sticky-drain даёт АКТИВНЫМ доиграть, но ТИХИЙ стрим (0 байт) drain-логика
   считает idle → снимает досрочно. Тихий долгий стрим = слепое пятно sticky-логики.
5. **404 closed pipe**: разобрать сколько из них — реальные обрывы тихих стримов vs штатные app-close.
6. close 1006 mode=direct — middlebox режет именно тихий direct. Keepalive чаще = маскировка под живой
   браузер (реальный idle keep-alive WS шлёт ping). Но НЕ ломать анти-DPI (jitter, не fixed period).

## ОБНОВЛЕНИЕ 2026-05-31 — keepalive-фикс НЕ закрыл, КОРЕНЬ ГЛУБЖЕ: рез по ВОЗРАСТУ + нет миграции стримов

Полевой ретест с keepalive 5s (бинарь 12:43). Лог nixavpn-DEBUG-20260531-124541.log (2457 строк, 39мин).
Keepalive ПОМОГ частично (тихих слотов 10s+ стало 8 из 126), НО обрывы продолжаются.

РАСПРЕДЕЛЕНИЕ 126× close 1006 ДОКАЗЫВАЕТ — режет по ВОЗРАСТУ слота, НЕ по молчанию/объёму:
- по last_write_age_ms: 58× active(0-2s), 42× 2-5s, 18× 5-10s, лишь 8× quiet(10s+). Т.е. режутся в основном АКТИВНЫЕ слоты.
- по slot_age_ms: 66× на 2-4мин, 40× на 1-2мин, 20× на 4мин+. ВОЗРАСТ — главный фактор.
- по down_bytes: 94× при <50KB (НЕ перегрузка).
ВЫВОД: middlebox/TSPU режет долгий direct-TCP к голому origin 104.222.177.67 по достижении возраста ~1-4мин.
Keepalive это НЕ лечит принципиально (режут не за тишину, а за долгое TCP к одному IP без CF).

СЛЕДСТВИЕ (настоящая проблема): 371× `downlink done (ch closed)` (стрим умер ПОТОМУ ЧТО слот закрыли)
vs 172× штатных app-close. + 11× `no ready slot`. Когда слот режется по возрасту, стримы на нём
(включая долгий стрим агента/видео/закачки) УМИРАЮТ ВМЕСТЕ С НИМ, НЕ мигрируют на живой слот.

СЕРВЕР ЧИСТ (подтверждено): ws_reader_exit_reset=0, other=0, local_close=0 — сервер НЕ рвёт.
nginx proxy_read_timeout=86400. Рез — строго middlebox между клиентом и origin. closed_pipe=0, decrypt_fails=0
(Bug#8 держится).

НАСТОЯЩАЯ ЦЕЛЬ (от юзера): МИГРАЦИЯ СТРИМОВ. Рез слота по возрасту — данность канала (direct без CF в РФ,
CF блокируется — direct намеренный). Бороться надо не с резом, а с последствием: при смерти слота активные
стримы должны ПЕРЕЕХАТЬ на живой слот прозрачно для приложения, а не умирать (ch closed).
Прошлое ревью назвало миграцию "архитектурно неустранимой без редизайна (per-slot core.Session, нет
cross-session TCP handoff)" — ПЕРЕПРОВЕРИТЬ: возможно есть способ (server-side session не привязан к WS-conn?
или client-side re-CONNECT того же dest на новом слоте с продолжением? или graceful pre-emptive миграция
ДО реза по возрасту, пока слот ещё жив?).
