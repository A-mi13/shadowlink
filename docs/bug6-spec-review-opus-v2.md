### A.B1 — шторм startDrain → ЗАКРЫТО

v1 предлагал *убрать* `Store(0)` из reader-пути и перенести reset в startDrain — это и порождало шторм. **v2 развернул решение на 180°:** «Reader-путь byte_budget НЕ трогаем» (§0, §2.1, §3.3, §8, §10/B1). Код `ws_pool.go:2547-2549` остаётся как есть: `startDrain(...)` → `slot.downBytes.Store(0)` → `continue`. Идемпотентность повторного входа в startDrain сохранена ровно тем механизмом, что её обеспечивал (комментарий `:2544-2546`).

Проверка «объёмный счёт теперь от `downBytes.Load()` без переноса reset — корректно?»: ДА. v2 НЕ вводит snapshot-поле, НЕ переносит reset, читает существующий `downBytes` как есть. Реакция на уже-обнулённый счётчик в byte_budget-пути разобрана в §3.3 и принята осознанно (см. B2). Регрессия v1 устранена в корне — фича больше не касается reader byte_budget вообще. **Инвариант §5 «reader byte_budget не штормит» подтверждён.** Вердикт: **ЗАКРЫТО.**

### A.B2 — инверсия объёмного предела → ЗАКРЫТО (с явно принятым допущением)

v1: `drainBytes >= 1GiB` рубит быструю закачку рано (downBytes растёт от реального downlink). **v2 переопределил семантику:** предел теперь не «байты в дренаже», а «анти-TSPU потолок на текущем отрезке TCP» (§3.3, §10/B2). Это логически когерентно с реальным сигналом, который проект и так считает (комментарий `ws_pool.go:289-295` + `:233-235`: middlebox убивает TCP в районе ~200 MB).

**Проверка ~200MiB vs byteBudget 4-30 MiB:** разумно. byte_budget (4-30 MiB) — это штатная *ротация для размывания* per-flow byte-counter кластера; ~200MiB — это *жёсткий потолок выживания TCP* (точка, где TSPU реально режет). Разные шкалы по построению, не конфликтуют: byte_budget срабатывает РАНЬШЕ и инициирует дренаж, а sticky-backstop ловит только тот хвост, где дренаж продлевается на активной закачке. Цифра ~200MiB прямо привязана к коду-комментарию `:293-294` «middlebox kills around 200 MB». **ЗАКРЫТО.**

**Когерентность «age от connect / byte_budget от reset» (§3.3):** проверил логику. Для age-дренажа `downBytes` НЕ обнулялся → `Load()` = байты от connect = честный «возраст TCP в байтах». Для byte_budget-дренажа `downBytes` обнулён на `:2548` → `Load()` считает от reset. v2 аргументирует: byte_budget-ротация САМА сработала по достижении штатного бюджета, т.е. TCP уже «отметился», счёт заново логичен (новый отрезок). Это НЕ новая дыра, а осознанная асимметрия. **Единственное практическое следствие** (фиксирую как LOW, см. Б): для byte_budget-дренажа суммарный возраст TCP в байтах = (бюджет 4-30MiB) + (≤200MiB от reset) ≈ до ~230MiB, т.е. потолок «на TCP» де-факто чуть выше номинала именно для byte_budget-пути. Для анти-TSPU это безопасно в сторону РАНЬШЕ-рвём по самому первому byte_budget, так что не регрессия. Когерентно.

### A.H1 — корень неполон → ЗАКРЫТО

v1: спека продавала «единственная точка смерти». **v2 §1.2 даёт честную таблицу всех путей** (deadline.C / reader-error / ctx.Done / generation-bump / tier-2) с обоснованием scope для каждого. Сверил с кодом:
- reader-error → `handleSlotDeath` на `ws_pool.go:2514` — подтверждён, помечен «вне scope, но измеряем отдельно» (§1.2, §6.1). Корректно: sticky физически бессилен против внешнего TCP-kill.
- ctx.Done на `ws_pool_drain.go:626` — подтверждён, graceful shutdown, корректно вне scope.
- generation-bump (shouldExitReader) — корректно «не вносится фичей».
- **tier-2 как РЕГРЕССИЯ** (`ws_pool_drain.go:449-457` `tryEmergencyEvictMinStreamsSlot`) — это сильная сторона v2: фича честно признаёт, что удержание sticky-слотов в slotDraining повышает давление на claimFreeSlot и шанс эвакуации активных стримов на ДРУГИХ слотах. Инвариант в §5 («sticky не повышает tier-2 эвакуацию активных») + тест. Адекватно для дизайн-стадии.

reader-error «измеряем отдельно» — достаточно: §6.1 явно требует считать reader-error-обрывы активных стримов ОТДЕЛЬНО от backstop-хвоста, чтобы канарейка не списала их на «остаточный хвост sticky» (ложный аргумент за миграцию). Это и был корень претензии v1. **ЗАКРЫТО.**

### A.H2 — cross-recycle гонка глобального счётчика → ЗАКРЫТО (разобрано построчно)

Это самый тонкий пункт задания. Разбираю строго, с учётом что `stickyDrainCount` — ГЛОБАЛЬНЫЙ `atomic.Int32` на transport, а `isSticky` — ПЕР-СЛОТ `atomic.Bool` на `*poolSlot`.

**Ключевой код-факт (verified):** `tearDown` в drainWatchdog (`ws_pool_drain.go:613`) вызывает `handleSlotDeath(...deathCauseDrainTeardown)` ВНУТРИ тела функции, ПЕРЕД её return. `handleSlotDeath` для drainTeardown ставит `p.slots[idx] = nil` под reserveMu (`ws_pool.go:2864-2866`). Новый слот той же ячейки создаётся ТОЛЬКО через `connectSlot` (`:1475` `&poolSlot{}` — НОВЫЙ указатель, `isSticky=false` zero-value). `defer p.releaseSticky(oldSlot)` (§4) сработает на выходе из старого watchdog, ПОСЛЕ tearDown→handleSlotDeath.

**Разбор последовательности из задания (oldSlot стал sticky, потом recycle, новый стал sticky):**
1. oldSlot.markSticky: CAS(false→true)=true → `count.Add(+1)` → count=1, isSticky_old=true.
2. deadline продляется N раз (markSticky идемпотентен через CAS → больше НЕ инкрементит, `:157` `CompareAndSwap(false,true)` вернёт false). count остаётся 1. ✓ (важно: повторные продления одного слота НЕ накручивают глобальный счётчик).
3. backstop/idle/quota → tearDown → handleSlotDeath → `slots[idx]=nil`. isSticky_old всё ещё =true, count всё ещё =1. (releaseSticky пока НЕ вызван — он в defer.)
4. **Окно:** ячейка nil. Новый дренаж той же idx НЕ может стартовать, пока connectReserveSlot/reconnect не поставит новый `*poolSlot` в ячейку. Когда поставит — это НОВЫЙ указатель, isSticky_new=false.
5. Новый watchdog (другого дренажа) markSticky(newSlot): CAS(false→true)=true → count.Add(+1) → count=2, isSticky_new=true.
6. Старый defer releaseSticky(oldSlot): `isSticky_old.Swap(false)`=true → count.Add(-1) → count=1, isSticky_old=false.
   **Итог: count=1, ровно один реально-sticky слот (newSlot). КОРРЕКТНО.**

**Проверка «новый слот НЕ стал sticky»:** после шага 3 count=1, isSticky_old=true. Старый defer: Swap(false)=true → Add(-1) → count=0. Корректно (нет активных sticky). ✓

**Проверка порядка 5↔6 переставлен (старый release РАНЬШЕ нового mark):**
- 6': releaseSticky(oldSlot): Swap(false)=true → count=0.
- 5': markSticky(newSlot): CAS=true → count=1. Корректно. ✓

**Проверка двойного release (паника + defer):** releaseSticky идемпотентен — `Swap(false)` второй раз вернёт false → НЕТ Add(-1). Утечки/двойного декремента нет. ✓

**Почему глобальный счётчик НЕ рассинхронизируется, хотя он общий:** инвариант держится потому, что (а) `isSticky` живёт на КОНКРЕТНОМ `*poolSlot` и обнуляется zero-value у каждого нового слота, (б) каждый `Add(+1)` парен ровно одному `Add(-1)` через CAS/Swap-гейт НА ТОМ ЖЕ указателе, (в) старый и новый watchdog работают с РАЗНЫМИ указателями, поэтому их CAS/Swap независимы и не «крадут» флаг друг у друга (классический баг v1 был бы при ключевании по idx → `p.slots[idx].isSticky`, где новый и старый дёргали бы ОДИН флаг). v2 явно ключует по захваченному `*poolSlot` (§4, §10/H2). Add(+1)/Add(-1) на глобальном atomic коммутативны и парны → сумма всегда = числу слотов с isSticky=true. **Счётчик НЕ врёт. ЗАКРЫТО.**

**Подтверждение временной изоляции (то, что v1 требовал доказать):** между tearDown(handleSlotDeath nil-cell) и появлением нового `*poolSlot` ячейка = nil, claimFreeSlot её не отдаст под markSticky до connectSlot. А connectSlot создаёт чистый слот. Старый defer бьёт по старому указателю независимо от того, что в ячейке. Окна, где markSticky нового и releaseSticky старого делят ОДИН указатель, не существует. -race тест §5 обязателен — оставить.

### A.H3 — bimodal lifetime → ЗАКРЫТО для дизайн-стадии

v2 §6.2 НЕ утверждает «всё ок» (это была претензия v1). Честно: «sticky до 10min = выброс ~2.6× за штатный диапазон [120s,232s], видимый в flow-age гистограмме TSPU». Даёт три смягчения (sticky только на реальную активность; динамический cap≤poolSize/2; абс. потолок 10m) + ОБЯЗАТЕЛЬНУЮ канареечную метрику разброса lifetime + явный follow-up с конкретными порогами усиления (10m→5m, авто→poolSize/4, 5s→2.5s) «по цифрам, не вслепую». Для дизайн-стадии это адекватно: риск назван, измеряем, есть план реакции. **ЗАКРЫТО для дизайн-стадии** (полевое подтверждение — на канарейке, §9 шаг 6).

### A.H4 — клинч readyCapacity → ЗАКРЫТО (с off-by-one оговоркой, выношу в новый MEDIUM)

v2 §4: динамический гейт `readyCapacity() <= readyCapacityFloor()` в `stickyQuotaAvailable` + досрочное снятие уже-sticky слота (§3.4 case перед quota-гейтом). Это системно сильнее статического poolSize/2 v1.

**Критичная проверка задания «гейт ДО или ПОСЛЕ входа слота в drain; не считает ли слот сам себя»:**
Код-факт: `readyCapacity()` (`ws_pool.go:604-612`) считает ТОЛЬКО `slot.getState()==slotReady`. К моменту, когда watchdog проверяет квоту в deadline-ветке, oldSlot УЖЕ в `slotDraining` (переведён в startDrain Gate 6 `:422` ДО спавна watchdog `:487`). **Значит oldSlot НЕ входит в собственный readyCapacity** — off-by-one «слот считает сам себя» отсутствует для дренируемого слота. ✓ Это в пользу v2.

**НО найден тонкий момент (новый MEDIUM, см. Б/M1-v2):** динамический гейт измеряет readyCapacity в момент tick'а, а его reserve-замена (connectReserveSlot) могла УЖЕ стать slotReady. Тогда «удержание ещё одного слота в slotDraining фактически вычитает 1 из эффективной ёмкости» (комментарий §4) уже НЕ верно — replacement поднялся, дренируемый слот свою ёмкость уже отдал. В этом случае гейт `readyCapacity<=floor` консервативен (может отказать в sticky/снять sticky, хотя ёмкость здорова). Это fail-safe в сторону ротации (безопасно для анти-TSPU), но может рвать закачки чаще необходимого. Не блокер — поведение «безопасное по умолчанию», но стоит зафиксировать в §4 что гейт намеренно консервативен и реальная просадка ёмкости может уже быть скомпенсирована reserve. **H4 как «клинч» ЗАКРЫТ** (клинч невозможен: floor слотов всегда ротируются, досрочное снятие саморазрешает); остаточная неоптимальность вынесена в MEDIUM.

### MEDIUM

#### M1-v2 — Динамический гейт readyCapacity консервативен: replacement уже мог подняться (ложно-частое снятие sticky)

**Где:** §3.4 case досрочного снятия + §4 `stickyQuotaAvailable` динамический гейт.
**Суть (от кода):** `readyCapacity()` (`ws_pool.go:604`) считает slotReady-ячейки в момент tick'а. Дренируемый oldSlot не входит (он slotDraining — верно). Но его reserve (`connectReserveSlot` → `slotReader`, `ws_pool_drain.go:545`) к моменту deadline-тика (≥90s после старта дренажа + recheck 5s) с подавляющей вероятностью УЖЕ slotReady. Тогда премиса §4 «удержание ещё одного слота в slotDraining вычитает 1 из ёмкости» НЕВЕРНА — ёмкость уже восстановлена reserve'ом, а дренируемый слот лишь «висит сверху». Гейт `readyCapacity<=floor` в этой ситуации измеряет здоровую ёмкость и НЕ должен срабатывать → ложного снятия обычно не будет. Проблема проявится только при реальной просадке (несколько reserve не поднялись). То есть гейт корректен по направлению (fail-safe → ротация), но его *обоснование* в §4 неточно описывает механику для штатного случая.
**Почему MEDIUM, не выше:** ошибка в сторону безопасности (предпочитает ротацию = анти-TSPU сохранён). Не вызывает клинч, не врёт счётчику. Влияет лишь на UX-хвост (закачка может порваться чуть чаще, чем строго необходимо).
**Рекомендация:** в §4 уточнить, что гейт ловит ИМЕННО просадку reserve (а не «всегда −1»), и что в здоровом пуле sticky активируется/держится свободно. Тест §5 H4-инварианта должен проверять ОБА: (а) здоровый reserve → sticky НЕ снимается ложно; (б) медленный reserve → sticky снимается, пул ротируется.

#### M2-v2 — Гонка `deadline.Reset(recheck)` vs ticker idle-ветка: окно до 2× интервалов на teardown активного→idle стрима

**Где:** §3.4 (deadline-ветка делает `markSticky`+`Reset(stickyRecheckInterval=5s)`) и параллельная ticker-ветка (`ws_pool_drain.go:631`, тик каждые drainPollInterval).
**Суть:** после продления стрим может стать idle. Его поймает либо ticker idle-ветка (`:637`, через ≤drainPollInterval), либо следующий deadline tick (через 5s, idle-первый-case §3.4). Худший случай: idle настал сразу после tick'а обеих веток → teardown отложен до min(drainPollInterval, 5s). Спека L3/§2.3 требует `stickyRecheckInterval ≥ drainPollInterval`, что гарантирует, что ticker поймает idle РАНЬШЕ deadline → задержка ограничена drainPollInterval, не 5s. Это уже учтено. Остаточный риск: лишний idle-период (один лишний цикл удержания ~5s после реального завершения закачки). Для скрытности это +5s к lifetime sticky-слота — пренебрежимо vs 10m потолок.
**Почему MEDIUM:** не баг, но §3.4 не показывает явно, что между двумя ветками НЕТ двойного teardown (Go select атомарен по выбору ветки, tearDown делает `return` — повторного входа нет). Стоит зафиксировать инвариант «tearDown ровно один раз» явно (в v1 H2 это отмечалось как ОК, но в v2 псевдокоде §3.4 повторного return-guard'а в комментарии нет).
**Рекомендация:** добавить в §5 инвариант «tearDown идемпотентен по факту return из watchdog (не вызывается дважды)»; в §3.4 пометить, что idle-case в deadline-ветке и idle-ветка ticker'а взаимоисключающи в одном select-проходе.

#### M3-v2 — Метрика `shadowlink_drain_sticky_active_slots` как gauge = stickyDrainCount: чтение неатомарно консистентно, но снапшот может «застрять» >0 при долгом sticky

**Где:** §6.1 `shadowlink_drain_sticky_active_slots # gauge = stickyDrainCount`.
**Суть:** gauge читает глобальный `stickyDrainCount.Load()`. Корректно по значению (H2 доказал, что счётчик не врёт). Но: при штатном долгоживущем sticky (до 10m) gauge будет держать >0 длительно — это ОЖИДАЕМО, не баг. Риск иной: если канареечный алерт повесить на «active_slots > 0 длительно» как на аномалию, он будет ложно срабатывать на нормальной большой закачке. Спека §6.2 говорит «sticky — редкое событие», но gauge>0 на 10m выглядит как «залипание» для наивного алерта.
**Почему MEDIUM:** операционный риск ложных алертов, не функциональный баг.
**Рекомендация:** в §6.1 указать, что `active_slots>0` в течение до StickyMaxDrainAge — НОРМА; алерт строить на `quota_denied_total` rate и на разбросе lifetime (§6.2), а не на самом факте active_slots>0.

### LOW

#### L1-v2 — Асимметрия «байты от connect / от reset» (§3.3): byte_budget-путь де-факто допускает суммарно ~230MiB на TCP

**Где:** §3.3, §10/B2. Разобрано в части А.B2. Для byte_budget-дренажа потолок «на TCP» = бюджет (≤30MiB) + ≤200MiB от reset. Безопасно (рвём раньше по первому byte_budget), но номинал «~200MiB на TCP» неточен для этого пути.
**Рекомендация:** одна строка в §3.3: «для byte_budget-пути суммарный байтовый возраст TCP может достигать ~(budget+StickyMaxTotalBytes); это приемлемо, т.к. первый byte_budget уже размыл per-flow кластер».

#### L2-v2 — `effectiveStickyMaxSlots` при poolSize=2 → cap=1: вырожденный bimodal (1 sticky из 2)

**Где:** §4 `half := poolSize/2; if half<1 {half=1}`. При clamp poolSize min 2 (`ws_pool.go:1082-1084`) → half=1. Один слот sticky, второй несёт всю ротацию = ровно тот вырожденный bimodal, что H3 называет сигналом, но на минимальном пуле. v2 §5 имеет тест «poolSize=2 (cap=1, вырожденный bimodal)» — то есть это ОСОЗНАНО.
**Почему LOW:** дефолтный пул = 6 (CLAUDE.md Phase D), poolSize=2 — только аварийный clamp. Принято с тестом.
**Рекомендация:** рассмотреть для poolSize≤2 принудительно cap=0 (sticky off) — на пуле из 2 слотов цена bimodal выше выгоды одной закачки. Решение оставить автору (политическое).

#### L3-v2 — `effectiveStickyMaxSlots` динамический гейт может дать 0 эффективных при нездоровом пуле (фича не активируется когда нужнее всего)

**Где:** §4 + вопрос задания. При `readyCapacity<=floor` гейт всегда отказывает → sticky не активируется. Парадокс: большая закачка рвётся именно тогда, когда пул деградировал (а это и есть момент, когда юзер сильнее всего страдает от обрыва).
**Анализ:** это ПРАВИЛЬНЫЙ fail-safe, не баг. Логика: при просадке ёмкости приоритет — восстановить ротацию/ёмкость пула (иначе анти-TSPU теряется для ВСЕХ стримов), а не спасать одну закачку. v2 §4 «приоритет: ротация > обрыв одной закачки» это и фиксирует. Альтернатива (держать sticky при деградации) хуже — усугубляет клинч (исходный H4).
**Почему LOW:** поведение корректное и осознанное; претензия только к тому, что §6.2 продаёт фичу как «спасает большие закачки», но в деградированном пуле она сознательно НЕ спасает. Это надо назвать явно, чтобы канарейка/юзер не сочли «фича не работает».
**Рекомендация:** одна строка в §4 или §6.2: «при деградации пула (readyCapacity≤floor) sticky сознательно отключается — приоритет восстановлению ёмкости; остаточные обрывы в этом режиме НЕ считать провалом фичи (отделять по метрике quota_denied при низком readyCapacity)».
