# WhiteCall — анализ аккаунтов / регистрации / гостевого доступа

Дата: 2026-06-05
Вопрос: горят ли ЛИЧНЫЕ аккаунты юзеров при туннелировании через SFU/TURN видеозвонков
(VK Calls, WB Stream, Yandex Telemost, MAX, Jitsi), или можно работать через
одноразовые/левые/гостевые аккаунты? Критично для оценки юр-риска продукта WhiteCall.

Метод: WebFetch README/docs изучаемых проектов + WebSearch (Habr, ntc.party).
Изученные проекты:
- github.com/kulikov0/whitelist-bypass (эталон, SFU/headless creator)
- github.com/cacggghp/vk-turn-proxy (TURN+DTLS, VK/Yandex)
- github.com/amurcanov/proxy-turn-vk-android (WDTT — автокапча, fallback client_id)
- github.com/zarazaex69/olcRTC (Jitsi/Telemost/WbStream, TCP-over-WebRTC)
- Habr «Lionheart» (habr.com/ru/articles/1017410/) — первоисточник WB Stream-метода

| Плечо | Нужен аккаунт? | Гостевой доступ? | Можно левый/одноразовый? | Что банится при abuse |
|---|---|---|---|---|
| **VK Calls** | ДА, обязательно | НЕТ | Можно, НО аккаунт жёстко привязан к номеру телефона (см. ниже) | client_id + captcha-шейпинг + throttle до 250кбс; аккаунт под риском |

## ДЕТАЛЬНО ПО ПЛЕЧАМ

### 1. VK Calls — ХУДШИЙ по юр-риску
- **Аккаунт обязателен, привязан к номеру телефона.**
  - vk-turn-proxy (cacggghp): *«Ссылка на действующий ВК звонок: создаём свой (нужен аккаунт вк)»*,
    *«Логин/пароль от TURN генерируются из ссылки на звонок»*.
  - whitelist-bypass (kulikov0): VK требует **cookies, экспортированные из desktop-приложения**
    (кнопка `VK Cookies`), формат JSON `[{"name":"..","value":".."}]` или `--cookie-string`.
  - ntc.party (Turnable thread, 2 мая 2026), прямая цитата по смыслу:
    *«WB в принципе позволяет создавать звонок без аккаунта, а VK строго привязан к номеру телефона.»*
- **Гостевого доступа НЕТ.**
- **Левый аккаунт:** технически да, но он всё равно требует SIM/номер при регистрации VK
  (а номер в РФ — это паспорт). Одноразовость дорогая.
- **Что банится / contromeasures (Habr «6 способов», апрель 2026):**
  *«VK натыкал капч»*, *«VK теперь шейпит до 250кбс»* (UPD Wed Apr 29 2026).
  WDTT (amurcanov) реагирует на это: имеет **fallback client_id** (2 проверенных значения
  `6287487` и `8202606`, переключение при отказе авторизации) и **режим «Авто капча»**
  (цепочка Go v2 solver → Auto WebView → manual WebView). То есть авторы уже борются
  с активным противодействием VK на уровне client_id/captcha.

### 2. WB Stream (Wildberries) — ЛУЧШИЙ по юр-риску
- **Аккаунт НЕ нужен. Чистый анонимный гость.**
  - whitelist-bypass: *«WB Stream uses anonymous guest tokens, so no cookies are required»*.
  - Lionheart (Habr, первоисточник): поток —
    `POST /auth/api/v1/auth/user/guest-register` *«POST с произвольным displayName. В ответ — JWT»*.
    Далее `/api-room/.../room` → `/join` → `/token` → WebSocket → ICE TURN creds.
  - Lionheart прямо: *«API-эндпоинты отвечают нормально — никаких cookies, CSRF, капч,
    проверок TLS fingerprint.»*
- **Гостевой токен одноразовый и disposable** — «no persistent identity is required, each
  connection generates disposable guest credentials». Личного аккаунта нет → **горение
  личного аккаунта структурно невозможно.**
- **Что банится:** только платформенный room/JWT/host (`wbstream01-el.wb.ru` хардкод).
  Авторы отмечают хрупкость: *«TURN credentials привязаны к одной платформе — если WB Stream
  изменит API или ужесточит ограничения, всё сломается»*. Но это ломает МЕТОД, а не аккаунт юзера.
- **На июнь 2026: всё ещё guest, регистрации НЕТ** (см. отдельный раздел ниже).
- olcRTC docs (about.md) формально пишет про wbstream «credentials через WbStream API,
  с отдельной регистрацией» — но это «регистрация» = тот самый guest-register POST,
  а не личный аккаунт; config (configuration.md) не требует ни cookies, ни credentials,
  только `room.id`. Расхождение терминологии, не факта.

### 3. Yandex Telemost — средний риск
- **Аккаунт/регистрация нужны.**
  - whitelist-bypass: cookies из desktop creator (кнопка `Yandex Cookies`), JSON.
  - olcRTC about.md: *«credentials через Yandex Telemost API, с отдельной регистрацией»*.
  - vk-turn-proxy: Yandex упоминается рядом с VK как TURN-источник.
- **Гостевого доступа в проектах НЕТ** (требует cookies/регистрацию).
- **Левый Яндекс-аккаунт:** допустимо (email-регистрация Яндекса проще VK, не всегда требует номер) —
  но это всё ещё идентичность, которую можно банить.
- **Что банится / countermeasure:** Habr — *«Yandex настроил TURN-серверы релеить только
  на Yandex IP»* (т.е. зарезали сам relay, не обязательно аккаунт). Direct-режим `-no-dtls`
  в vk-turn-proxy: *«Может привести к бану от вк/яндекса»* — единственное прямое предупреждение о бане.

### 4. MAX (госмессенджер VK-экосистемы) — НЕ объект туннелирования
- **Звонки есть:** MAX использует WebRTC, ~30 млн звонков/день, групповые без лимита участников,
  **E2E-шифрования НЕТ** (Habr-обсуждение).
- **В whitelist ТСПУ — да:** домен `max.ru` в белых списках, MAX предустанавливается на новые
  телефоны в РФ («единственный мессенджер, который останется работать»).
- **НО ни один из изученных проектов MAX НЕ туннелирует.** Архитектура MAX как SFU/TURN-донора
  публично не реверсилась в этих проектах.
- **Контр-риск (важно для WhiteCall):** Habr-разбор MAX — приложение **детектирует VPN-соединение**
  и по команде сервера может блокировать доступ к чатам/мини-аппам, пока VPN не выключен;
  сбор IP-адресов «для корректной работы звонков» вызвал подозрения в анализе эффективности
  блокировок. MAX как плечо = высокий регуляторный/комплаенс-риск, не рекомендуется.

### 5. Jitsi — без аккаунта, но self-hosted
- **Регистрации нет.** olcRTC about.md: *«URL комнаты Jitsi (`meet.small-dm.ru`,
  `meet1.arbitr.ru`, `meet.handyweb.org`), без отдельной регистрации»*. Config — только room URL.
- **Гостевой/анонимный вход по room URL.** Аккаунт юзера не задействован → нечему гореть.
- **Нюанс:** это НЕ российская whitelist-платформа по умолчанию. Перечисленные инстансы —
  сторонние Jitsi-серверы; нужно проверять, попадает ли конкретный инстанс в белый список
  (olcRTC: *«Обязательно проверяйте, есть ли сервис видеозвонков в белых списках»*).
  «Банить» нечего на уровне аккаунта, но инстанс могут выкинуть из whitelist / заблокировать.

## ВОПРОС 7: WB Stream — guest или регистрация в июне 2026?

**Guest, без регистрации, на июнь 2026 регистрацию НЕ ввели.**
- Не нашёл НИ ОДНОГО источника, датированного июнем 2026, о введении регистрации/аккаунта
  для `guest-register`.
- Самые свежие данные — ntc.party (Turnable thread, **2 мая 2026**): пользователь подтверждает,
  что **«WB в принципе позволяет создавать звонок без аккаунта»** (в противовес VK с номером).
- Lionheart + форк vk-turn-proxy (kiper292, `wb.go`: «WB Stream: guest register → room → LiveKit ICE»)
  по-прежнему строят поток на `guest-register` POST без cookies/капч.
- Честно: данных строго за июнь 2026 (последняя неделя) нет — последнее подтверждение конец мая 2026.
  Если WB ужесточил за ~5 недель — это бы сломало форки, публичных репортов о поломке не найдено.

## ЧТО СОВЕТУЮТ САМИ АВТОРЫ ПРО АККАУНТЫ

- **Прямых дисклеймеров «не используйте основной аккаунт» в README НЕТ ни в одном проекте.**
  Это пробел: авторы не предупреждают о риске личного аккаунта явно.
- Общие дисклеймеры: vk-turn-proxy — *«Только для учебных целей!»*; Lionheart — автор
  *«не рекомендует использовать для обхода сетевых ограничений»* (side-effect, не фича).
- Единственное предупреждение о бане: vk-turn-proxy про `-no-dtls` direct-режим —
  *«Может привести к бану от вк/яндекса»* (про IP/relay, не про личный аккаунт прямо).
- WDTT (amurcanov): предупреждает не о бане, а о механике —
  *«При выходе из звонка нажимайте „Просто завершить“, а не „Завершить для всех“.
  Если закрыть комнату для всех, хеш перестанет работать.»*
- **Автоматизация регистрации/токенов есть только у WB (guest-register, тривиально) и
  у WDTT для VK (autocaptcha + fallback client_id).** Пула личных аккаунтов / автогенерации
  VK-аккаунтов ни у кого нет — VK-аккаунт всё равно создаётся вручную через номер.

## ГЛАВНЫЙ ВЫВОД ДЛЯ WhiteCall

**Избежать «горения личных аккаунтов» — ЧАСТИЧНО, и это резко зависит от выбора плеча:**

- **WB Stream — ДА, полностью избегаемо.** Анонимный guest-register, одноразовый JWT,
  нет cookies/капч/идентичности. Личный аккаунт клиента в принципе не задействован.
  **Это безопасное по аккаунт-риску плечо №1 на июнь 2026.**
- **Jitsi — ДА (но не РФ-whitelist по умолчанию).** Анонимный вход по room URL, аккаунта нет.
  Проблема не в аккаунте, а в попадании инстанса в белый список.
- **VK Calls — НЕТ.** Обязателен аккаунт, жёстко привязанный к номеру телефона
  (= паспорт, переписки, Госуслуги). VK активно противодействует (капчи, throttle 250кбс,
  client_id-блок). Туннелирование через VK = прямой риск ЛИЧНОГО аккаунта клиента.
  Левый VK-аккаунт требует левую SIM — дорого и тоже под риском бана.
- **Yandex Telemost — ЧАСТИЧНО.** Нужна идентичность (cookies/регистрация), но левый
  Яндекс-аккаунт дешевле VK (email, не всегда номер). Yandex режет TURN на свои IP →
  ломает метод. Риск личного аккаунта средний, если использовать отдельный Яндекс-аккаунт.
- **MAX — не плечо.** Никто не туннелирует; вдобавок MAX сам детектирует VPN и сообщает серверу.
  Высокий регуляторный риск. Исключить из рассмотрения.

**Рекомендация по архитектуре WhiteCall:** строить на **WB Stream (guest)** как основном плече —
там «горение личного аккаунта» структурно невозможно. **Не строить на VK Calls** для массового
продукта — это прямой перенос юр-риска на личный VK клиента. Jitsi — резерв при условии
whitelisted-инстанса. Главная хрупкость WB-метода — не юридическая, а техническая: всё держится
на одном недокументированном guest-эндпоинте, который WB может закрыть в любой момент.
