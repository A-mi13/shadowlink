## 2. Архитектура kulikov0/whitelist-bypass (основной объект)

### Два режима туннеля
- **DC (DataChannel):** Pion открывает SCTP DataChannel на стороне publisher PC и туннелирует TCP/UDP внутри. Фреймы проходят через SFU платформы как обычная DataChannel-нагрузка.
- **Video (VP8):** туннель «едет» внутри опубликованного VP8 видеотрека вместо SCTP DataChannel — для платформ, которые рейт-лимитят DataChannels, но пропускают RTP. Есть `configurable VP8 pacing` и `VP8 bandwidth control` (из release notes).

### Роли
- **Joiner** (в цензурированной сети, РФ): `VpnService → tun2socks (IP→TCP) → SOCKS5 → headless Pion joiner → DataChannel/VP8 туннель`.
- **Creator** (в открытой сети, за рубежом): `headless Pion creator ↔ SFU платформы ← relay bridge → Internet`.
- Трафик идёт через whitelisted SFU и для DPI выглядит как обычный видеозвонок.

### Компоненты репозитория
- `relay/` — Go-релей: SOCKS5, tun2socks, tunnel codec, ChaCha20-обфускатор, мультиплексор, iOS-bindings. Подпакеты: `androidbind`, `common`, `desktoptun`, `dion`, `livekit`, `pion`, `telemost`, `tunnel`, `wbstream`; файлы `dc_creator.go`, `main.go`.
- `headless/` — чистые Go API-creators (VK, Telemost, WB Stream) и joiners на Pion без браузера. Подпапки: `vk`, `telemost`, `wbstream` + `-joiner` варианты, `docker`, `tests`.
- `android-app/` — VpnService-joiner (VpnService + tun2socks + Pion).
- `ios-proxy-app/` — SOCKS5-only joiner через gomobile.
- `creator-app/` — Electron GUI (legacy browser + headless пути).
- `hooks/` — JS-хуки для legacy браузерного режима (DC/Video для VK/Telemost).

### Стек / зависимости (из `relay/go.mod`)
- **Go 1.26.1** (свежак — учесть в нашей CI).
- `pion/webrtc/v4 v4.2.9`, `pion/datachannel v1.6.0`.
- `tun2socks v2.6.0` (tun-интерфейс), `gvisor.dev/gvisor` (сетевой стек), `gorilla/websocket v1.5.3`, `google/uuid`.
- Индиректы: полный pion-набор (DTLS, ICE, SRTP, TURN) + `golang.zx2c4.com/wireguard`.
- smux/chacha20 не в прямых зависимостях — обфускатор, видимо, реализован внутри `tunnel`/`common`/`dion` (свой код, не внешняя либа). Не удалось вытащить точный файл обфускатора через raw (директория видна, конкретный .go не достал) — **TODO при реальной интеграции: прочитать `relay/tunnel` и `relay/common` напрямую через git clone.**

## 3. Как получают доступ к SFU (ключевой вопрос масштабируемости)

Из README (`/blob/main/README.md`):
- **VK creator:** требует **cookies**, экспортированные из desktop creator app (кнопка `VK Cookies`), формат JSON `[{"name":"..","value":".."}]`. То есть **нужен залогиненный VK-аккаунт** (cookies = сессия живого аккаунта). Привязка к call: `--vk-link https://vk.com/call/join/<token>`.
- **Telemost creator:** аналогично — **cookies Yandex** (`Yandex Cookies`). Привязка: `--tm-link https://telemost.yandex.ru/j/<id>`.
- **WB Stream:** **анонимные guest-токены, cookies НЕ нужны.** Привязка: `--room <uuid>`. ← это самый «бесаккаунтный» путь.
- Капча/верификация телефона/создание аккаунта в README **не описаны** (в отличие от WDTT, где явно заявлено авто-решение VK Smart Captcha).

**Вывод по доступу:** VK и Telemost = привязка к живым cookie-сессиям (значит — к аккаунтам, которые надо где-то брать, греть и ротировать). WB Stream — гостевой, без аккаунта = **наименее хрупкий путь для автоматизации/масштаба** (это важный инсайт для нашей оркестрации).

## 4. СЛАБЫЕ СТОРОНЫ ЭТАЛОНА = наши точки роста

Из open issues (https://github.com/kulikov0/whitelist-bypass/issues) и архитектуры:

1. **Ручное создание звонков, нет оркестрации пула.** Creator запускается вручную с флагами `--vk-link/--tm-link/--room`, привязка к одному звонку. Нет пула звонков, нет балансировки, нет автоподнятия нового звонка при падении. ← **наш оркестратор закрывает это.**
2. **Один аккаунт/cookies-сессия, нет ротации.** VK/Telemost привязаны к одному набору cookies. Нет пула аккаунтов, нет ротации до бана, нет «прогрева». Для масштаба на сотни юзеров это узкое горло. ← **наш пул аккаунтов + ротация.**
3. **Нет детектора бана/деградации и авто-пересоздания сессии.** Issue #122 «wb dc вырубается через 2 минуты ровно» — стабильный обрыв, который никто автоматически не лечит. Issue #116 «на 0.3.4 все равно не робит DC WB». Issue #112 iOS «подключается к звонку, и на этом всё». Нет телеметрии «жив/деградирует/забанен» → нет авто-failover. ← **наш мониторинг + canary + авто-rotate (у нас уже есть похожая механика в ShadowLink: slot reader errors, meltdown counter, anomaly classifier — переносимо).**
4. **Скорость и легаси-путь.** Legacy браузерный путь (Android WebView + Electron + JS hooks) «slower, can't obfuscate, is being phased out». Headless быстрее, но конкретных throughput-цифр проект НЕ публикует (не удалось найти бенчмарки). VP8-видеорежим по природе ограничен битрейтом видеотрека и pacing'ом. Мультистрим/агрегация каналов в README не заявлены. ← **мультиплексирование звонков/каналов для агрегации полосы — наша надстройка.**
5. **Нет управления/мониторинга/UI на стороне оператора.** Только CLI-флаги и Electron GUI для ручного создателя. Нет централизованной панели: какие звонки живы, сколько юзеров, какой трафик, какие аккаунты сгорели. ← **наша React-админка + WS-стриминг логов уже готовы под это.**

Доп. слабые места (из issues и анализа):
- Стабильность на мобильных привязана к WB DC «2-минутному» обрыву (#122) — намёк на server-side/SFU таймаут, который требует keep-alive/пере-публикации. Карьер-специфики (Мегафон/Tele2/МТС/LTE) в issues явно не вынесено — **не удалось** найти прямых данных, но #119 «катка в играх не начинается» = проблемы с UDP/латентностью игрового трафика.
- DTLS-fingerprint остаточный: туннель идёт через настоящий WebRTC/Pion-стек, значит DTLS ClientHello = Pion-фингерпринт, а не браузерный. На фоне «звонка из браузера» это потенциальный различитель для продвинутой DPI. В README не адресовано. ← **потенциальная точка нашей работы (uTLS-аналог для DTLS), у нас уже есть экспертиза по uTLS-фингерпринтам.**
- Проект фактически **одноавторский**: kulikov0 = 85 коммитов, ещё двое по 1 коммиту. Bus-factor = 1. Когда VK ломает протокол — чинит один человек, и issues копятся (#127, #131, #132 свежие, нерешённые). ← риск для зависимости, аргумент в пользу собственного контроля над transport-ядром.

## 5. Что переиспользуем как transport-ядро vs что строим сами

### Переиспользуем (transport-ядро, MIT — берём из kulikov0):
- **`relay/` Go-пакеты:** SOCKS5-прокси, tun2socks-интеграция, tunnel codec, ChaCha20-обфускатор, мультиплексор. Это самое ценное и сложное — рабочий, отлаженный SFU-туннель на Pion.
- **`headless/` creators+joiners** для VK/Telemost/WB Stream — готовая API-механика поднятия звонка и присоединения без браузера. Особенно **WB Stream (guest-токены)** как наименее хрупкий путь.
- **Pion v4 WebRTC pipeline** (DataChannel + VP8) — основа transport'а.
- Идеи из **olcRTC (WTFPL)**: XChaCha20-Poly1305 + smux-мультиплексирование поверх каналов — можно заимствовать как улучшение обфускации/мультиплекса (другая лицензия, но совместимая).

### Строим сами (наша надстройка поверх transport-ядра):
- **Оркестрация пула звонков** — авто-создание/балансировка/пере-создание call-сессий (через наш SSH-оркестратор деплоим creator-серверы за рубежом).
- **Пул аккаунтов VK/Yandex + ротация cookies** до бана, прогрев, учёт «сгоревших» аккаунтов. (WB Stream — без аккаунтов, приоритетный путь для автоскейла.)
- **Детектор бана/деградации + авто-failover** — переносим механику из нашего ShadowLink (slot reader errors, meltdown counter, anomaly classifier, canary-мониторинг).
- **Мониторинг в админке** — живые звонки, трафик, статус аккаунтов, WS-стриминг логов (инфраструктура у нас есть).
- **Биллинг/планы/устройства** — наш существующий слой (auth_devices, тарифы, рефералы) поверх.
- **Поведенческая мимикрия + DTLS-fingerprint hardening** — наша анти-DPI экспертиза (по аналогии с uTLS Chrome-фингерпринтом в ShadowLink).
- **Деплой creator-серверов** через наш SSH-оркестратор (у эталона это ручной запуск бинаря).

### Не берём (GPL — только идеи):
- vk-turn-proxy и WDTT: подход **TURN ChannelData + DTLS-обфускация поверх WireGuard** — концептуально интереснее (TURN relay вместо полноценного SFU-звонка = меньше overhead, чем VP8). Но код GPL — реализовывать с нуля, если решим идти TURN-путём вместо SFU-путём.

## 6. ВЕРДИКТ: надстройка или transport с нуля?

**Реально сделать надстройку над базой kulikov0 — лицензия MIT это прямо позволяет.**

- Transport-ядро (`relay/` + `headless/` на Pion) — рабочее, отлаженное, MIT, на Go (наш стек). Берём как библиотеку/форк, изолируем (по аналогии с тем, как у нас изолирован `shadowlink/`).
- Наша уникальная ценность — ровно то, чего у эталона НЕТ: оркестрация пула, ротация аккаунтов, детектор бана, мониторинг, биллинг, деплой. Это мы уже умеем (ShadowLink + админка + SSH-оркестратор).
- Главные технические риски, которые надо валидировать ДО коммита в направление:
  1. **Throughput** — эталон не публикует цифры; VP8-режим ограничен битрейтом видео. Нужен свой замер на pl1/реальном звонке (DC-режим vs VP8-режим, агрегация нескольких звонков).
  2. **WB DC «2-минутный» обрыв** (#122) — понять причину (SFU-таймаут?) и закрыть keep-alive/re-publish'ем, иначе мобильная стабильность пострадает.
  3. **Источник и ротация VK/Yandex аккаунтов** — операционно сложная задача (cookies живых сессий). Приоритет — WB Stream guest-путь, где аккаунты не нужны.
  4. **DTLS-fingerprint** — Pion-стек различим от браузера; оценить риск для РФ-DPI.
  5. **Bus-factor эталона = 1** — мы должны быть готовы сами чинить transport при поломках VK, а не ждать апстрим. Это аргумент за форк (контроль кода), а не за runtime-зависимость от чужих релизов.

**Итого:** не нужно писать transport с нуля — берём MIT-ядро kulikov0 как форк, надстраиваем нашу оркестрацию/управление/мониторинг/биллинг. Опционально заимствуем XChaCha20+smux идеи из olcRTC (WTFPL). GPL-проекты (vk-turn-proxy, WDTT) — только как источник идей для альтернативного TURN-пути, без копирования кода.
