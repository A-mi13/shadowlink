# Co-tenancy обход РФ mobile allowlist через whitelisted-IP — разведка

**Дата:** 2026-06-05
**Тип:** read-only research (РАЗВЕДКА, не реализация)
**Источник списка:** github.com/hxehex/russia-mobile-internet-whitelist (ветка `main`)

---

## TL;DR / Вердикт

**Co-tenancy РЕАЛЬНА, но узка и эфемерна — "частично ДА".**

В whitelist реально присутствуют shared-cloud диапазоны, на которых можно арендовать VM рядом с легитимными сервисами: **Yandex / Yandex Cloud (AS200350), Selectel (AS49505), Timeweb**. Это подтверждается и присутствием их CIDR в файле, и независимыми гайдами/обсуждениями. Но:

- Получить именно whitelisted-IP из пула стало почти невозможно (VK Cloud: «в 99% случаев больше не выдаёт белые IP новым пользователям»).
- IP палится **по поведению** (зарубежный трафик с РФ-IP), не по форме — и отзывается/банится за недели-месяцы.
- Модель фильтрации сместилась на **IP + SNI комбинированно**: даже идеальная SNI-мимикрия (то, что делает ShadowLink) НЕ проходит, если IP не в списке. Это подтверждает вывод из whitelist-whitepaper 2026-06-04: HTTPS-мимикрии недостаточно против allowlist.

## 1. Масштаб списка

| Файл | Содержимое | Кол-во |
|---|---|---|
| `ipwhitelist.txt` | отдельные IP (legacy формат, `.1` на подсеть) | **~5 000** строк |
| `cidrwhitelist.txt` | подсети CIDR (актуальный формат) | **~4 864** строк |
| `whitelist.txt` | домены/SNI | **1 179** доменов |

Файл `ipwhitelist.txt` — старый формат (по одному IP, обычно `.1` каждой /24); `cidrwhitelist.txt` — новый, в подсетях. Авторепозиторий обновляется через GitHub Actions; методология источников ASN в README НЕ опубликована (агрегация из открытых источников + сканы, как у родственных репо escapingworm/russia-whitelist).

**Важная оговорка о шуме в файле:** WHOIS-проверка показала, что `cidrwhitelist.txt` содержит много диапазонов, НЕ относящихся к РФ-cloud и вообще сомнительных для контекста:
- `2.78.x` → **AS29355 Kcell** (Казахстан, телеком)
- `33.63.x` → **AS749 US Department of Defense** (sic!)
- `81.213–81.217.x` → **AS9121 Türk Telekom** (Турция)
- `2.63.x` → **AS12389 Ростелеком** (РФ телеком)

То есть список — широкая агрегация, частично зашумлён/over-inclusive. Это перекликается с разбором на Хабре (997088): РКН сделал whitelist для **72 AS**, но под раздачу попал **391 AS / >225 млн IP** — реализация непоследовательна, с логическими дырами (главная страница сайта открывается, а соседний домен той же зоны — нет; обрыв после ~16 КБ). Вывод статьи: даже внутри одной whitelisted-ASN отдельные блоки/направления могут резаться → co-host через ASN-принадлежность **ненадёжен**.

Прочие зашумлённые крупные ASN в файле: Kcell (KZ), Türk Telekom (TR), US DoD — нерелевантны.

**Топ-5 значимых для co-tenancy (по присутствию + multi-tenancy):**
1. **Yandex Cloud — AS200350** (аренда VM/Functions/API Gateway, ~236 800 IPv4, RIPE/RU)
2. **Selectel — AS49505** (~994 IPv4 префикса, классический VPS/cloud)
3. **Yandex core — AS13238** (77.88/5.255 — CDN/инфра Яндекса)
4. **VK / VK Cloud — AS47764** (2565 IP, 10471 домен — максимальная плотность арендаторов; в whitelist через core-сервисы)
5. **Ростелеком — AS12389** (телеком, dedicated, co-host недоступен)

## 3. Доля shared-cloud vs dedicated (оценка)

Точную долю по 4 864 CIDR без полного WHOIS-прохода всех строк дать нельзя — **честно: точный процент не посчитан**. Но по структуре:

- **Преобладает dedicated телеком-инфраструктура** (Ростелеком, МегаФон, региональные операторы) + зашумлённые иностранные/гос ASN (DoD, Türk Telekom, Kcell) — на них co-host **невозможен** (стена: гос/банк/телеком/чужие страны).
- **Shared-cloud — меньшинство, но НЕ ноль:** подтверждённо присутствуют Yandex Cloud (51.250.x), Selectel (5.101.x, 79.137.x), плюс по гайдам Timeweb и VK Cloud. Это именно те диапазоны, где аренда VM рядом с whitelisted-сервисами технически возможна.

Грубая качественная оценка: **арендопригодный shared-cloud — единицы процентов от списка**, и из них реально получить whitelisted-IP — лотерея (нужно «перебрать как минимум 100 IP», по сообществу).

## 4. Что whitelisted в SNI (`whitelist.txt`) и пересечение с арендными cloud-диапазонами

1 179 доменов — это РФ-экосистема: `*.img.avito.st`, `*.mail.ru`, `*.yandex.ru`, `mc.yandex.ru`, `2gis.ru`, `ya.ru`, VK/OK, Ozon, Wildberries, Gosuslugi, Rutube, Mir, MAX, сайты госорганов.

Ключевой механизм (2 уровня):
- **L3:** IP в whitelist? нет → DROP (пакет исчезает). да → переход к L7.
- **L7:** SNI в blacklist? да → RST. нет → PASS.
- Тренд: **IP + SNI комбинированно** — даже идеальный spoof SNI не пройдёт без whitelisted-IP.

**Пересечение SNI ↔ арендные cloud-диапазоны:** домены Яндекса (`mc.yandex.ru`, `ya.ru`) и их CDN живут на AS13238/AS200350 — те же ASN, где можно арендовать VM. Отсюда и эксплойт: `functions.yandexcloud.net` «универсально в whitelist у всех операторов»; Yandex Functions/API Gateway/Cloud VM позволяют выйти трафиком с «железобетонно разрешённых IP Yandex Cloud». Для VK/Mail.ru core-IP в выборке файла не нашлись — пересечение слабее.

**Гос/банк (Gosuslugi, Mir, сайты госорганов)** сидят на dedicated-инфраструктуре — co-host туда невозможен (это и есть «стена»).

## 5. Эфемерность Aeza-подхода и практика хостеров (ключевые выводы)

1. **Aeza активно вычищает VPN по требованию РКН.** С 3 декабря 2025 Aeza рассылает «письма счастья»: РКН передал список IP из подсети `138.124/16`, поддержка требует удалить VPN-сервер и прислать скриншот, иначе блок услуги. Один автор мигрировал с Aeza на VDSina (Амстердам). Вывод: дешёвый РФ-хостинг под VPN **схлопывается** под регуляторным давлением — IP не «выпадает белым» как фича, а является краткоживущей случайностью до момента, когда хостер/РКН замечает.

2. **Co-tenancy на cloud живёт недели-месяцы, потом бан по поведению.** Прямое свидетельство (kort0881/russia-whitelist discussion #21): автор получил whitelisted VK Cloud IP, тот прожил **3.5 месяца** до suspension «из-за подозрений VPN-сервиса»; к январю 2026 метод в целом перестал работать (операторы стали детектить и блокировать эти диапазоны). VK Cloud «в 99% больше не выдаёт белые IP новым юзерам». На Хабре: сервер внутри РФ банится **активнее**, чем зарубежный; «прокладка» на юге РФ легла на месяц раньше связки без неё. Это ровно подтверждает тезис юзера: **палится по зарубежному трафику с whitelisted-IP, не по форме трафика.**

3. **Yandex Cloud whitelist — НЕ автоматом для арендатора.** Официальная дока Yandex Cloud: проживание в инфраструктуре Yandex Cloud «не делает ресурс whitelisted автоматически»; нужно обращаться в Минцифры, каждый сервис рассматривается индивидуально, whitelist только статических (reserved) публичных IP, рекомендуют подавать `/32`, нужно доказательство владения. То есть «легальный» путь к whitelisted-IP закрыт для рядового арендатора. Серый путь (поймать уже-whitelisted IP из пула / Functions) — лотерея и быстро сносится («Быстро сносят», API Gateway-метод уже забанен).

**Архитектурный итог для ShadowLink:** наиболее надёжная схема сообщества — **каскад из 2 серверов**: клиент → РФ-сервер с whitelisted-IP → зарубежный сервер → интернет (для ТСПУ это выглядит как межсерверный обмен, фильтруется слабее). Но whitelisted-IP в этой схеме — дефицитный, эфемерный, баннящийся по behavioral-сигнатуре ресурс. Co-tenancy даёт временное окно, не устойчивую опору. Согласуется с whitelist-whitepaper 2026-06-04: HTTPS/SNI-мимикрии (сильная сторона ShadowLink) недостаточно — упор переходит на дефицит whitelisted-IP, который мы не контролируем.
