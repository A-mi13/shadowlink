# Готовность к внедрению в нативные клиенты (Windows / Android / iOS)

Проверка 2026-08-21, после подтверждённого полевого прогона (ветка
`fix/keepalive-reaches-draining-slots`, `bf66f41`). Ответ на вопрос «с нашей
стороны всё готово?».

Короткий ответ: **Windows — да, Android — почти, iOS — нет.** Протокол и
клиентская логика готовы для всех трёх; отсутствует связующий слой (gomobile
bindings), и для iOS есть отдельное архитектурное ограничение, которое надо
решить ДО начала работ, а не в процессе.

## Что проверено фактически, а не по документации

| Проверка | Результат |
|---|---|
| `GOOS=android GOARCH=arm64 go build ./client/` | **OK** |
| `GOOS=ios GOARCH=arm64 go build ./client/` | **OK** |
| `GOOS=darwin GOARCH=arm64 go build ./client/` | **OK** |
| tun2socks | **встроен как Go-библиотека** (`github.com/xjasonlyu/tun2socks/v2`), внешний бинарь не нужен |
| gomobile-обёртка (`mobile/`, `bind/`) | **отсутствует** |
| Полный `go test ./...` | зелёный |

Дополнено 2026-08-24 (тулчейн поставлен, проверки перевыполнены):

| Проверка | Результат |
|---|---|
| `client/` под `android/arm64` **с CGO=1** (режим gomobile) | **OK** — главный риск снят |
| gVisor в зависимостях `./client` | **0 пакетов** (у `tun2socks/v2/engine` — 41) |
| gomobile + gobind + NDK 27.2.12479018 + JDK 21 | **установлены**, `gomobile init` прошёл |
| go.mod поднят `1.25.7` → `1.26.0` (нужен свежему `x/mobile`) | `build`+`vet` чисты, **18/18 пакетов зелёные**, сервер кросс-собирается (15.1 МБ) |
| Сборка `.xcframework` с этой машины | **невозможна физически** — gomobile требует Xcode/macOS |

⚠ `client/leakguard` компилируется под android/ios, **но работать там не
будет**: под Android это `guard_linux.go` с `iptables`/`systemctl`, которых у
непривилегированного приложения нет. Зелёная сборка ≠ рабочий код — фасад
обязан исключать этот слой явно, а не наследовать.

То есть ядро **кросс-компилируется под мобильные платформы без единой правки** —
это главный риск, и он снят. `client/` не тянет платформенных зависимостей:
всё, что специфично для ОС, изолировано в `client/leakguard/` через
`_windows.go` / `_linux.go` / `_darwin.go`.

⚠ **`docs/plans` пункт «Planned work #1» (встроить tun2socks) фактически
закрыт** — он уже in-process (`cmd/nixavpn-client/engine.go`). Список
запланированных работ в `CLAUDE.md` в этой части устарел.

## Что НЕ готово

### 1. gomobile-биндинга нет, а README утверждает обратное — P1

`README.md` (строки ~124 и ~245) описывает сборку в `.aar` и `.xcframework`
как существующую возможность. **Кода под это нет**: ни пакета-обёртки, ни
build-скрипта, ни упоминания gomobile где-либо кроме документации. Скриптов в
корне три: `build-client.sh`, `build-server.sh`, `deploy-round18.sh`.

Это классический случай «документ описывает механизм, которого нет» — тот же
класс дефекта, что разбирается в правиле 9 `CLAUDE.md` про докстринг
`startCreditSender`. Опасность конкретная: команда нативки прочтёт README и
заложит в план несуществующий артефакт.

### 2. Публичный API несовместим с gomobile напрямую — нужна обёртка

gomobile экспортирует только ограниченный набор типов: `string`, `bool`,
числовые, `[]byte`, `error`, интерфейсы и указатели на структуры своего
пакета. **Ни структуры по значению, ни слайсы (кроме `[]byte`), ни `context.Context`.**

Текущий API этому не удовлетворяет:

```go
func NewClient(config ClientConfig) *Client        // struct по значению — нельзя
func (c *Client) Connect(ctx context.Context) error // context.Context — нельзя
func (c *Client) ConnectTo(ctx context.Context, target string) error
```

`ClientConfig` содержит `[]byte`, `string`, `bool` — то есть поля сами по себе
пригодны, но передача структуры значением недопустима.

⚠ **«Объём небольшой и механический» — оценка НЕВЕРНА** (проверено чтением кода
2026-08-24). Она исходила из того, что обернуть надо `client.Client`. На деле
вся сборочная логика — SOCKS5-сервер, роутер, WS-пул, `DomainPool`, stats,
разбор `SHADOWLINK_*` — живёт в `cmd/nixavpn-client/engine_shadowlink.go`,
**915 строк в `package main`, который импортировать нельзя**. Голый
`client.Client` — это транспорт и стримы; обёртка только над ним даст мобильщикам
API, из которого сеть не поднимется.

⚠ И `ShadowLinkEngine` **не goroutine-safe**: мьютекса в структуре нет
(`engine_shadowlink.go:23-46`), поля `e.cl`/`e.stream`/`e.socks` пишутся из
`Connect` и из `streamReaderLoop` (`:762-765`) без синхронизации, `Close` читает
их без блокировки, `Connect` не идемпотентен. Фасад вызывают из UI-потока —
переносить это состояние как есть нельзя.

⚠ Два дефекта конфигурации, которые на мобильных перестают быть безобидными:
`ClientID` в CLI генерируется заново каждый запуск (`uuid.New()`,
`engine_shadowlink.go:84-85`), а `FPCacheDir` не задаётся **вообще** — то есть
fingerprint-профиль не переживает перезапуск. На мобильных система даёт
постоянный путь, и это надо чинить: иначе каждый холодный старт — новый профиль,
что работает против hard rule 2 (уникальность и есть сигнал).

Форма плоского фасада (сама по себе верна):

```go
package mobile

type Session struct{ c *client.Client; cancel context.CancelFunc }

func NewSession(serverAddr string, pubKey, clientID []byte, cacheDir string) *Session
func (s *Session) Start() error   // context создаётся внутри
func (s *Session) Stop() error
func (s *Session) Connected() bool
```

Это обёртка, а не переписывание: вся логика остаётся в `client/`.

### 3. iOS — блокер СНЯТ проверкой источников 2026-08-24, но риск переформулирован

Прежняя запись этого раздела гласила: «лимит памяти NetworkExtension на iOS —
15 МБ, gvisor в него не укладывается», со ссылкой на
`docs/whitecall-master-spec-review-opus-2026-06-05.md` и с оговоркой «нами не
перепроверялось». Перепроверено — **цифра неверна, потому что относится к
другому типу provider'а**.

| Provider | iOS ≤14 | iOS 15 | iOS 16–18 |
|---|---|---|---|
| **Packet Tunnel** (наш случай) | 15 MiB | **50 MiB** | **50 MiB** |
| App Proxy | 15 | 15 | 15 MiB |
| DNS Proxy | — | 15 | 15 MiB |

15 MiB — это `NEAppProxyProvider`/`NEDNSProxyProvider`. Для
`NEPacketTunnelProvider` с iOS 15 бюджет — **50 MiB**, то есть в 3.3 раза выше
заложенного. Источники: канонический тред Apple DTS (Quinn),
[forums/thread/73148](https://developer.apple.com/forums/thread/73148);
независимое подтверждение ядерным логом jetsam
(`memorystatus: singboxExtension exceeded mem limit: ActiveHard 50 MB (fatal)`,
[sing-box#3976](https://github.com/SagerNet/sing-box/issues/3976)); Tailscale со
стороны разработчика — «iOS 15 launched and quietly gave us 35MB more»
([tailscale.com/blog/go-linker](https://tailscale.com/blog/go-linker)).

Вывод меняется с «gvisor не влезает» на **«влезает в steady state, риск — срыв
на пиках»**.

⚠ **Три оговорки, которые обязаны ехать вместе с числом**, иначе оно снова
станет формулировкой сильнее данных:
1. Лимиты **официально не документированы**. Дословно Apple DTS: *«These limits
   have changed in the past and may well change in the future… You should not
   hard code knowledge about these limits into your code.»*
2. Есть **неразрешённый контрпример**: разработчик на iPhone 14 Pro Max /
   iOS 17.3.1 сообщает об убийстве расширения на 15 МБ вопреки заявленным 50
   ([forums/thread/747474](https://developer.apple.com/forums/thread/747474));
   инженер Apple ответил вопросом, тред закрыт не был. Причина не найдена —
   **не подтверждено**.
3. Лимит применяется **ко всему процессу** расширения, и на старых устройствах
   может быть ниже при той же версии ОС.

#### Что из этого следует для архитектуры

✅ **Замерено 2026-08-24, а не выведено из документации:** `client/` тянет
**0** пакетов gVisor, `tun2socks/v2/engine` — **41**. То есть память gVisor это
цена TUN-режима, **отделимая от ядра протокола**: SOCKS5-режим фасада можно
собрать вообще без gVisor.

⚠ **Структурная развилка, из-за которой нельзя копировать WireGuard.**
WireGuard дёшев по памяти не из-за оптимизаций, а потому что он **L3 и не
терминирует TCP** — TCP-сессии терминирует ядро iOS; ни gVisor, ни lwIP у него
нет, биндинг — cgo `c-archive`, не gomobile
([api-apple.go](https://github.com/WireGuard/wireguard-apple/blob/master/Sources/WireGuardKitGo/api-apple.go)).
ShadowLink TCP **терминирует** (SOCKS5 + tun2socks, сам gVisor-based), поэтому
мы структурно в лиге Tailscale/sing-box.

Варианты, теперь с оценкой:
- **Packet Tunnel + gVisor, зажатый по буферам** — эволюционный путь, ядро не
  переписывается. Так возит Tailscale (`wgengine/netstack`) в проде.
  ⚠ Риск не гипотетический: в sing-box#3976 профиль указывает в
  `gvisor/pkg/buffer.newChunk` (23.2 %) и `PullUp` (23.2 %), в ядре сотни
  `ctl_enqueuembuf failed: 55` (ENOBUFS). Их правки (урезание очередей, TCP-
  буферов, отключение autotuning) дали jetsam реже, **но регрессию — залипания
  трафика при внешне подключённом туннеле**. Это наш знакомый класс дефекта:
  правка ручки вместо механизма, метрика улучшилась, поведение сломалось (ср.
  `creditSenderInterval`). Мерить обязаны обе стороны.
  Числа gVisor: `DefaultBufferSize` = 212 KiB на endpoint,
  `DefaultMaxBufferSize` = **4 MiB** (8 % бюджета на одно соединение).
  Обязательное условие — netstack новее октября 2022
  ([buffer pooling](https://gvisor.dev/blog/2022/10/24/buffer-pooling/) убрал
  99 % аллокаций).
- **`NEAppProxyProvider`** — система отдаёт **уже терминированные потоки**
  (`NEAppProxyTCPFlow`/`UDPFlow`), userspace-стек не нужен вовсе: исчезает сам
  источник расхода, а не смягчается. Flow-модель ложится на ShadowLink ближе,
  чем IP-пакеты, — мы и так мультиплексируем стримы поверх WS-слотов. Цена:
  лимит **15 MiB** (Go runtime ~5 МБ → остаётся ~10). Psiphon так работал в
  проде больше года. Разумный план отхода.
- **lwIP через cgo** — отвергнут: меняет известный риск на менее изученный
  (cgo-память невидима для GOMEMLIMIT; история утечки в Go↔lwIP-биндинге,
  [go-tun2socks#157](https://github.com/eycorsican/go-tun2socks/issues/157);
  автор архивировал проект и отправляет iOS-разработчиков на Rust). Head-to-head
  бенчмарка lwIP vs gVisor в iOS-расширении **не публиковалось**.

#### Риск, специфичный именно для нас

Psiphon и Tailscale независимо указывают: пики памяти приходятся на
**(пере)подключение**, и лечится это снижением конкурентности (Tailscale урезал
одновременные DoH-запросы 1000 → 10,
[#2566](https://github.com/tailscale/tailscale/issues/2566); Psiphon — *«dial
back and stagger concurrent operations»*). У ShadowLink пул из 8 слотов с
ротацией каждые ~70–142 с — это **непрерывный поток переподключений, а не
однократный старт**, причём `staggerDelay` есть на старте и **отсутствует в
reconnect-пути** (`CLAUDE.md` п. 8). Это первое, что надо мерить на устройстве.

#### Две ловушки измерения

- `runtime.ReadMemStats` в расширении **может врать** — Psiphon сообщает о
  несогласованной статистике, похоже, репортилась память основного приложения.
  Правильный API — `os_proc_available_memory()` (iOS 13+).
- При jetsam **крэш-лог расширения система не пишет**, приложение не падает.
  «VPN внезапно отвалился» без артефактов — ожидаемая симптоматика, а не
  загадка.

#### Одна экономия работы

`FreeOSMemory` / `GODEBUG=madvdontneed=1` на iOS **не нужны**. Расхожий довод
«Go отдаёт память через `MADV_FREE`, RSS остаётся высоким, jetsam засчитывает»
на Darwin неверен: `src/runtime/mem_darwin.go` шлёт **`MADV_FREE_REUSABLE`**,
который *«propagates accounting information about the process to task_info»*.
Это ровно тот патч, что Outline держал в кастомном Go 1.12 и который ушёл в
апстрим в **Go 1.13**. Оценка Psiphon «FreeOSMemory с mixed success» относится к
эпохе до патча.
⚠ Построчная проверка ledger'а XNU (`vm_map.c`/`task.c`) не делалась —
утверждение опирается на код Go и его комментарии.

### 4. Windows — готово, но проверить стоит одно

Клиент собирается и отработал 8-часовой полевой прогон. Единственное:
`bin/nixavpn-client.exe` весит 50.29 МБ, GitHub предупреждает о превышении
рекомендованных 50 МБ (жёсткий лимит — 100 МБ). Каждая пересборка добавляет
в историю ~50 МБ. На работу не влияет, но репозиторий пухнет — стоит решить
про Git LFS или про то, чтобы не версионировать бинарь.

## Порядок работ, если начинать сейчас

1. **Привести README в соответствие** — убрать gomobile из списка готового,
   перенести в roadmap. Иначе план нативки будет построен на несуществующем.
2. **Написать пакет `mobile/`** — плоский фасад над `client.Client`. Малый
   объём, механическая работа, покрывается тестами обычным образом.
3. **Android первым** — путь чистый: `.aar` + `VpnService`, tun2socks уже
   встроен, кросс-компиляция подтверждена.
4. **iOS — только после решения по памяти extension.** Начинать разработку до
   выбора архитектуры нельзя: переделывать придётся целиком.

## Что от протокола НЕ требуется

Ось возраста (резы посредника при 80–88 с) — структурное свойство, общее для
всех платформ, и нативка его не наследует как дефект. Правка keepalive
подтверждена полем; следующий шаг по этой линии — адаптер per-AS, который
работает внутри `client/` и мобильных клиентов не касается. Подробности —
`docs/plans/2026-08-21-field-run-analysis.md` и правило 15 `CLAUDE.md`.
