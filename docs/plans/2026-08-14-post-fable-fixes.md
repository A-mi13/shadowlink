# Правки по итогам независимой проверки — 2026-08-14

Fable-агент перепроверил разбор от 2026-08-13 по первичным логам. Реконструкция
устояла бин в бин, но **вердикт держится на другом основании**, а по пути нашлись
две вещи крупнее исходного вопроса. Здесь — что сделано и что осталось замерить.

## Исходный вопрос закрыт: cap не трогать, потому что он no-op

Вопрос «срезать ли `SHADOWLINK_STAGGER_OFFSET_CAP` 15s → 10s» снят. Причина —
не цена, а инертность:

`slotStaggerOffset`: `base = idx*step`, кламп при `base > cap`. При `step=1s` и
16 ячейках максимум `idx=15` даёт ровно `15s` → **при `cap=15s` кламп не
срабатывает ни на одной ячейке**. `cap=10s` связал бы только `idx 11…15`, чья
занятость в поле 0.16 %:

```
cell: 0:87 1:84 2:83 3:84 4:82 5:80 6:75 7:31 8:16 9:2 10:3 11:1  (12..15: 0)
```

После квантования 5-секундным тиком корзину меняет только `idx=15` → **ноль
соединений за прогон**. Правка бессмысленна, а по hard rule 8 каждая тайминговая
правка оплачивается замером.

Мой прежний довод («ценой роста conn/час») **неверен по масштабу**: даже полное
схлопывание лестницы стоит +2.8 % (307.9 → 316.6 conn/ч), потому что ладдер
занимает 0…9 с при базе 70 с. P0 «policing по числу TLS» решается базой
(70 → 60 с даёт +17 %), а не капом. Зафиксировано правилом 10 в `CLAUDE.md`.

## Что сделано в коде

### 1. Фазовый замок свипа развязан (приоритет 1)

Замер по `nixavpn-DEBUG-20260813-153638`:

```
все 588 age-ротаций — в ОДНОЙ фазе сетки 5.000s
   σ фазы 0.0001s, дрейфа за 2 часа нет
92.2 % TCP-connect'ов — в одном односекундном окне этой фазы
```

Комментарий в `client/ws_pool.go` утверждал, что additive grid jitter размазывает
FFT-пик и «observer can no longer reject the irregular null hypothesis». Замер
**опроверг**: пик не размазан, он переехал с `1/step` на `1/rotationWatchdogTick`
и стал предельно узким. Причина: джиттер прибавляется к **порогу**, а порог
сравнивается с возрастом только на тике, поэтому подтиковая фаза не размазывается
вообще.

Побочное следствие того же квантования: при `step=1s` соседние offsets
неразличимы — в поле видны ровно два режима с разницей 5.0 с, а не лестница из 16
ступеней. Модель подтверждена на втором прогоне (base 75 → 79.7 / 84.7 / 89.6 с).

**Сделано:** новая ручка `SweepPhaseJitter` (env
`SHADOWLINK_SWEEP_PHASE_JITTER`), дефолт **4 с**, `-1s` выключает ровно.
Перешагнувший порог слот получает разовую отсрочку `uniform[0, jitter)` через уже
существующий `nextDrainAttemptNs` — новой ветки поведения нет. Однократность
держит флаг `phaseJitterApplied` на `*poolSlot`; без него отсрочка перевзводилась
бы каждый тик и слот не ротировался бы **никогда**.

Слагаемое вошло в `worstCaseTeardown()`, поле в логе переименовано
`sweep_tick` → **`sweep_budget`** (величина перестала быть чистым тиком; рядом
печатаются `sweep_tick` и `sweep_phase_jitter` порознь). Счётчик —
`sweep_phase_jitter_applied_total` + Prometheus.

⚠ **Ручка не бесплатна.** Плата — до +4 с возраста: при базе 70 с худшая ячейка
уходит с 74…79 с в 74…83 с, то есть внутрь полосы, где hazard 2.1 % на проход
против нуля ниже 80 с. Что дороже — периодический сигнал или экспозиция —
решается замером, поэтому дефолт включён, но выключатель выведен.

Тесты: `client/ws_pool_sweep_phase_test.go` (5 тестов).

### 2. Hazard считался неверно в обе стороны

**Занижение вдвое.** `HazardBand.Rate()` применяет actuarial-вес 1/2 к
цензурированным, предполагая, что они прожили полполосы (2.5 с). В нашей
конфигурации порог стоит **на кромке**: плановые умирают на 74–80 с, полоса
начинается с 80 с, проживают в ней ~0.2 с. Логируемые 3.37 % для 80–85 с против
**6.94 %** по экспозиции — занижение ровно там, где ищется порог. По памяти
проекта «занижение хуже завышения».

**Завышение ×2.06.** Ринг плановых (`DefaultCapacity=512`) переполнялся (1256
плановых), ринг резов нет (126). Числитель полный, знаменатель обрезан последними
512 → в PROBE логировалось `rate=0.0367` против `0.0178` по экспозиции. `CutShare`
про эту ловушку предупреждает, `Hazard` не предупреждал. И `reached=522` читается
как «дошло 522 соединения», а значит «осталось 522 записи в ринге».

**Сделано:** `HazardBand.ExposureMs` + `RateByExposure()` (1/с, несмещённая
форма: резы делятся на фактически прожитое в полосе время) и флаг
`RingSaturated`. Лог печатает `exposure_s`, `rate_exp`, `p_pass` (вероятность
реза при проходе полосы — та величина, что сравнивают с «hazard 2–6 %»),
`rate_act` (прежняя форма, для сравнимости со старыми логами) и
`ring_saturated`; при насыщении добавляются `cuts_lifetime` / `planned_lifetime`.

Тесты: `client/slotobs/planned_test.go` (4 новых).

### 3. `capacity floor` → рез: гейт выведен в env

Разбор всех четырёх резов прогона по контексту:

| рез | жизнь | что было перед |
|---|---|---|
| slot 8 | 86.6 с | `drain deferred (capacity floor)` на 79.6 с → рез +7.0 с |
| slot 6 | 84.4 с | то же на 79.8 с → рез +4.6 с |
| slot 5 | 82.7 с | то же на 79.7 с → рез +3.0 с |
| slot 10 | 83.7 с | отложек нет, `idx=10` доросла до порога |

**3 реза из 4 — на конце цепочки отложки.** RR ×21 (3/22 против 4/622),
гипергеометрический p ≈ 1.5e-4. n=3, поэтому указание, не доказательство — но
механизм статистики не требует: отложка на 79.7 с гарантирует ≥3 с экспозиции в
первой ненулевой полосе.

Причина: `floor = floor(8 × 0.75) = 6`, а сокращение порога 75 → 70 с сдвинуло
рабочую точку пула **ровно на** пол:

```
порог 70s: alive=5:15  alive=6:146  alive=7:75  alive=8:8   ← мода = ПОЛ
порог 75s: alive=6:26  alive=7:203  alive=8:95              ← пол с запасом 1
```

Гейт, написанный для катастрофы, взведён в штатном режиме и стреляет по обычной
ротации. Это уточняет вывод коммита `e058b74`: потерь по балансам нет (верно), но
«гейт делает ровно то, для чего написан» — неверно.

**Сделано:** доля выведена в `ReadyCapacityFloorFraction` (env
`SHADOWLINK_READY_CAPACITY_FLOOR_FRACTION`), **дефолт не изменён** — занижение
пола это риск clinch'а, ради которого гейт и заводился. Мусор и значения ≥ 1
клампятся (`normalizeFloorFraction`): доля 1.0 запретила бы ротацию навсегда.
Описание `CapacityFloorDeferredTotal` в `stats.go` переписано — прежнее
(«Catastrophic path») делало счётчик нечитаемым.

Тесты: `TestNormalizeFloorFraction`, `TestReadyCapacityFloor_HonoursConfiguredFraction`.

## Мои ошибки, исправленные в документации

1. **PROBE не был замером при 150 с.** Адаптер сжал порог за 43 минуты и держал
   ~67 с: `12:30 applied=1m36s → 12:31 1m31s → 1m16s → … → 13:00 1m7s`,
   `changes_total=11`. Замер при 150 с длился ~12 минут. Это самоподдерживающийся
   рэтчет: порог = `0.8 × p10 резов`, а p10 падает вслед за порогом; в разнос не
   идёт, потому что ограничен снизу настоящей стеной.
   → Мои перцентили **p10 84.4 / p50 93.7 / p90 123.8 с описывают смесь двух
   политик**, а не цензора: p90 набран первыми 43 минутами. Вывод про стену выжил
   только потому, что hazard по экспозиции к этому нечувствителен — фазы 1 и 2
   совпали (80–85: 1.74 % vs 1.80 %).
2. **Стена подтверждена независимо и сильнее:** 52 808 с экспозиции ниже 80 с,
   **0 резов**; при hazard'е полосы 80–85 ожидалось бы ~190. Дальше не стена, а
   ступень с плато 4–7e⁻³ 1/с до 105 с.
3. **`worstCaseTeardown()` в проде = 145.5 с**, не 142.5 (то была величина PROBE
   после адаптации базы до 67 с). В накладных `stagger` — 21 %, а
   `deferred 30 + tear 25` — 73 %; `drainRevertBackoff` в прод-прогоне не
   наблюдался ни разу. Сжимать бюджет через stagger/cap — неверная точка.
4. **`AGE_CUT_MIN_AGE` в проде 45 с**, не 60 (60 — только PROBE). При базе 70 с
   безвредно, но полосы hazard начинаются с 45 с и первые семь пусты.
5. Сравнение «166 слотов в полосе, резов ~4» с «3.9 % из замера» — **разные
   единицы**. Слоты входят в полосу 80–85 и выходят через 0.2 с; полная
   экспозиция полосы 208 с на 190 входов. 3 реза на 208 с = 14.4e⁻³ 1/с, в 3.4
   раза **выше** пулового. Знак моего аргумента не подтверждается: данные говорят
   не «в полосе резов почти нет», а «в полосу почти не заходят».

## Что замерить дальше

### A/B №1 — фазовый замок (сделано, нужен прогон)

Критерий: концентрация в модальном 1-секундном окне **ниже 40 %** (сейчас 92.2 %).

```bash
grep 'drain started' "$LOG" | grep 'reason=age' \
  | grep -o 'T[0-9][0-9]:[0-9][0-9]:[0-9.]*' | awk -F: '{printf "%.1f\n",($3+0)%5}' \
  | sort -n | uniq -c    # до правки: одно значение на 100% строк
```

Контроль цены: возрасты плановых ротаций не должны заползать за 85 с массово, и
`slot_cuts_1m` не должен вырасти против 1.96 реза/час.

Выключить для контрольного прогона: `SHADOWLINK_SWEEP_PHASE_JITTER=-1s`.

### A/B №2 — снять пул с пола storm-brake

`SHADOWLINK_READY_CAPACITY_FLOOR_FRACTION=0.5` (пол 6 → 4).

Критерий: `capacity_floor_deferred_total` → 0 **и** число резов, следующих за
отложкой той же ячейки в пределах 10 с. Нужно **≥3 прогона по 2 ч**, чтобы n
вышел из области n=3.

```bash
grep -c 'capacity floor' "$LOG"; grep -c 'slot reader error' "$LOG"
```

**Адаптер молчит.** `MinSamplesForInference=12` недостижим, пока порог работает
