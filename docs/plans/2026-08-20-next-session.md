### Что проверять в новом логе — три правки фазы + P0

```bash
LOG="$TEMP/nixavpn-DEBUG-<дата>.log"

# 1. ГЛАВНОЕ (P0): смерти по ТИШИНЕ. Разнос keepalive добавлял молчание, и
#    правка это лечила. Если появятся смерти с last_write_age_ms 9000-13000 —
#    значит проход всё ещё выводит слот за middleboxSilentCutFloor (10s).
grep 'slot reader error' "$LOG" | grep -o 'last_write_age_ms=[0-9]*' | sort -n | tail -10
#    ⚠ Такие смерти маскируются под резы посредника: isAgeCut метит любую
#    терминальную ошибку старше ageCutMinAge, тип не смотрит (правило 9).
#    Отличать по last_write_age_ms, а не по cause=age_cut.

# 2. фаза по логу (критерий R < 0.2; эталон 0.005-0.018)
grep 'slot reader started' "$LOG" | sed -n 's/^time=[0-9-]*T\([0-9:.]*\)+.*/\1/p' \
| awk -F: '{print $1*3600+$2*60+$3}' \
| awk '{t[n++]=$1} END{for(i=0;i<n;i++){a=2*3.14159265*(t[i]/0.5); sr+=cos(a); si+=sin(a)}; \
  printf "R=%.4f n=%d noise=%.4f\n", sqrt(sr*sr+si*si)/n, n, 1/sqrt(n)}'

# 3. downlink-throughput — контроль цены правки credit-sender (задержка credit
#    выросла с 9.1 до 16.3 мс на burst'ах; порог credit-stall 200 мс)
grep 'stats (delta)' "$LOG" | grep -o 'downlink_kb=[0-9]*' | cut -d= -f2 \
| sort -n | awk '{a[NR]=$1} END{print "p50="a[int(NR/2)], "p90="a[int(NR*0.9)], "max="a[NR]}'

# 4. здоровье пула (эталон: mean alive 8.28, gave_up 0, capacity_floor 0)
grep 'pool health' "$LOG" | grep -o ' alive=[0-9]*' | sort | uniq -c
grep -o 'healing_gave_up_total=[0-9]*' "$LOG" | tail -1   # обязан быть 0
grep -o 'capacity_floor_deferred_total=[0-9]*' "$LOG" | tail -1

# 5. inflight_cap_deferred_total — ТОЛЬКО с разбивкой по uptime (правило 14)
grep 'pool health' "$LOG" | sed -n 's/.*inflight_cap_deferred_total=\([0-9]*\).*uptime=\([0-9hms]*\).*/\1 \2/p' \
| awk '{if($1!=p){print "  до "$2": "$1; p=$1}}'

# 6. экспозиция, резы, sticky
grep -o 'age_exposure_over_threshold_ms=[0-9]*' "$LOG" | tail -1
grep -c 'slot reader error' "$LOG"
grep 'pool health' "$LOG" | grep -o 'sticky_active=[0-9]*' | sort | uniq -c
grep -c 'level=ERROR' "$LOG"   # ожидается 0
```

### P0 в моей же правке — найден ревью, исправлен (91a7ae2)

Первая версия разноса keepalive спала кумулятивно внутри цикла: проход стоил
Σ по слотам, замер дал max 2.8 с при 8 слотах и худшее молчание **12.4 с против
порога 10 с**. То есть возвращала Bug #9, от которого и защищает. Причём вторая

Исправлено структурно: смещения считаются заранее, сортируются, сон до
АБСОЛЮТНЫХ моментов от начала прохода → проход = максимум, не сумма. Замер:
400 мс при 1/4/8/16 слотах, фактический прогон 400.3 мс.

## Открытые вопросы

1. **P1 (не блокирующий): ack-гейт может дать сетку 75 мс** при квазирегулярном
   приходе данных с шагом, сопоставимым с окном (ревью: feed 37.5 мс → R = 0.9994
   @ 75 мс, CV 0.008). При пуассоновских приходах джиттер держится (CV 0.17-0.34).
   Достижимость в поле НЕ показана. Лечение — джиттер на момент отправки
   (отложенный ack), а не на порог окна; сторожу нужен слепой скан и второй feed.
2. **Второй AS/оператор** — блокирован нативкой. Адаптер порога ни разу не
   сработал в поле (`samples=5` при `required=12`), поэтому per-AS вывод не
   подтверждён, а 85-95 с — это «где риск заметен при данном n на ЭТОМ AS».
3. **`-race` только на Linux/CI** — на Windows нет gcc (правило 6). Выводы о
   гонках в keepalive сделаны чтением кода, не детектором.
4. **Нативка** — следующий этап после успешного 8-часового прогона (решение
   пользователя 2026-08-19).
