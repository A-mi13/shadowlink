Первый полевой прогон после правок утра 08-14 (`nixavpn-DEBUG-20260814-115514.log`,
2ч57м, `MAX_SLOT_AGE=70s`) плюс независимый анализ. Здесь — что замер показал и
что из этого исправлено.

## Что замер опроверг

### 1. Фаза: критерий был тавтологичен, пик переехал

Мой критерий «доля в модальном 1-секундном окне сетки 5 с» дал 100 % → 21.4 %,
то есть формально выполнен. Но он падает **автоматически** при любом тике меньше
секунды — он измеряет нашу ручку, а не наблюдаемость.

Правильная метрика — vector strength `R = |⟨e^{i2πt/T}⟩|` (тест Рэлея, не требует
опорной фазы — ровно то, что доступно пассивному наблюдателю):

| Период | База | Прогон 08-14 |
|---|---|---|
| 5 с | 1.0000 | **0.0096** (ниже шума) |
| 0.5 с | 1.0000 | **0.8657** |
| 0.5 с по `reader started` | 0.5980 | **0.5525** (не изменилось) |

Линия 0.2 Гц убита. Но пик **переехал на 2 Гц**: 76.2 % моментов дренажа — в
первых 50 мс полупериода. Причина не в величине периода, а в его **постоянстве**,
поэтому дальнейшее уменьшение тика воспроизвело бы тот же результат на следующем
масштабе.

**Исправлено:** `time.NewTicker` → `time.Timer` с перевзводом на
`tick + uniform[0, tick)`. Джиттер сэмплируется заново каждый взвод — один сэмпл
на сеанс дал бы решётку с другим шагом («single-sample reused», разобрано у
`slotStaggerOffset`). Средний период 750 мс, худший 1 с.

Бюджет: `sweep` = **`sweepWorstCase()` = 4 × tick** (два пробуждения по
`tick + jitter`). Формула ошибалась дважды за день: `1×tick` → `2×tick` → `4×tick`.
`worstCaseTeardown()` = 142.5 с.

### 2. Диагноз capacity floor был неверен — причина в утечке ячеек

Я утверждал: «порог 75 → 70 с сдвинул рабочую точку пула на пол». Хронология
опровергает:

```
15:42:12  первая ПОТЕРЯ ячейки (empty 8 → 9)
15:44:32  первая отложка гейта, все 22 при ready=5 floor=6
до 15:42:12 пул шёл на 8 живых, гейт не срабатывал НИ РАЗУ
```

`ready=5` при `poolSize=8` достижимо только после потери двух ячеек.

**Механизм утечки:**

```
placeholder freed slot=0      ← connectReserveSlot не смог поднять резерв
reconnecting slot 0 backoff=7.6s
drain slot 1 → replacement_slot=0   ← дренаж забрал ту же ячейку
reconnect short-circuited            ← recycle guard: голый return
→ ячейка потеряна НАВСЕГДА
```

Периодического healer'а ёмкости в пуле **нет**: каждая цепочка `reconnectLoop`
одноразова, единственный вызов на старте — начальный connect. Итог в поле:
`empty` 8→9→10→11, `mean alive` 7.21→5.80 за 2 ч.

Настоящая цепочка: **утечка → alive до пола → отложка гейта → +возраст → рез.**
Три реза из четырёх сидят на её конце. Гейт — предпоследнее звено, не первое.

**Исправлено:** guard по-прежнему отказывается от ЯЧЕЙКИ (чужую перезаписывать
нельзя), но восполняет ЁМКОСТЬ на свободной — `claimFreeCellForHealing()`.
Лечение **условное**: только при реальной недостаче живых слотов, потому что
лишнее TLS-соединение к origin — это P0. Предел `maxHealingRetargets=3` против
бесконечной погони за ячейками. Счётчики `healing_retargets_total` /
`healing_gave_up_total` — без них лечение неотличимо от исходной утечки.

⚠ **A/B по доле пола обесценен**: критерий `capacity_floor_deferred_total → 0`
выполняется сам, как только пул перестаёт терять ячейки (в этом прогоне уже 0 при
неизменной доле 0.75). Понижать долю нельзя — **замаскирует** остаточную утечку и
приблизит clinch. Осмысленный критерий теперь: число отложек при `ready < floor`
на прогонах, где `empty > 8`.

### 3. Бюджет и hazard были непроверяемы замером

`worst_case_teardown` и слагаемые жили только в строке `slot death inference`, а
та выходит при `samples >= 12`. Резов ноль → `samples=0` → строка молчала все 3
часа, и правка бюджета оказалась неподтверждаемой. Одновременно все
`rate_exp`/`p_pass` = 0.

Тот же контур, что уже описан для адаптера: **чем лучше работает порог, тем
меньше видно и порог, и бюджет, и hazard.**

**Исправлено:** бюджет печатается и в ветке нехватки выборки. Он считается из
конфигурации и от выборки не зависит — прятать его за гейтом наблюдений было
ошибкой категории. `margin_to_age_min` там помечен `n/a`: он требует
`age_min_clean` из выборки, и ноль читался бы как дефицит 142.5 с.

## Что подтвердилось как работающее

- `ring_saturated=false` при 1148 плановых — `PlannedCapacity=4096` держит.
  ⚠ При 372 ротациях/час 4096 наберётся за ~11 ч: на суточной сессии насыщение
  вернётся, и тогда доли снова смещаются.
- `exposure_s` сходится с независимой реконструкцией (band 70–75: 548 полных
  проходов × 5 с + 516 цензурированных = 4122.5 с).
- `ready_capacity`/`floor`/`fraction` печатаются в 354 снимках.
- `decrypt_fails=0`, `meltdowns_1m=0`, 0 ERROR, 14 WARN — все известные.

## Что осталось открытым

1. **Фаза после Timer'а не замерена.** Критерий: `R < 0.2` на периоде тика по
   `reader started` (сейчас 0.5525).
   ```bash
   grep 'slot reader started' "$LOG" | grep -o 'T[0-9][0-9]:[0-9][0-9]:[0-9.]*' | sed 's/^T//' \
   | awk -F: '{print $1*3600+$2*60+$3}' \
   | awk '{t[n++]=$1} END{for(i=0;i<n;i++){a=2*3.14159265*(t[i]/0.5); sr+=cos(a); si+=sin(a)}; \
     printf "R=%.4f n=%d noise=%.4f\n", sqrt(sr*sr+si*si)/n, n, 1/sqrt(n)}'
   ```
2. **Утечка не встретится сама.** В прогоне 08-14 было 3 отказа connect против 7 в
   базе, и все реконнекты успели. Отсутствие утечки там — вероятно удача сети, а не
   правка. Проверять `healing_retargets_total > 0` как доказательство работы.
3. **Sticky — новый главный источник хвоста**: 6 из 8 соединений >85 с — sticky,
   до 102.5 с. Замерить `stickyMaxDrainAge` против окна реза.
4. **Отказы connect как отдельный сигнал**: `ws upgrade: flowctl ack read` — RST на
   этапе апгрейда, до всякого возраста, в `slotobs` не попадает вовсе. 3.4/ч в базе,
   1.0/ч в новом. Если это посредник, у него есть второй механизм, который мы не
   измеряем.
5. **Адаптер по-прежнему слеп** (`samples=0 required=12`) — при нуле резов
   принципиально. Развязка через hazard со знаменателем из плановых.
6. **Момент ЗАКРЫТИЯ соединения остался на жёсткой сетке** (ревью 08-14).
   Правка `Timer` развязала только момент нового соединения: `startDrain` зовётся
   из свипа и сразу спавнит `connectReserveSlot`, поэтому `reader started` едет на
   джиттерованном расписании. А `tearDown` делает `drainWatchdog` по своему
   `time.NewTicker(drainPollInterval = 500 мс)` (`ws_pool_drain.go:805`) — сетка
   2 Гц по close жива. Замер `R = 0.8657` брался «по моменту дренажа», то есть как
   раз по ней, и от правки watchdog упасть **не обязан**. Замерять R раздельно:
   по `reader started` (должен упасть) и по моментам close (не должен).
   Правка `drainPollInterval` — отдельная работа, там тик ещё и гейтит
   `stickyRecheckInterval` (обязан быть ≥ drainPollInterval, спец L3).
7. **Прочие источники периодичности на wire, не тронутые.** Найдены тем же
   ревью, каждый требует своего решения:
   - `proxy/socks5/tcp.go:124` и `proxy/socks5/udp.go:384` — poll-циклы с
     **жёсткими 20 мс** и реальной отправкой байтов (`PollStreams`). Грубейшая
     решётка в проекте, 50 Гц, две копии одного паттерна;
   - `client/ws_pool.go` `Connect` fan-out — `idx * staggerDelay` без джиттера:
     cold start даёт идеально равномерную лестницу SYN;
   - `client/connmanager.go:417` — `AfterFunc(2 с)` после каждой ротации:
     устойчивая пара (new TLS, +2.000 с close), сильный корреляционный признак;
   - `client/ws_ready_pool.go:529` — backoff без джиттера, плато ровно 10 с;
   - `client/ws_pool.go` keepalive — джиттер по времени есть, но залп идёт на
     ВСЕ слоты одновременно (кросс-слотовая корреляция, временным джиттером не
     лечится).

## Состояние

`go build`, `go vet` — чисто. `go test ./client/...` — зелено (Windows, без
`-race`, hard rule 6). Прод-настройки `.bat` не менялись.

# Прогон 161915 (4 ч) — результаты и что закрыто

Замер после коммитов `a0dfe86` и `f2d577a`. Все правки подтверждены; два прогноза
этого документа оказались НЕВЕРНЫ в свою пользу.

## Фаза развязана ЦЕЛИКОМ — прогноз «наполовину» опровергнут

| Событие @ 0.5 с | база (5 с) | 500 мс без джиттера | **Timer+джиттер** |
|---|---|---|---|
| `reader started` | 0.5892 | 0.6023 | **0.0330** |
| `drain started` | 0.9541 | 0.8900 | **0.0464** |
| close (`natural finish`) | 0.9655 | 0.8933 | **0.0447** |

Шум `1/√n` = 0.025. Слепой скан 0.05–6.0 с шагом 5 мс: max R = 0.063.

**Механизм — якорь.** Сетка дренажа жива на 100 %:
`R((close − drain_start) mod 500мс) = 1.0000`, 1575/1575 в одном 50-мс бине. Но её
фаза наследуется от `startDrain`, а тот приходит из джиттерованного свипа.

→ **Правка `drainPollInterval` НЕ нужна**, пункт снят. Это зависимость, а не
свобода: возврат свипа к `time.NewTicker` немедленно проявит решётку 500 мс в
моментах close без правок в коде дренажа (ровно это и было в прогоне 115514).

`healing_retargets_total=2`, `healing_gave_up_total=0`, `short-circuited=0`
(в базе 2 — те и теряли ячейки). 8 поводов (`reserve connect failed`), 2 дошли до
конфликта с дренажем, оба вылечены.

| | Q1 | Q2 | Q3 | Q4 | max empty |
|---|---|---|---|---|---|
| База | 6.97 | 6.49 | 5.92 | **5.87** | **11** |
| Новый | 7.92 | 7.97 | 7.93 | **7.96** | 9 |

База деградировала монотонно (`alive<7` в 161 из 244 снимков), новый — плоско
7.95 за 4 ч, `alive<7` в **1 снимке из 481**.

## Sticky — единственное, что осталось

77 % опасной экспозиции (196.8 из 254 с), 12 из 17 соединений >85 с.
Все 50 teardown'ов — `sticky_outcome=age_backstop` и `drain_duration=25s` РОВНО,
то есть каждый упёрся в `stickyMaxDrainAge`.

Механизм: дренаж по `byte_budget` (38 из 50) стартует в любом возрасте — p50 34.2,
p90 74.2, max 77.6 с — и sticky добавляет +25 с. Потолок = старт + 25 с
(наблюдаемый max 102.6 сходится с 77.6 + 25).

**Вред не наступил**: 0 резов за 4 ч. Константу не трогали (hard rule 8). Вместо неё:
- `slot_age` — во ВСЕХ ветках teardown (не только sticky): `drain_duration` в ветке
  `age_backstop` константа и о риске молчит;
- `age_exposure_over_threshold_ms` — накопленный перебег за порогом, в мс (не в числе
  событий: 1 с и 20 с перебега — разный риск), по всем путям терминации. Порог 82 с,
  потому что плановые ротации массово идут через 80.2 с.

⚠ **Ревизия 2026-08-14 (независимая перепроверка лога, n=1575).** Два утверждения
выше были сильнее данных:
1. **«Sticky — почти единственный источник»** — неверно как «единственный». При
   пороге 82 с sticky даёт 196.8 из 254.0 с (77 %), а **natural finish — 57.3 с
   (23 %)**; из 17 соединений старше 85 с natural дал 5 (max 95.0 с). Доля не
   константа: при пороге 80 с sticky — уже 66 % (222.8 из 339.7 с). Первая версия
   счётчика накапливала только в `emitStickyTeardownLog` и эти 23 % не видела —
   накопление перенесено на общий путь `tearDown` (`accrueAgeExposure`).
2. **«При 49.2 с/ч ожидается ~1 рез»** — арифметика неверна, и вывод
   противоположный. 49.2 с/ч — это перебег за **85 с**; за 82 с он равен
   **63.4 с/ч**. Произведение 63.4 × 4.01 × 14.4e⁻³ = **3.7 реза**, а не 1 (даже по
   49.2 с/ч выходит 2.8). При наблюдённых 0 это значит, что модель замером
   **отвергается**, а не что «запас есть»: либо `rate_exp` полосы 80–85 с
   неприменим выше неё, либо он завышен (получен по 3 резам на 208 с). Подмена
   единиц — тот же класс ошибки, что разобран в
   `2026-08-14-post-fable-fixes.md` §2. Счётчик — индикатор ТРЕНДА, не прогноз.

## Осталось открытым

1. **Sticky-константу решать замером** — нужен A/B с одинаковым профилем трафика:
   рост 3.0/ч → 12.5/ч объясняется нагрузкой лишь частично (`sticky/ГБ` 6.1 → 16.4).
2. **20-мс poll-циклы в SOCKS5** (`tcp.go:124`, `udp.go:384`) — 50 Гц с реальной
   отправкой байтов, грубейшая решётка. Горячий путь, нужно решение по архитектуре.
3. **Медиана `close − start` = 0.500 с ровно** — пара «новое TLS → close через
   полсекунды» коррелирована по интервалу. Шаблон, а не периодичность.
4. **Прогон ≥11 ч** — увидеть `ring_saturated=true` и поведение доль при насыщении.
5. **Hazard слеп при нуле резов** (`rate_exp=0` во всех полосах) — развязка через
   знаменатель из плановых ротаций, работа не сделана.
6. ⚠ **`R` считается по меткам лога, не по SYN/FIN на проводе.** Контрдовод: в
   старых логах тем же методом R=0.89–0.97, то есть тракт решётку пропускает, когда
   она есть. Но линия тоньше ~10 мс этим методом не видна.
