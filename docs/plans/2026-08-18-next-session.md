```bash
LOG="$TEMP/nixavpn-DEBUG-<дата>.log"

grep -o 'age_exposure_over_threshold_ms=[0-9]*' "$LOG" | tail -1

# делить на часы uptime; ТРЕНД, не прогноз (см. ниже про rate_exp)

grep 'pool health' "$LOG" | grep -o 'empty=[0-9]*' | sort | uniq -c  # НЕ должен расти

# 3. фаза (R < 0.2 — критерий; в прогоне 161915 было 0.033-0.046)
grep 'slot reader started' "$LOG" | grep -o 'T[0-9][0-9]:[0-9][0-9]:[0-9.]*' | sed 's/^T//' \
| awk -F: '{print $1*3600+$2*60+$3}' \
| awk '{t[n++]=$1} END{for(i=0;i<n;i++){a=2*3.14159265*(t[i]/0.5); sr+=cos(a); si+=sin(a)}; \
  printf "R=%.4f n=%d noise=%.4f\n", sqrt(sr*sr+si*si)/n, n, 1/sqrt(n)}'

# 4. sticky: читать slot_age, НЕ drain_duration (тот константа 25s)
grep 'sticky backstop teardown' "$LOG" | grep -o 'slot_age=[0-9a-z.]*' | sort | tail -5

# 5. здоровье
grep -o 'worst_case_teardown=[^ ]*' "$LOG" | tail -1   # ожидается 2m22.5s
grep 'slot death hazard' "$LOG" | tail -1              # ring_saturated, rate_exp
grep -c 'level=ERROR' "$LOG"                            # ожидается 0
```

выбрасывает код. Это касается ВСЕХ метрик, не только новых. Смотреть только логи.

## Открытые вопросы — с чего начинать

1. **Sticky-константа `stickyMaxDrainAge=25s`.** Sticky даёт 77 % перебега за 82 с
   (196.8 из 254.0 с), 12 из 17 соединений >85 с, max 102.6 с. Механизм:
   `byte_budget`-дренаж стартует в любом возрасте (p50 34.2 / max 77.6 с), sticky
   добавляет +25 с → потолок = старт + 25 с. Константу не трогали (hard rule 8).
   Нужен **A/B с одинаковым профилем трафика**: рост 3.0/ч → 12.5/ч объясняется
   нагрузкой лишь частично (`sticky/ГБ` 6.1 → 16.4).
2. **Число резов из экспозиции НЕ выводится** умножением на `rate_exp` — я так
   ошибся дважды за день. Нужен hazard со знаменателем из плановых ротаций в тех же
   полосах. Пока счётчик — только тренд.
3. **20-мс poll-циклы в SOCKS5** (`proxy/socks5/tcp.go:124`, `udp.go:384`) —
   50 Гц с реальной отправкой байтов, грубейшая решётка в проекте. Горячий путь,
   нужно решение по архитектуре, не правка на глаз.
4. **Медиана `close − start` = 0.500 с ровно** — пара «новое TLS → close через
   полсекунды» коррелирована по **интервалу**. Шаблон, не периодичность.
5. **Прогон ≥11 ч** — увидеть `ring_saturated=true` (`PlannedCapacity=4096` при
   ~370 ротациях/час) и поведение долей при насыщении.
6. **Hazard слеп при нуле резов** — `rate_exp=0` во всех полосах. Развязка через
   знаменатель из плановых; работа не сделана.

## Методологические уроки дня (не повторять)

- **Критерий, который падает автоматически, ничего не измеряет.** «Доля в модальном
  окне сетки 5 с» падает при любом тике меньше секунды — измеряет ручку, а не
  наблюдаемость. Правильно — vector strength `R` на периоде тика.
- **Джиттер к ПОРОГУ периодической проверки не размазывает фазу** — только к
  моменту ДЕЙСТВИЯ. И даже это не помогает, если действие читает отсрочку тем же
  тикером: отсрочка короче тика переносит событие ровно на следующий тик.
- **Фаза лечится непостоянством периода, а не его величиной.** Уменьшение тика
  переносит пик на новую частоту.
- **Счётчик надо ставить на общий путь, а не в ветку**, иначе имя обещает больше,
  чем величина считает (видел 77 % вместо 100 %).
- **Порог в имени поля становится ложью** при первой смене константы.
- **Тест, дублирующий формулу, проверяет свою копию**, а не код. И поведенческий
  тест на функцию остаётся зелёным, если цикл перестанет её вызывать — нужен сторож
  на исходник.
- **Ноль событий ≠ подтверждение**: при 0 резов и 3.7 ожидаемых модель
  **отвергается**, а не «запас есть».
- **Проверять бинарь штампом `vcs.revision`/`modified`** — дважды за день собирал
  до коммита и получал `modified=true`.
