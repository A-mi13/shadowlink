## 1. Три места, где план 08-21 расходился с кодом

Зафиксировано, чтобы оценка не воспроизвелась.

1. **«Объём небольшой и механический» — неверно.** Оценка исходила из того, что
   обернуть надо `client.Client`. Но `client.Client` — это транспорт и стримы;
   SOCKS5-сервер, роутер, WS-пул, `DomainPool`, stats и разбор `SHADOWLINK_*`
   живут в `cmd/nixavpn-client/engine_shadowlink.go`, **915 строк в
   `package main`**. Обёртка только над `client.Client` дала бы API, из которого
   сеть не поднимается.
2. **`ShadowLinkEngine` не goroutine-safe.** Мьютекса в структуре нет
   (`engine_shadowlink.go:23-46`), `e.cl`/`e.stream`/`e.socks` пишутся из
   `Connect` и из `streamReaderLoop` (`:762-765`) без синхронизации, `Close`
   читает их без блокировки, `Connect` не идемпотентен.
3. **`leakguard` компилируется под мобильные, но работать там не будет** — под
   Android это `guard_linux.go` с `iptables`/`systemctl`. Зелёная сборка ≠
   рабочий код.

## 2. Граница API: SOCKS5, не TUN fd

Выбор сделан по трём проверенным причинам:

1. **SOCKS5-режим не тянет gVisor вообще** (0 против 41 пакета) — а gVisor и
   есть главный потребитель памяти в TUN-режиме. Один фасад годится обеим
   мобильным платформам и оставляет открытым путь на `NEAppProxyProvider`, где
   userspace-стек не нужен в принципе.
   ⚠ **Первая редакция приписывала «Packet Tunnel, 50 MiB» Android'у — это
   фактическая ошибка.** У Android нет NetworkExtension и нет лимита в MiB:
   `VpnService` работает в обычном процессе приложения с обычной кучей (сотни
   МБ). Лимиты 50 MiB (Packet Tunnel) / 15 MiB (App Proxy) — **только iOS**,
   см. §4.8.9.
   ⚠ **И gVisor — не главный вклад в размер `.aar`**: см. §3, `tun2socks/v2/proxy`
   тянет **211 пакетов** ради одного типа в сигнатуре. Риск размера в первой
   редакции был назван не тем механизмом.
2. **Минимальная поверхность** — меньше того, что придётся ломать после того,
   как мобильные команды завяжутся на API.
3. **TUN на Android не теряется**: нативка получает порт SOCKS5 и скармливает
   его tun2socks/VpnService. Приём fd добавляется позже отдельным методом, не
   ломая существующий.

Это разделение слоёв, а не урезанный режим: Go отдаёт прокси, платформа решает,
как заворачивать трафик.

## 4. API фасада

```go
package mobile

type Config struct {
    ServerAddr  string // "1.2.3.4:443"
    PubKeyHex   string // hex X25519, как в sl:// ссылке
    ClientIDHex string // ПЕРСИСТЕНТНЫЙ, задаёт платформа
    SNI         string
    CDN         string
    UseTLS      bool
    WSPoolSize  int32  // 0 = дефолт. int32, НЕ int — см. ниже
    StateDir    string // системный путь: fp-state, кеши
}
func NewConfig() *Config
func (c *Config) SetRouting(spec string) error   // сложное — через JSON
func (c *Config) AddBypass(pattern string)       // простые случаи без парсера

type Session struct{ /* mu, state atomic.Int32, engine, cancel */ }
func NewSession(cfg *Config) (*Session, error)
func (s *Session) Start() error       // НЕ блокирует до готовности пула (см. §4.8.6)
func (s *Session) Stop() error        // идемпотентен; УНИЧТОЖАЕТ engine
func (s *Session) State() string      // idle|connecting|connected|degraded|failed
func (s *Session) SocksPort() int32   // 0 до Start(); фактический порт листенера
func (s *Session) SocksUser() string  // креды генерируются внутри — см. ниже
func (s *Session) SocksPass() string
func (s *Session) NetworkChanged()    // нужен ВСЕМ платформам — см. §4.8.1

type Logger interface{ Log(level, msg string) }
func SetLogger(l Logger)              // ГЛОБАЛЕН по процессу (slog.SetDefault)
func SetLogLevel(level string)        // глобален; не поле Config — см. ниже

type EventHandler interface{ OnStateChange(state string); OnError(msg string) }
func (s *Session) SetEventHandler(h EventHandler)
```

**Ограничения gomobile, которые этим обходятся:** нельзя структуры по значению
(→ `*Config` + конструктор), нельзя слайсы кроме `[]byte` (→ JSON-строка для
routing/backup-серверов), нельзя `context.Context` (→ создаётся внутри `Start`).
Интерфейсы gomobile поддерживает — на них построены логгер и события.

✅ **Совместимость проверена ревью 2026-08-24 по каждому объявлению — нарушений
правил gobind нет.** Уточнения, которые из проверки следуют:

- **`int` в Go на Android 64-битный → gobind маппит его в Java `long`**, а не
  `int`. Поэтому размерные поля объявлены `int32` (`WSPoolSize`, `SocksPort`),
  иначе Kotlin получит неожиданный `setWSPoolSize(long)`.
- **Поля структуры gobind отдаёт как геттеры/сеттеры автоматически**
  (`cfg.setServerAddr(...)` в Java, свойство `cfg.serverAddr` в Swift) — писать
  их руками не нужно.
- **`NewConfig()`/`NewSession()` становятся конструкторами класса** в Java
  (`new Config()`, `new Session(cfg)` с `throws Exception`), а не статическими
  методами. Коллизий имён и Java-ключевых слов среди полей нет.
- Параметр `SetRouting` назван `spec`, а не `json`: имя `json` затенило бы пакет
  `encoding/json` внутри тела метода.
- ⚠ **`LogLevel` убран из `Config`** и заменён пакетным `SetLogLevel`: `slog` —
  процесс-глобал, поэтому per-session уровень невыразим, и обещать его в полях
  сессии значило бы описывать механизм, которого нет. По той же причине
  `SetLogger` документируется как глобальный, а `SetLogger(nil)` обязателен на
  `Stop()` — иначе глобальная JNI-ссылка удержит Java-объект (классическая утечка
  Activity/Context на Android).
- Уровни принимаются полным набором `parseLogLevel` (`logging.go:22-37`):
  `info|quiet|warn|error|debug|trace`; неизвестное значение → `info`, а не ошибка.
  ⚠ `trace` нужен для полевой диагностики, и первая редакция спеки его теряла.

### 4.1. Контракт колбэков: НЕ звать Java синхронно из горутин ядра

⚠ Первая редакция уместила интерфейсы в строку «gomobile их поддерживает». Это
формулировка сильнее данных: типы валидны, но контракт исполнения не разобран, а
он опасен.

- **Из какой горутины.** `SetLogger` → `slog.SetDefault` означает вызов `Log()`
  из **любой** горутины ядра: ридеров всех 8 слотов, `streamReaderLoop`,
  `StartStatsLogger` (`engine_shadowlink.go:216`). Не из UI-потока — реализация
  на платформе обязана сама делать `runOnUiThread`/`Handler.post`, иначе
  `CalledFromWrongThreadException` при касании View.
- ⚠ **Исключение в колбэке роняет процесс.** gobind не ловит Java-исключения:
  необработанный `RuntimeException` в `Log()` даёт JNI abort, а не ошибку в Go.
- ⚠ **Блокировка в колбэке останавливает горутину ядра.** Если `Log()` пришёл из
  ридера слота, блокировка останавливает чтение WS → тишина на слоте → рез
  посредником. Порог тишины — `middleboxSilentCutFloor` = 10 с (hard rule 15),
  то есть это не теоретический риск.
- **Стоимость:** JNI-переход на каждую строку. При `debug` ядро печатает тысячи
  строк (полевой прогон: 5491 строка keepalive за 8 ч + stats каждые 5 с).
  Фильтр по уровню обязан стоять **до** JNI — в `slog.HandlerOptions{Level:}`, а
  не внутри Java.

**Решение:** между ядром и JNI — буферизованный канал и одна диспетчер-горутина
с **неблокирующей** отправкой (`select/default`, дроп при переполнении). Тогда
медленный или упавший колбэк не задевает ридеры. То же для `EventHandler`.

### 4.2. Аутентификация SOCKS5 — ОТСУТСТВУЮЩАЯ ФУНКЦИЯ, а не принятый риск

⚠ Первая редакция записала открытый порт как «принятую цену границы API §2».
**Это неверно: аутентификация от границы API не зависит.** На десктопе защита
двойная и уже реализована:
- случайные креды на каждый запуск — `generateProxyCredentials()`
  (`main.go:120-124`, `:739`): пользователь `nix`, пароль 16 hex-символов;
- случайный порт 10000–60000 — `randomSOCKSAddr()` (`main.go:872-880`).

В первой редакции `mobile.Config` не имел ни `ProxyUser`, ни `ProxyPass`, то
есть фасад отдавал бы **неаутентифицированный SOCKS5 на публикуемом порту** —
строго слабее десктопа, притом что на Android порт доступен **любому
приложению** устройства.

**Решение:** креды генерируются внутри `NewSession` тем же механизмом и
отдаются нативке через `SocksUser()`/`SocksPass()` — их не задаёт платформа
(чтобы нельзя было выставить слабые) и они не переживают перезапуск.
Нативка передаёт их в свой tun2socks/прокси-клиент.

### 4.2a. `SocksPort`: bind на `:0`, а не фиксированный порт

⚠ Первая редакция объявляла метод, не сказав, откуда берётся значение — а взять
его сейчас неоткуда: `SOCKSAddr()` (`engine_shadowlink.go:813`) возвращает
**строку из конфига** (`e.socksAddr`), не адрес листенера, и поля SOCKS-адреса в
`mobile.Config` нет вовсе.

Фиксированный порт на мобильном брать **нельзя**: 1080 может быть занят другим
VPN-приложением, и `net.Listen` (`proxy/socks5/server.go:104`) упадёт. Механизм
уже есть — `Server.ListenAddr()` (`server.go:154-162`, под мьютексом, с
комментарием «useful when binding to :0»), но `engine` использует его лишь как
проверку живости (`engine_shadowlink.go:681`).

Решение: фасад биндит `127.0.0.1:0`; `SocksPort()` читает фактический порт из
`ListenAddr()`; до `Start()` возвращает `0`. Требуется прокинуть фактический
адрес наружу из `engine/` — **мелкая правка, которой не было в §6**.

⚠ **Принятая цена выбранной границы API, которую надо назвать явно:** открытый
`127.0.0.1:PORT` на Android доступен **любому приложению на устройстве** без
аутентификации SOCKS5. Это следствие решения §2, а не упущение; фиксируется как
принятый риск.

### 4.3. Два дефекта конфигурации, которые фасад чинит

- **`ClientIDHex` задаёт платформа.** В CLI `ClientID` — `uuid.New()` на каждый
  запуск (`engine_shadowlink.go:84-85`), то есть идентичность не переживает
  перезапуск. ⚠ **Не реализовывать до правки handshake — см. §4.3.**
- **`StateDir` обязателен.** В CLI `FPCacheDir` не задаётся **вообще**, поэтому
  fingerprint-профиль не персистится и выбирается заново каждый старт. На
  мобильных это работало бы против hard rule 2 (уникальность и есть сигнал).

### 4.4. Зависимость от аудита ключей: ClientID нельзя делать предсказуемым «просто так»

Аудит криптографии (2026-08-24) снял главный вопрос — **ключи у клиентов не
общие**: свежая эфемерная X25519-пара с обеих сторон на каждый handshake
(`core/handshake.go:45` клиент, `:90` сервер), статический ключ сервера в выводе
сессионных ключей **не участвует**; свой ключ у каждого из 8 слотов и у каждой
ротации. Nonce-дисциплина AES-GCM корректна (счётчик, связанный с эпохой ключа;
`InitSendEpoch` идемпотентен и не сбрасывает счётчик, `core/session.go:238-240`).
P0-находок нет.

Но найдено следующее, и оно прямо касается поля `ClientIDHex`:

1. **Аутентификации клиентов в проде фактически нет.** При пустом
   `authorized_clients` сервер в open mode пропускает любой ClientID
   (`server/ratelimit.go:115-117`). Любой обладатель `sl://`-ссылки пользуется
   сервером. Это риск абуза/затрат/репутации IP, не конфиденциальности.
2. **Whitelist невключаем при текущем клиенте:** он шлёт случайный UUID каждый
   запуск и в список попасть не может. Механизм с обеих сторон построен
   (проверка на handshake `server/handler.go:717`, квота устройств
   `AdmitSession`, management API) и разорван ровно в одном месте — маппинге
   конфига: `?id=` из ссылки парсится (`client/slurl.go:88`), но в
   `ShadowLinkConfig` такого поля нет (`cmd/nixavpn-client/config.go:149-161`).
3. ⚠ **Переход на предсказуемые ID (`user_<id>`) ОСЛАБЛЯЕТ аутентификацию
   сервера.** Подписи в handshake нет; MITM не может завершить обмен только
   потому, что не знает ClientID, входящий в HKDF-info (122 бита случайного
   UUID). С аккаунт-ID эта защита исчезает.

**Следствие для порядка работ:** `ClientIDHex` как поле фасада — верно, но
включать персистентный аккаунт-ID **до** правки handshake нельзя: мы обменяем
риск абуза на риск MITM. Правка известна и точечна — подмешать в IKM ещё и
`ECDH(client_eph, server_static)`, тогда аутентификация сервера перестаёт
зависеть от секретности ID; делать с бампом `protoVersion` (механизм
downgrade-защиты уже есть, `core/crypto.go:111-137`).

Это **отдельная работа вне пакета `mobile/`**. Фасад принимает `ClientIDHex` как
непрозрачную строку; чем её заполнять (случайным UUID или аккаунт-ID) — решается
после правки handshake. До неё платформа передаёт персистентный **случайный**
UUID: это чинит «новая идентичность каждый запуск», не трогая крипто-свойства.

### 4.6. Глобальное состояние между сессиями — проверено

Мобильный процесс переживает много подключений подряд (в отличие от CLI, где
процесс живёт одну сессию), поэтому процесс-глобалы `client/` проверены отдельно:

- ✅ `globalPoolForStatsPtr` (`client/stats.go:741`) **корректно очищается**:
  `SetGlobalPoolForStats(nil)` на закрытии пула (`client/ws_pool.go:5431`).
  Указателя на мёртвый пул между сессиями не остаётся.
- ✅ `StartStatsLogger` (`client/stats.go:1198`) привязан к контексту и выходит
  по `ctx.Done()` — висячих горутин между сессиями нет.
- ⚠ `var Stats statsRegistry` (`client/stats.go:736`) — **метода сброса нет**
  (проверено). Счётчики кумулятивны на весь процесс. Добавлять `Reset()` не
  предлагается — глобал разделяется всеми экземплярами `Client`, сброс из фасада
  был бы гонкой.
- ⚠ **`StatsJSON()` УБРАН из API первой версии.** Первая редакция объявляла его и
  подробно описывала семантику, но **сериализатора не существует**: `StatsJSON`
  — ноль вхождений в `client/`, у `statsRegistry` только инкременторы, а
  `StartStatsLogger` печатает в slog, не сериализует. То есть метод обещал
  механизм, которого нет, и тянул за собой новую работу в `client/` (снимок +
  сериализация ~50 атомарных полей и пулловых gauge'ов). Минимум наблюдаемости
  покрывают `State()` + `OnStateChange`; сериализатор — кандидат следующей
  версии (§7).
- ⚠ **`SetGlobalPoolForStats(nil)` безусловен — при перекрытии сессий обнуляет
  ЧУЖОЙ указатель.** Первая редакция записала «✅ корректно очищается», и это
  формулировка сильнее данных: `ws_pool.go:5431` ставит `nil` без сравнения с
  текущим значением. Сценарий, штатный для мобильных: `Stop()` → быстрый
  `Start()`; `Close()` старого пула идёт неспешно (шлёт session-FIN по 8 слотам),
  новый успевает выставить себя, затем старый обнуляет указатель **на новый**.
  Результат — `stats.go:1085/1158/1382` навсегда перестают видеть живой пул, то
  есть наблюдаемость умирает молча. На десктопе не проявляется (процесс = одна
  сессия). → Однострочная правка в `client/`: `CompareAndSwap(p, nil)`.
  ⚠ Это подрывает и §4.8.2 п. 3, где состояние `degraded` предлагается строить
  **именно на этих данных**.

### 4.7. Goroutine-safety — ДВА разных дефекта, фасад закрывает только один

⚠ **Первая редакция этого раздела гласила «чинится в фасаде, не трогая
`engine/`» — это формулировка сильнее данных.** Проверено чтением кода
2026-08-24; дефектов два, и мьютекс в фасаде закрывает только внешний.

**(1) Внешний — двойной вызов из UI-потока.** Закрывается фасадом:
`mobile.Session` несёт `sync.Mutex` и явную машину состояний
(`idle → connecting → connected → stopping → idle`), `Start`/`Stop`
идемпотентны. Двойной `Start()` при быстром тапе — реальный сценарий.

**(2) Внутренний — гонка `streamReaderLoop` ↔ `Close()`. Мьютекс в фасаде от неё
НЕ защищает**, потому что она между двумя горутинами внутри `engine`:

- `streamReaderLoop` пишет `e.stream = newWST` (`engine_shadowlink.go:762`) и
  `e.socks.WST = newWST` (`:764`) **без синхронизации**;
- `Close()` читает `e.stream` и зовёт `.Close()` на нём (`:846`), также без
  блокировки;
- ⚠ **`streamReaderLoop` запускается через `go` в ЧЕТЫРЁХ местах** (`:554`,
  `:610`, `:626`, `:808`) и **не покрыт никаким WaitGroup**: `pollWG` считает
  только poll-воркеры (`:775-776`). То есть `Close()` дожидается poll-воркеров
  (`:833`), но **не дожидается stream-ридера**;
- `e.cancel()` в начале `Close()` (`:830`) не закрывает окно: цикл проверяет
  `ctx.Done()` в `select` (`:721`), но между проверкой и записью на `:762`
  ридер может успеть переприсвоить `e.stream`.

Последствие: закрывается старый транспорт, новый остаётся висеть — то есть
утечка TLS-соединения к origin. Для мобильного клиента, где `Start`/`Stop`
происходят десятки раз за жизнь процесса, это накапливается; лишние соединения
к origin — P0-класс по модели угроз (policing по числу соединений, hard rule 11).

**Что делать:** при переносе в `engine/` добавить `streamWG sync.WaitGroup` по
образцу существующего `pollWG` и защитить `e.stream`/`e.socks.WST` мьютексом.
Это **правка внутри `engine/`, а не только фасада**, — то есть шаг 1 порядка
работ перестаёт быть чисто механическим переносом.

⚠ Windows-dev: `-race` недоступен (hard rule 6), поэтому доказывать исправление
надо детерминированным тестом (например, `Close()` во время активного
реконнекта с проверкой, что закрыт именно текущий транспорт), а не «зелёным
прогоном».

## 4.8. Среда исполнения телефона — раздел, которого не было

⚠ Ревью 2026-08-24 вынесло системный диагноз первой редакции: **это была спека о
том, как вынести Go-код из `package main`, а не о том, как он будет жить на
телефоне.** Всё проверенное проверялось со стороны компилятора и линкера; всё
пропущенное — со стороны среды исполнения. Ниже закрытие этого крена.

### 4.8.1. Смена сети — P0, обработки НЕТ нигде. Проблема ВСЕХ ТРЁХ платформ

⚠ **Заголовок первой редакции («Wi-Fi↔LTE») сузил проблему до мобильных — это
неверно.** Смена сети бывает и на десктопе: Wi-Fi↔Ethernet, док-станция,
подключение другого VPN, выход из спящего режима. Механизм зависания слотов от
платформы не зависит; на Windows он просто реже наступает.

Поиск по `client/`, `proxy/`, `cmd/` на `NetworkChanged|OnNetworkChange|
ENETUNREACH|EHOSTUNREACH|no route to host` даёт **одно попадание, и то в CLI**
(`cmd/nixavpn-client/tunnel.go:350`).

⚠ **И это попадание делает НЕ то, что нужно** (проверено 2026-08-24): NIC-вотчер
обновляет `tunsdialer.DefaultDialer.InterfaceName/InterfaceIndex`
(`tunnel.go:578-579`) — то есть чинит **bypass-диалер**, чтобы обход туннеля не
бил в down-адаптер. **Слоты WS-пула он не трогает вообще.** Поэтому:
- регресса на Windows от переноса **нет** — вотчер живёт в `tunnel.go`, который
  остаётся в CLI и продолжит работать;
- но и защиты от зависания слотов у десктопа **сейчас тоже нет**.

✅ Проверено: у `WSPoolTransport` **нет публичного метода форс-реконнекта** —
только `Connect` (`ws_pool.go:2435`), `Close` (`:5430`), `HealthySlots`
(`:5464`). Ручки «пересоздать слоты» не существует ни для одной платформы.

Что происходит фактически при переключении сети:
1. Все 8 слотов держат TCP со **старого** IP. Они не падают — они **зависают**
   до TCP-таймаута, потому что RST никто не пришлёт.
2. Смерть обнаружит только ридер по ошибке чтения (`ws_pool.go:4589`) или
   keepalive-таймаут.
3. Дальше `reconnectLoopInner` (`ws_pool.go:3445`) с экспоненциальным backoff,
   который по hard rule 8 при `attempt ≥ 4` вырождается **ровно в 60.000 с**.
4. Смягчение `waitBackoffOrRevival` (`ws_pool.go:3510`) будит паузу, только если
   **хоть один** слот пробился; при одновременной смерти всех восьми будить
   некому.

**Итог: туннель встаёт на десятки секунд, в худшем случае за минуту**, тогда как
ОС знает о смене сети мгновенно. Для мобильного это не краевой случай, а
основной режим жизни.

⚠ Удар и по маскировке: пачка реконнектов после смены сети — тот самый
thunder-herd, против которого сделан post-meltdown spread
(`ws_pool.go:3495-3505`). Он **не сработает**, потому что `recentMeltdownNs` не
выставлен: смерти пойдут как natural/age_cut, а не как meltdown.

**Решение — ОБЩЕЕ для трёх платформ, а не мобильная фича:**

1. **Ядро:** новый публичный метод на `WSPoolTransport` в `client/` —
   принудительный teardown слотов + сброс лестницы backoff + **разнесённый**
   реконнект (переиспользовать `reconnectJitterOffset`, `ws_pool.go:968`, чтобы
   не отдать herd). Пишется один раз, служит всем платформам.
2. **Android/iOS:** `Session.NetworkChanged()` в фасаде; нативка зовёт из
   `ConnectivityManager.NetworkCallback` / `NWPathMonitor`.
3. **Windows/десктоп:** источник сигнала уже есть — `runNICWatcher`
   (`tunnel.go:558-580`) уже детектирует смену интерфейса раз в 30 с. Достаточно
   добавить туда вызов того же метода ядра, рядом с существующим `Store`
   интерфейса. ⚠ Без этого шага десктоп останется с той же дырой, что и сегодня,
   — то есть кроссплатформенность будет заявлена, но не достигнута.

⚠ **Это работа в `client/` (+ одна строка в `tunnel.go`), а не строчка в
фасаде.** И метод **обязан уважать существующий запрет** на сброс лестницы
(`ws_pool.go:3512-3520`, гейт `lastWasRateLimited`, запрет от 2026-05-18):
рейт-лимит бывает per-carrier, и слепой сброс превратил бы смену сети в способ
обойти собственный backoff.

⚠ Периодичность у десктопного детектора — **30 с**, то есть реакция там будет
медленнее событийной мобильной. Это не дефект: на десктопе смена сети реже и
время простоя терпимее. Но записать честно, чтобы «работает на всех платформах»
не читалось как «одинаково быстро на всех платформах».

### 4.8.2. Наблюдаемость: в прод-режиме `ErrorCh` не сигналит НИКОГДА — P1

`signalError` обёрнут в `sync.Once` (`engine_shadowlink.go:60-67`) при буфере 1 —
то есть **одна ошибка за всю жизнь объекта**, терминальная по построению.
Источников два: `:693` (SOCKS5 упал) и `:756` (reconnect не удался), причём
второй — **только для single-WS пути** и только при `SystemVPN`.

⚠ Для `WSPoolTransport` (прод-режим) ветка реконнекта **не сигналит вовсе**:
`engine_shadowlink.go:743-748` — `if _, isPool := ...(*client.WSPoolTransport);
isPool { return }`. А `reconnectLoopInner` бесконечен.

Следствие: при потере сети пул молча сидит в backoff, SOCKS5-порт **продолжает
принимать соединения**, приложения получают зависшие сокеты, а `State()`
показывает `connected`. Наружу — тишина ровно там, где наблюдаемость нужнее.

**Решение:**
1. `ErrorCh` маппится в `OnError` + состояние `failed`; сессия после этого
   непригодна и требует нового `Start()`.
2. ⚠ **Автореконнект в фасаде НЕ делать** — он уже есть уровнем ниже и
   бесконечен. Свой контур поверх дал бы два конкурирующих и удвоил соединения к
   origin (P0-класс, hard rule 11).
3. Нужен отдельный сигнал **здоровья**, а не ошибки: состояние `degraded` при
   `ready_slots == 0` дольше N секунд (данные уже есть в `client/stats.go`).

### 4.8.3. Doze и скачки часов — P1

⚠ **Две величины с именем `slot_age*` считаются по-разному, и это новая грань
ловушки из hard rule 12:**
- watchdog: `slot.startedAtNs.Store(time.Now().UnixNano())` (`ws_pool.go:3319`),
  читается на `:2576/:2599` — **`.UnixNano()` теряет монотонную компоненту**, то
  есть это чистый wall clock, чувствительный к NTP-коррекции;
- ридер: `time.Since(slotStart)` (`ws_pool.go:4589`) — монотонность сохраняет.

На мобильном NTP-коррекция после долгого сна штатна, и эти два источника
разойдутся. Детектора нет: поиск на `suspend|resume|clockJump` в `client/` —
ноль попаданий.

**Doze — штатный аналог laptop-sleep артефакта** (hard rule 13): в том прогоне
сон дал возрасты до **505.4 с** при `worstCaseTeardown` 142.5 с (в 3.6 раза выше
бюджета), контур ротации встал целиком. На телефоне это не авария, а ежедневный
режим.

**Решение:** привести watchdog к монотонному источнику. ⚠ Это правка
тайминг-контура → по hard rule 8 требует замера, поэтому выносится в §8
отдельной работой, а не в объём `mobile/`. Минимум для фасада — детектор скачка:
если `now - started` кратно превысил `worstCaseTeardown()`, принудительно
ротировать пул, не дожидаясь watchdog.

### 4.8.4. `Stop()` уничтожает engine — P1

`ShadowLinkEngine.Close()` (`engine_shadowlink.go:828`) **необратим**: отменяет
контекст, закрывает пул, транспорт и клиент; `Connect()` после него не
предусмотрен. Машина состояний §4.2 обещает возврат в `idle`, подразумевающий
новый `Start()`, — под ней лежит объект, который в `idle` не возвращается.

**Контракт:** `Start()` после `Stop()` создаёт **новый** `ShadowLinkEngine`.
Причина частых `Start`/`Stop` на мобильном — не «быстрый тап», а жизненный цикл
приложения (уход в фон, убийство процесса, рестарт extension), поэтому утечка
транспорта из §4.7 п. 2 накапливается тем быстрее.

⚠ Смежное: в `Connect` три ранних `return` (`:573`, `:679`, `:683`) зовут
`cancel()`, но **не закрывают уже подключённый `e.cl`** — каждый неудачный
`Start()` оставляет висящий `client.Client` с TLS-соединениями к origin. Привести
к единому `defer`-cleanup при неуспехе; это предусловие идемпотентного `Stop`.

### 4.8.5. Энергопрофиль — P1, конфликт с hard rule 8 предъявляется честно

`keepaliveDefaultBase` = 5 с, сэмплер усечён в **[2.5 с, 10 с]**
(`ws_pool.go:922`, `:2814`, `:2844`), проход шлёт всем 8 слотам. LTE-модем держит
RRC Connected ~5–10 с после передачи — **при таком интервале модем практически
никогда не уходит в idle**. Плюс ротация каждые 70–142 с = новые TCP+TLS
handshakes, самая дорогая по энергии операция. Поиск на
`lowPower|batterySaver|pauseWhenIdle` в `client/` — ноль попаданий.

⚠ **Прямой конфликт:** §4.4 помечает `KEEPALIVE_INTERVAL`/`MAX_SLOT_AGE` как «не
трогать» — дефолты выведены полевыми замерами. Но **замеры делались на десктопе с
постоянным питанием**. На телефоне та же константа означает разряд батареи:
маскировка идеальная, а продукта нет.

**Решение:** константу НЕ менять (hard rule 8), а завести **замер энергопрофиля
как предусловие релиза** (§7). Возможный компромисс — меньший `WSPoolSize` на
мобильном (поле уже есть), что снижает и энергию, и число соединений к origin —
но правило 8 требует замера и на стороне выживаемости.

### 4.8.6. DNS — требование переходит нативке

✅ Проверено: `dnsproxy` в мобильное дерево **не попадает**. Единственный
`NewForwarder` вне тестов — `tunnel.go:688` внутри `startSplitDNS` (`:684`),
вызываемого только из тоннельного пути (`:371`); `engine_shadowlink.go` его не
импортирует. Bind на привилегированный `:53` (`tunnel.go:632-635`) при границе
API «SOCKS5» **не наступает**.

⚠ Но следствие обратное и в первой редакции отсутствовало: в CLI split-DNS
решал задачу «DNS не уходит мимо туннеля». На Android при `VpnService` резолв
идёт через системный резолвер, и **если нативка не вызовет
`Builder.addDnsServer()`, DNS утечёт мимо туннеля**. Фасад про DNS не знает
ничего — это **непереданное требование к нативной стороне**
(`addDnsServer` / `NEDNSSettings`), а не дефект Go-кода.

⚠ **`SHADOWLINK_DNS_STUB_IPS` — ложный P0 для `mobile/`** (исправление §4.4):
пакет в дерево не входит, чинить ради фасада не нужно. Настоящий P0 остаётся
**один** — `client/datapath.go:25`.

### 4.8.7. IPv6 — политика не определена, P2

`client/dnsproxy/proxy.go:95` и `:520` фиксируют: AAAA получают пустой NOERROR,
потому что **IPv6 глушится LeakGuard'ом**. На мобильных leakguard'а нет (§4.8.8)
— значит **глушить некому**, а многие LTE-сети РФ IPv6-preferred. `ServerAddr` —
голый origin IP (hard rule 1); если он только v4, а сеть v6-only, соединение не
встанет вовсе. Нужно решение владельца: AAAA у origin, форс v4 нативкой
(`Builder.allowFamily`), либо принять неработоспособность в v6-only сетях.

### 4.8.9. Память iOS: числа разъезжались, оценки для 8 слотов НЕТ — P1

⚠ **Сводка чисел, потому что первая редакция путалась в трёх местах:**

| Что | Лимит | Кого касается |
|---|---|---|
| `NEPacketTunnelProvider` | **50 MiB** (iOS 15+) | **только iOS** |
| `NEAppProxyProvider` / DNS Proxy | **15 MiB** | только iOS |
| Android `VpnService` | лимита в MiB **нет** — обычная куча процесса | Android |
| Windows | не применимо | — |

Источники и оговорки — `docs/plans/2026-08-21-native-readiness.md` §3 (тред Apple
DTS 73148, лог jetsam sing-box#3976, блог Tailscale). ⚠ `CLAUDE.md` п. 1a
приведён в соответствие 2026-08-24; прежние «~15 МБ для NetworkExtension» —
неверная цифра (это лимит другого provider'а).

⚠ **Оценки памяти для нашего пула НЕТ ни в спеке, ни в коде.** Известно только:
`poolSize` = 8 (`engine_shadowlink.go:313`), `MaxStreamsPerSlot` = 8 (`:423`) →
до 64 стримов со своими буферами и flow-control окнами, плюс uTLS-состояние на
слот, плюс `skins/browser`, плюс 211 пакетов tun2socks (§3).

При **жёстком** лимите 50 MiB это не отложенный вопрос, а **предусловие выбора
границы API**: если 8 слотов не влезают, режется `WSPoolSize` — а это hard
rule 8, то есть замер на выживаемость, работа с длинным циклом.

→ **Ход:** замерить RSS десктопного прогона в WS-Pool режиме под нагрузкой
(`poolSize=8`) как **нижнюю оценку** для iOS.

⚠ **Что этот замер может и чего не может** (решено с владельцем 2026-08-24).
Асимметричен: код общий, 8 слотов с TLS и буферами весят сопоставимо на любой
платформе, а на iOS сверху ложится Go-рантайм в extension и мост — то есть там
будет **больше, не меньше**. Поэтому:
- RSS ≥ ~45 МБ → в 50 MiB не влезем **гарантированно**, вопрос закрыт
  отрицательно без устройства;
- RSS 15–20 МБ → вероятно влезем, но подтвердить может только реальный iOS;
- 30–40 МБ → серая зона, нужен замер на устройстве.

То есть он способен **закрыть** вопрос отрицательно, но не способен закрыть
положительно.

⚠ **Приоритет понижен с P1 до предусловия iOS-РЕЛИЗА, а не старта работ.**
Обоснование: (1) на шаги 0–2 ответ не влияет — вынос `engine/`, конфиг и
`mobile/` делаются одинаково при любом числе, а граница API (SOCKS5) совместима
с обеими iOS-архитектурами; (2) `.xcframework` с текущей машины не собирается в
принципе (нужен Xcode/macOS), то есть до реальной iOS-сборки дистанция;
(3) Android от лимита не зависит вовсе. Делать замер лучше сразу на устройстве,
когда дойдём до iOS вплотную.

### 4.8.10. iOS: Go-код обязан жить ВНУТРИ extension — P2

⚠ §2 говорит «Go отдаёт прокси, платформа решает, как заворачивать трафик». На
iOS это **не свободный выбор**: NetworkExtension — отдельный процесс с
собственным адресным пространством, и `127.0.0.1:PORT` главного приложения ему
недоступен как способ завернуть системный трафик. Значит фасад линкуется **в
extension**, и бюджет §4.8.9 — это бюджет extension'а **целиком**.

### 4.8.11. Убийство процесса без `Stop()` → ghost-сессии — P2

§4.8.4 описывает `Start` после `Stop`. Но iOS (и Android при нехватке памяти)
убивают процесс **без** вызова `Stop()`: `WSPoolTransport.Close()` не
выполняется, **session-FIN серверу не уходит**, и на сервере остаются до 8
ghost-сессий до истечения `SessionTimeout` = **90 с**
(`server/config.go:291`).
⚠ Первая редакция писала «idle-таймаут захардкожен 300 с» — **склеены две
разные величины** (найдено при подготовке доки для интеграторов, 2026-08-24):
300 с это `IdleTimeout` HTTP-сервера (`server/server.go:177`), время
простоя TCP-соединения, а живучесть VPN-сессии задаёт `SessionTimeout`.
Ошибка была не безобидной: на ней строилась оценка, как долго ghost-сессии
занимают квоту устройств — реальное окно втрое короче.

⚠ Связка, которую надо держать в уме при включении whitelist (§4.4): если у
`AdmitSession` есть квота устройств, пользователь с трижды перезапущенным
extension'ом может **упереться в собственную квоту** и получить отказ.

### 4.8.8. leakguard — исправление ошибки первой редакции

⚠ Первая редакция писала «фасад обязан исключать этот слой явно» и ставила
leakguard в один список с `tunnel.go`/`logging.go`. **Обоснование неверно, а
проблемы не существует:** стрелка зависимостей направлена **обратно** —
`client/leakguard` зависит от `client` (`rules.go:96` зовёт
`dnsproxy.DefaultYandexIPs()`), а не наоборот; `go list -deps ./client | grep
leakguard` → пусто; единственный импортёр во всём дереве — `main.go:31`.

Исключение достигается тем, что `engine/` его не импортирует. Build tags не
нужны, отдельный пакет не нужен: Go отбрасывает неимпортированные пакеты на
уровне графа сборки.

**Сторож:** тест в `mobile/`, утверждающий, что `go list -deps ./mobile` не
содержит `leakguard` — иначе связь появится молча, когда кто-нибудь потянет
`dnsproxy.DefaultYandexIPs()` из `engine/`.

### 4.9.1. Пути десктопа и мобильных РАСХОДЯТСЯ — это надо признать явно

⚠ Первая редакция этого не обсуждала, а различие принципиальное.

На Windows трафик **не ходит через localhost-сокет**: `InProcessDialer`
(`proxy/socks5/inprocess.go:261`) подключается к SOCKS5-серверу в процессе,
минуя loopback (`main.go:241-245`, `tunnel.go:611-613`). Фасад же по §2 отдаёт
**реальный TCP-порт** на `127.0.0.1`.

Следствия, которые надо принять сознательно:
1. **Производительность.** На мобильных добавляется реальный loopback-сокет
   (лишнее копирование + syscalls на каждый пакет). Для Android с tun2socks
   внутри Go этого можно избежать, отдав тот же `InProcessDialer` — но это
   расширение API за пределы первой версии.
2. **Безопасность.** Открытый `127.0.0.1:PORT` на Android доступен **любому
   приложению**. У десктопа этой поверхности нет вовсе. Частично компенсируется
   кредами SOCKS5 (§4.2), которых в первой редакции не было; остаточная разница —
   сам факт слушающего порта.
3. **Тестируемость.** Два разных пути данных = два разных набора отказов.
   Регресс на десктопе не проявится в мобильных тестах и наоборот.
4. ⚠ **Весь накопленный корпус полевых замеров получен на in-process пути.**
   Hard rules 8/9/12/15 — окно реза, фаза, экспозиция, keepalive — измерялись на
   десктопе, где loopback-сокета на flow нет. К мобильному datapath они
   переносятся **не автоматически**. §4.8.5 называет причиной отличия только
   питание — реальных отличий как минимум два.

**Решение для первой версии:** оставить SOCKS5-порт (он единственный работает на
всех трёх), но записать in-process путь для мобильных как **явный кандидат
второй версии** (§7), а не как забытую деталь. Механизм уже существует и
переиспользуем — `socks5.NewInProcessDialer` не платформозависим.

### 4.9.2. Риски регресса для работающего Windows-клиента

Windows работает в проде — его регресс дороже любой мобильной фичи. Отсортировано
по вероятности × цене (ревью 2026-08-24):

| # | Риск | Механизм | Как поймать |
|---|---|---|---|
| R1 | **`ErrorCh` отваливается молча** | `main.go:378` comma-ok: `ok=false` → `engineErr` остаётся nil → `select` (`:382-387`) ждёт только сигнал. Клиент перестаёт выходить при смерти SOCKS5 | compile-time `var _ ErrorSignaller` + тест, что канал не nil (шаг 0a) |

## 5. Тестирование

- Юнит-тесты `mobile/`: идемпотентность `Start`/`Stop`, **`Start` после `Stop`
  создаёт новый engine** (§4.8.4), парсинг конфига, отсутствие паники при `Stop`
  до `Start`, `SocksPort() == 0` до `Start`.
- **Сторож изоляции зависимостей**: `go list -deps ./mobile` не содержит
  `leakguard`, `tun2socks/v2/engine` (gVisor), `xray` — и, **главное,
  `tun2socks/v2/proxy`** (211 пакетов, §3).
  ⚠ Первая редакция перечисляла только первые три, то есть сторожила пакеты,
  которые и так не приезжают, и **не сторожила приезжающий**. Это ровно тот
  зелёный сторож, который ничего не измеряет.
- ⚠ **`go vet` под всеми тремя `GOOS`** — дёшево, ловит платформенные ошибки без
  устройства, должно стоять наравне с `go test ./...`:
  `GOOS=android GOARCH=arm64 go vet ./engine/ ./mobile/` и то же для `ios`.
- **Сторож gomobile-совместимости**: прогон `gobind` по пакету.
  ⚠ `gobind` — внешний бинарь; тест, который при его отсутствии делает
  `t.Skip`, **зелен всегда и не сторожит ничего** («Guard tests that measure
  nothing»). Поэтому: тест помечается build-тегом и запускается в CI явной
  целью, а его отсутствие в обычном прогоне фиксируется как известный пробел, а
  не маскируется скипом.
- Проверка сборкой: `gomobile bind -target=android` → реальный `.aar`.
  ⚠ **Порог размера задать до сборки**, иначе «проверить размер» ничего не
  значит. И не путать с лимитом iOS: 50 MiB из §4.6 — это **память**
  NetworkExtension, а не размер артефакта.
- Регресс: полный `go test ./...` — 18 пакетов должны остаться зелёными.
- ⚠ **Кроссплатформенный регресс проверяется СБОРКОЙ под все три таргета**, а не
  только тестами на Windows: `GOOS=windows`, `GOOS=android`, `GOOS=ios`
  (`GOARCH=arm64`, плюс `CGO_ENABLED=1` для android — режим gomobile). Зелёный
  прогон на одной платформе о двух других не говорит ничего.
- ⚠ **Windows-путь SystemVPN тестами не покрывается** (требует админских прав,
  TUN-адаптера и правки маршрутов) — после рефакторинга проверять **вручную**
  по §4.9.2. Это известный пробел, а не то, что можно закрыть скипом.
- ⚠ Тест на утечку транспорта (§4.7 п. 2) и на cleanup при неудачном `Connect`
  (§4.8.4) — детерминированные, а не под race-детектором (hard rule 6).

⚠ Windows-dev: `-race` недоступен (hard rule 6), поэтому зелёный локальный
прогон гонку не исключает. Тест двойного старта пишется так, чтобы дефект
проявлялся детерминированно (проверка состояния), а не только под race-детектором.

0a. **Заменить `eng.(*ShadowLinkEngine)`** (`main.go:378`) на именованный
   интерфейс `ErrorSignaller` в `engine.go` + compile-time сторож
   `var _ ErrorSignaller = (*engine.ShadowLinkEngine)(nil)`. ⚠ Иначе comma-ok
   вернёт `false` молча и **W8-контур «engine упал → выход» отключится**;
   компилятор этого не поймает, тестов на `main.go:378` в дереве нет.
1a. **Починить гонки и утечки** отдельными коммитами от перемещения:
   - `streamWG` для трёх живых спавнов `streamReaderLoop` (§4.7 п. 2).
     ⚠ **НЕ «по образцу `pollWG`»**: `pollWG.Wait()` стоит на `:833`, а
     `streamWG.Wait()` там заблокирует `socks.Close()` на время висящего
     `UpgradeToWebSocket` (до `HandshakeTimeout` = 10 с). Место — **после**
     `socks.Close()` и **перед** `stream.Close()`, с таймаутом. На iOS 10 с —
     это весь бюджет `stopTunnel`;
   - ⚠ `e.socks.WST` — **правка выходит за `engine/`**: поле публичное и
     читается из `proxy/socks5` (`server.go:252/258`, `inprocess.go:58/94/98`),
     поэтому мьютекс в `engine/` гонку не закрывает. Вариант — косвенность
     `WSTProvider func() client.StreamTransport` в `socks5.Server` (локальнее,
     чем `atomic.Pointer` + геттер);
   - единый `defer`-cleanup на ранних `return` в `Connect` (§4.8.4);
   - удалить мёртвый `StartDownloadStream` + `streamCtx`.
1b. **`NetworkChanged()` на `WSPoolTransport`** (§4.8.1) — **работа в `client/`**,
   с уважением гейта `lastWasRateLimited` (`ws_pool.go:3512-3520`).
   Без неё фасад пройдёт все тесты и окажется непригоден при первом же выходе
   пользователя из дома.
2. **Написать `mobile/`** поверх `engine/`: диспетчер колбэков (§4.1), bind `:0`
   (§4.5), состояние в `atomic` (`State()` не должен блокироваться на время
   `Start`).
3. **Собрать `.aar`**, сверить с заранее заданным порогом размера.
4. **Обновить документы** фактическим статусом (README, план 08-21, `CLAUDE.md`).

⚠ **Порядок работ занижался ПЯТЬ раз подряд** (ревью 2026-08-24). К признанным
расширениям (гонка 1a, смена сети 1b) добавились: правка `ListenAddr` (§4.2a),
`CompareAndSwap` в `SetGlobalPoolForStats` (§4.6), правка 3 тестовых файлов в
`proxy/socks5` (§3), вынос `InProcessDialer` из `engine/` (§3), 4 файла CLI
из-за переезда `ShadowLinkConfig` (§4.9.2).

**Формулировать надо прямо: шагов в `client/` и `proxy/` больше, чем в
`mobile/`.** Это не «обёртка над готовым ядром» — это подготовка ядра к тому,
чтобы у него вообще мог быть второй потребитель.

Что из этого следует практически: **пункт 0a дешёвый и делается первым** —
замер RSS может изменить архитектуру iOS, а сторож на `ErrorSignaller` защищает
от самого коварного регресса (R1, молчаливый).

⚠ **Вне этого объёма** (§8): правка handshake, включение whitelist, key
separation. Их порядок относительно шагов 0–4 определяет владелец.

## 7. Открытые вопросы

1. ✅ **Аудит ключей — ЗАКРЫТ** (2026-08-24, см. §4.3). Ключи не общие,
   P0-находок нет. Но выявлена зависимость: персистентный **аккаунт**-ID
   требует предварительной правки handshake, иначе ослабляется аутентификация
   сервера. Фасад принимает `ClientIDHex` как непрозрачную строку — это решение
   от находки не зависит.
2. ✅ **Аудит конфигурируемости — ЗАКРЫТ** (2026-08-24, см. §4.4). Package-init
   ENV ровно два (`client/datapath.go:25`, `client/dnsproxy/stub.go:29`) — для
   мобильных недоступны в принципе, лечатся полями `ClientConfig`.
3. ⏳ **iOS-архитектура** — Packet Tunnel + gVisor (50 MiB) против
   `NEAppProxyProvider` (15 MiB, стек не нужен). Решение **не требуется** для
   шагов 1–2: выбранная граница API (SOCKS5) совместима с обоими.
4. ⏳ **Энергопрофиль не измерен** (§4.8.5) — keepalive [2.5–10 с] + ротация
   [70–142 с] × 8 слотов; цена в мА·ч неизвестна. **Предусловие релиза**, не
   правка констант (hard rule 8).
5. ⏳ **IPv6-политика на мобильных** (§4.8.7) — решение владельца: AAAA у origin,
   форс v4 нативкой, либо принять неработоспособность в v6-only сетях.
6. ⏳ **Бюджет холодного старта.** Fan-out 8 слотов — замеренный span **2.422 с**
   (hard rule 8), при зависшем handshake до ~10 с (`HandshakeTimeout`,
   `ws_transport.go:362`). У `NEPacketTunnelProvider.startTunnel` окно
   ограничено. → `Start()` **не должен блокироваться** до готовности всего пула;
   готовность сообщается через `OnStateChange`. Зафиксировано в §4 сигнатурой.
7. ⏳ **Порог размера `.aar`** не задан (§5).

## 8. Что в объём этой работы НЕ входит

Найдено аудитами, требует отдельного решения владельца — фиксирую, чтобы не
потерялось и чтобы не расползся объём:

- **P1 — open relay.** Аутентификации клиентов в проде нет; включение whitelist
  требует (а) персистентного ID на клиенте, (б) заполнения `authorized_clients`
  из биллинга через management API. См. §4.3.
- **P1 — правка handshake** (подмешать `ECDH(client_eph, server_static)` в IKM)
  как предусловие предсказуемых ID. Бамп `protoVersion`, затрагивает сервер.
- **P3 — key separation:** статический приватный X25519-ключ сервера
  переиспользуется как HKDF-IKM миграции (`server/websocket.go:740-745`).
  На wire не выходит, риск низкий, но правильнее отдельный master key.
- **Уборка мусора:** `SHADOWLINK_DRAIN_IDLE_STREAMS_MAX`, серверное мёртвое
  `mimicry.cover_traffic`, `idle_timeout_sec` (валидируется, но `IdleTimeout`
  захардкожен 300 с), неверный комментарий «default 6» у `ws_pool_size`.
