# WhiteCall — обход allowlist через whitelisted SFU (VK/WB/…) — MASTER design

**Date:** 2026-06-05
**Status:** MASTER DESIGN (карта ветви) — pending opus-review → декомпозиция на под-проекты
**Класс:** новый самостоятельный продукт, отдельный Go-модуль `whitecall/` (как `shadowlink/`), интегрируемый в NixaVPN через тонкие точки.

> Это MASTER-спека ВЕТВИ (видение + декомпозиция на под-проекты + threat model + инварианты), НЕ
> реализационная спека. Каждый под-проект получает свою spec→plan→impl. Декомпозиция обязательна —
> ветвь = платформа из многих подсистем, не одна спека.

## Этическая рамка (важно для позиционирования)

Allowlist (default-drop) — отрезка доступа ко ВСЕМУ легальному интернету кроме ~720 «одобренных»
доменов — сам по себе правовым образом сомнителен (право искать/получать информацию: Конституция РФ ст. 29,
международные нормы). WhiteCall — средство ВОССТАНОВЛЕНИЯ доступа к легальным ресурсам, а не «помощь в
нарушении». Мы не симметричная сторона «оба нарушаем ToS»: цензор отнимает право, мы помогаем его вернуть.

**НО — асимметрия власти (определяет реальный риск, не справедливость):** «кто морально прав» ≠ «у кого
рычаг наказать». Цензор/РКН действует под прикрытием закона (ФЗ о суверенном интернете, режим учений) —
оспаривание годами, исход непредсказуем. Юзер же формально нарушает ToS частной платформы (VK/WB), у
которой МГНОВЕННЫЙ рычаг (бан/жалоба). За обход allowlist прямой статьи для ПОЛЬЗОВАТЕЛЯ пока нет (в отличие
от распространения средств обхода — тут риск у НАС как у продукта). Вывод: издержки несёт юзер, хоть право
нарушает цензор. Поэтому WB-guest (без личной идентичности) — правильный выбор: минимизирует то, чем юзер
может поплатиться, НЕЗАВИСИМО от того кто прав. Позиционирование продукта — «восстановление доступа», не
«взлом»; но техническая защита юзера строится исходя из асимметрии, а не из моральной правоты.

## Цель и позиционирование

**Самостоятельный продукт** (своё ядро, возможно отдельный бренд) с **лёгкой интеграцией в админку NixaVPN**.
Архитектурно изолирован (отдельный модуль/go.mod, как shadowlink/), NixaVPN потребляет через чёткие точки
(деплой/админка/биллинг), не лезет внутрь. Принцип проекта [[feedback_shadowlink_isolation]].

**MVP-цель (юзер): «сначала просто чтоб работало»** — доказать, что механика живая У НАС. Позиционирование
(аварийный доступ vs повседневный VPN) — после PoC. VK-SFU даёт 5-25 Мбит/с (PoC-класс).

**⚠ ЧЕСТНАЯ РАМКА (опус-ревью 2026-06-05):** это **R&D-ставка с PoC-gate, НЕ продукт с дорожной картой**.
Ожидаемая ценность = «работающий аварийный доступ на недели-месяцы между ban-волнами», НЕ устойчивый
продукт и НЕ технический моат. Orchestrator-ротация = инженерная зрелость + операционная инфраструктура
поверх известной механики, а НЕ защищённая ниша (любой может добавить таймер-пересоздание; реальная
защита продукта — инфраструктура: пул VPS, биллинг, мобильные приложения, поддержка). Инвестировать в
PoC-форк дёшево и оправдано; в orchestrator — ТОЛЬКО если PoC докажет, что плечо живёт достаточно долго,
чтобы ротация осей внутри него имела смысл (если плечо умирает за дни — ротация бессмысленна).

## Архитектура

**Топология (3 узла):**
```
[Клиент РФ: joiner] → [whitelisted SFU плечо: WB/VK/…] → [Creator-VPS за рубежом] → интернет
   локальный SOCKS5/TUN      форвардер (в белом списке)        наш exit-node
```
- **joiner** (устройство юзера): SOCKS5/TUN → кодирует трафик в медиа-поток (DataChannel/VP8) → на SFU.
  Адресует ТОЛЬКО whitelisted media-IP. Заграничный creator-IP никогда не адресуется напрямую.
- **SFU плечо** (WB/VK/…): форвардит байты joiner↔creator. Не владеем — легально «участники звонка».
- **creator** (наш зарубежный VPS): на том же звонке, разворачивает поток в обычный интернет-трафик.

**Слои модуля `whitecall/`:**
1. **`transport/`** — форк kulikov0 (MIT): Pion v4, DataChannel/VP8 codec, ChaCha20-обфускация,
   SOCKS5/tun2socks, mux. БЕРЁМ, не пишем с нуля. Изолировать (bus-factor эталона = 1 → форк, не runtime-dep).
2. **`legs/`** — абстракция плеча: `Leg` interface (поднять звонок, получить креды, подключиться к SFU).

   **🔑 АРХИТЕКТУРНОЕ ПОДТВЕРЖДЕНИЕ (research `docs/research/2026-06-05-ok-and-webrtc-legs-landscape.md`):**
   «звонок = WebRTC ВСЕГДА» подтверждено для всего живого РФ-сегмента (VK/OK/Telemost/WB/Jitsi/Salute — все
   ICE/DTLS/SRTP/SCTP). → **ОДНО transport-ядро (Pion) на ВСЕ плечи**, различается только signaling-адаптер
   (логин/эндпоинт/формат крендов/DataChannel-vs-video-track). Уже ДОКАЗАНО: olcRTC одним ядром обслуживает
   Jitsi+Telemost+WbStream. Значит `legs/` — не теоретическая абстракция, а подтверждённый паттерн.

   **Плечи-кандидаты (по приоритету для гостевого/безопасного доступа):**
   | Плечо | Гостевой | SFU-движок | Занято кем-то? | Заметка |
   |-------|----------|-----------|----------------|---------|
   | **WB Stream** | ✅ guest без аккаунта | LiveKit (open-source signaling — ЛЕГКО) | да (эталоны) | **приоритет MVP** |
   | **Одноклассники (OK.ru)** | ✅ по ссылке, только имя | свой SFU (mycdn.me) | **НИКЕМ — незанято** | проприетарный signaling → реверс (puppeteer-sniffer) |
   | **Salute Jazz/SberJazz** | ✅ гостевой | свой WebRTC SFU | незанято (упоминается) | в whitelist |
   | VK Calls | ❌ аккаунт+номер | свой | да (эталоны) | юр-риск (личный аккаунт) — опционально |
   | Jitsi | ✅ по room URL | Jitsi Videobridge | да | НЕ в whitelist по умолчанию |
   | Telemost | ❌ | свой | да | ЗАКРЫТ |

   ОТВЕРГНУТЫ: MAX, Telegram — media-ядро WebRTC, но обвязка проприетарна (бинарный MessagePack / MTProto),
   обвязка ≫ ядро = дорогой реверс, не окупается.

   Мультиплечо С СТАРТА (интерфейс), MVP на WB guest. OK/Salute — следующие незанятые ниши (дифференциация:
   эталоны их не делают).
3. **`orchestrator/`** — НАШЕ ЯДРО ЦЕННОСТИ (см. ниже). Детектор + 4 оси ротации + bridging. Переносит
   принцип «жить меньше окна детекта» из ShadowLink.
4. **Точки интеграции NixaVPN** (тонкие): деплой creator-VPS через SSH-оркестратор; мониторинг/управление
   в React-админке; биллинг/планы. NixaVPN вызывает whitecall через чёткий API, не внутрь.

## Orchestrator — живучесть (наше отличие от PoC)

**Единый принцип: «жить меньше окна детекта»** на 4 осях (перенос механики ShadowLink — слот живёт < окна
заморозки TSPU, [[tspu-age-freeze-window-2026-06-05]]).

**Детектор:** мерит здоровье каждой сессии (throughput, время с последнего байта, паттерн обрывов).
Классифицирует: `natural` / `degraded` (шейпинг) / `banned` (детект). По образцу isAgeCut/anomaly classifier.

**4 оси ротации:**
| Ось | Окно детекта | Реакция |
|-----|--------------|---------|
| Сессии/звонки | WB DC рвётся ровно в 2 мин (issue #122, никем не лечится) | Пересоздать звонок ДО обрыва (~100с) + мигрировать стримы на свежий. ЭТО ЛЕЧИТ то, что у эталона не лечится. |
| Аккаунты/токены | бан аккаунта (VK) | Пул токенов, ротация при banned. WB guest → ось почти не нужна (бесплатные одноразовые). |
| Creator-VPS | блок exit-IP | Пул зарубежных VPS (деплой через наш SSH-оркестратор), увод на живой при блоке. |
| DTLS-fingerprint | детект Pion-отпечатка (исторически главный вектор) | Вариация DTLS-параметров/обфускации. Пересекается с FP-темой основного проекта. |

**Bridging:** пул из N активных звонков + M прогревающихся; стримы переезжают на свежий ДО обрыва старого.

**⚠ HIGH-1 (опус-ревью) — миграция WebRTC-звонков ≠ миграция WS-слотов, НЕ переносится механически:**
В ShadowLink миграция стрима = смена маршрута на УЖЕ прогретый WS-слот (handshake сделан, близко к
мгновенному). Свежий звонок WhiteCall = НОВАЯ WebRTC-сессия: signaling + ICE gathering + ICE checks +
full DTLS handshake + DataChannel open = СЕКУНДЫ (особенно на LTE с потерями). ICE-restart НЕприменим
(он в рамках той же сессии; нам нужен переход на другую сессию/ключи/SFU-узел = всегда full handshake).
Прогретый пул снимает handshake-латентность с критического пути — но перенос АКТИВНОГО TCP-стрима между
двумя независимыми DataChannel-сессиями требует того же re-keying/resume, что в ShadowLink Bug#9 заняло
29 коммитов + 9 пойманных багов, ПЛЮС WebRTC добавляет слой которого в WS не было. **Реалистичная цель —
НЕ «юзер не видит обрыва», а «обрыв 1-3с с авто-resume» (для аварийного доступа приемлемо).** Бесшовность
миграции звонков = самостоятельный исследовательский риск PoC-уровня, НЕ «применим инвариант ShadowLink».
2-мин обрыв WB (issue #122) — детерминированный, лечится тривиально таймером-пересозданием (WDTT уже делает
keepalive); наш детектор ценен для НЕдетерминированных обрывов (degraded/banned), не для 2-мин (MEDIUM-3).

**🔴 ИНВАРИАНТ МИГРАЦИИ (урок ShadowLink — sticky vs age-window конфликт этой же сессии):** миграция
звонков ДОЛЖНА быть НЕОБХОДИМОЙ И ДОСТАТОЧНОЙ, не излишней:
- Мигрировать ТОЛЬКО когда детектор подтвердил приближение окна обрыва, НЕ по таймеру наугад.
- Новый звонок поднят и ПРОВЕРЕН живым до переноса (как selectYoungTargetSlot — только на здоровый target).
- Перенос бесшовный: старый звонок держится пока стримы не переехали (как drain), не рвём при активных данных.
- НЕ излишне: idle-сессия без активных стримов не мигрируется — пересоздаётся при нужде (не вхолостую).
- Каждая миграция логируется с причиной (как migrate_ok/reason) — по данным видеть, не мигрируем ли зря.

**Всё измеряемо:** каждая ось — отдельный измеримый эксперимент. Детектор логирует окно детекта по оси
(как мерили окно заморозки TSPU) → пороги ротации ПО ДАННЫМ, не наугад.

## 🔴 BLOCKER-предусловия (опус-ревью — закрыть ДО техники)

### Юридический / ToS-риск (BLOCKER-1): чьи аккаунты горят — СМЯГЧЁН выбором плеча
Использование SFU как форвардера произвольного трафика — нарушение ToS платформы. Риск РАЗНЫЙ по плечам
(research `docs/research/2026-06-05-whitecall-account-access-analysis.md`, 2026-06-05):

| Плечо | Аккаунт | Гостевой | Что горит при abuse | Юр-риск юзеру |
|-------|---------|----------|---------------------|----------------|
| **WB Stream** | НЕ нужен | ✅ guest-register, произвольное имя → одноразовый JWT (без cookies/капч/номера) | только платформенный room/JWT (расходник) | **МИНИМАЛЬНЫЙ — личная идентичность не задействована** |
| Jitsi | НЕ нужен | ✅ вход по room URL | self-hosted инстанс | минимальный, НО инстанс не в whitelist |
| VK Calls | ДА | ❌ | **ЛИЧНЫЙ VK-аккаунт (привязка к номеру → паспорт/Госуслуги/переписки)** | **ВЫСОКИЙ** |
| Yandex Telemost | ДА | ❌ | Яндекс-аккаунт (левый дешевле, email) | средний, НО Телемост закрыт |
| MAX | — | — | никто не туннелирует, сам детектит VPN | исключён |

**КЛЮЧЕВОЙ ВЫВОД:** **WB Stream СТРУКТУРНО снимает BLOCKER-1** — анонимный гость, одноразовый JWT, личная
идентичность юзера НЕ задействована, гореть нечему. На июнь 2026 WB guest жив, регистрацию НЕ ввели
(подтв. ntc.party 2 мая 2026). Поскольку MVP и так на WB guest — юр-риск из «может зарубить» превращается
в **«избегать VK-плечо для платящих юзеров; WB/Jitsi безопасны»**. VK — только опционально/для тех кто
осознанно даёт свой аккаунт.

**Под-проект 0 (юр-оценка) — СУЖЕН (не блокер целиком):** (а) для WB-плеча — оценить риск самому продукту
(не юзеру): WB→жалоба оператору/РКН по abuse-IP? (б) дисклеймер про VK-плечо если включаем (горит личный
аккаунт). (в) Авторы PoC дисклеймеров «не используй основной аккаунт» НЕ дают (пробел) — мы ОБЯЗАНЫ дать
для VK-плеча. Остаточный риск (даже на WB): сам ФАКТ форвардинга через WB SFU = нарушение их ToS, WB может
банить abuse-IP/жаловаться — но это бьёт по расходнику/IP, не по личности юзера.

### Мобильная мишень (BLOCKER-2): продукт существует ТОЛЬКО на мобиле
Allowlist (default-drop) — МОБИЛЬНАЯ угроза (LTE; Wi-Fi обычно ок; desktop в РФ не страдает остро). Значит
продукт имеет смысл ТОЛЬКО если joiner работает на Android/iOS в LTE. Мобильный клиент = **отдельный крупный
под-проект**, НЕ деталь PoC: iOS NetworkExtension memory cap 15MB убьёт gvisor/tun2socks-стек; iOS-путь у
kulikov0 уже урезан (SOCKS5-only, не системный VPN). **PoC-gate ОБЯЗАН проверяться на Android+LTE на реальном
операторе (Мегафон/Tele2, «фильтруют жёстче»), НЕ на desktop+Wi-Fi** — иначе gate меряет не ту переменную и
даст ложный go.

## Декомпозиция на под-проекты (каждый — свой spec→plan→impl)

0. **Юр/ToS-оценка (BLOCKER-gate)** — ДО техники: чьи аккаунты горят, вовлечение юзера в abuse, согласие.
   Может зарубить коммерциализацию.
1. **PoC-форк (технический go/no-go gate, на МОБИЛЕ)** — форкнуть kulikov0 (MIT) в `whitecall/transport/`,
   поднять WB guest-плечо, прогнать **на Android+LTE на Мегафон/Tele2** (НЕ desktop+Wi-Fi). **КОЛИЧЕСТВЕННЫЙ
   gate:** throughput ≥ планка устойчиво 10 мин на LTE; переживаемость 2-мин обрыва на мобиле; стабильность
   на жёстких операторах. Не «руками посмотрели — вроде работает».
2. **Мобильный клиент (joiner Android/iOS)** — отдельный под-проект (BLOCKER-2): VpnService/NetworkExtension +
   headless Pion + tun2socks, iOS memory-лимиты. Вся ценность ветви живёт здесь.
3. **Доразведка плеч + мультиплечо** — research: Yandex / MAX (госмессенджер, в whitelist) / др. ЗАТЕМ `legs/`
   интерфейс + VK. Учесть: коррелированный риск (один media-behavioral детект на LiveKit-движке убьёт ВСЕ
   LiveKit-плечи разом — мультиплечо НЕ спасает от этого, только от независимых отказов).
4. **Creator/exit серверная часть** — НЕ «тонкая интеграция» (HIGH-4): пул прогретых звонков (M creator-присутствий
   на разных SFU одновременно), управление множеством Pion-сессий на VPS, ресурсные лимиты, exit-node
   NAT/маршрутизация/leak-защита, throughput-агрегация. Сюда же экономика creator:юзеры (HIGH-5 — **второй
   go/no-go gate наравне с техническим**: 1:1 = цена обычного VPN с PoC-скоростью, зачем покупать; 1:N = риск
   «один бан роняет N юзеров»).
5. **Orchestrator** — детектор + 4 оси ротации + bridging. ТОЛЬКО после PoC-gate. Перенос механики ShadowLink
   с поправкой HIGH-1 (см. инвариант ниже — миграция WebRTC-звонков ≠ миграция WS-слотов).
6. **Интеграция в платформу** — мониторинг/управление в React-админке, биллинг/планы, деплой creator через
   SSH-оркестратор.

## Threat model / эфемерность (честно)

Всё ЭФЕМЕРНО — авторы PoC единодушны: «коммерциализируется → зарежут быстро». Векторы убийства плеча:
DTLS-fingerprint, peer-IP фильтр на SFU, поведенческий анализ медиапотока, ToS/аккаунт-бан,
rate-limit/шейпинг, закрытие плеча целиком (Телемост уже закрыт). НАША ставка: не вечная лазейка (её нет),
а живучесть через ротацию + мультиплечо.

**⚠ HIGH-2 — КОРРЕЛИРОВАННЫЙ риск (мультиплечо НЕ спасает):** механизм валидации участника архитектурно
ОДИНАКОВ для всех LiveKit-подобных SFU (WB Stream = LiveKit; JWT-scoped токены, server-enforced permissions,
webhook-мониторинг аномальных участников). Если индустриальный паттерн «детект участника, форвардящего
non-media bulk вместо реального аудио/видео» станет стандартным (дёшев — bitrate-профиль bulk радикально
отличается от OPUS/VP8), он накроет ВСЕ LiveKit-плечи ОДНОВРЕМЕННО. Мультиплечо защищает от НЕЗАВИСИМЫХ
отказов (VK закрыл аккаунты ≠ WB ввёл фильтр), НЕ от коррелированных (один анти-abuse паттерн на движке SFU).
Прецедент: WB ввёл denied-peer-ip, убил WhitePass. **Явный exit-критерий ветви:** если за ~6 мес индустрия
SFU введёт media-behavioral validation — ветвь умирает целиком, не спасёт ничто. Это осознанная ставка
«жить между волнами», а не защищённая позиция.

**⚠ MEDIUM-6 — детект «вечного звонка»:** реальный человек не сидит в видеозвонке 24/7. «Пул звонков, юзер
всегда на звонке» = поведенческая сигнатура на уровне аккаунта/устройства («этот номер всегда в звонке»).
Вектор детекта на стороне ПЛАТФОРМЫ (не оператора). Учесть в orchestrator (паузы? имитация естественного
паттерна звонков?).

**⚠ MEDIUM-2 — DTLS-fp это бинарный детект, не градиент:** TSPU фингерпринтит Pion DTLS детерминированно
(байты Elliptic Curves на фикс-оффсете), `-no-dtls`=бан. «Вариация параметров» может не помочь (residual
distinguishers: версия DTLS, порядок cipher suites, CN серта "WebRTC", выбор STUN). Реальное решение —
uTLS-аналог для DTLS (наша uTLS-экспертиза есть, [[utls-chrome-fingerprint-maintenance]]), но это отдельный
крупный проект, НЕ «вариация». DTLS-fp ось недооценена в сложности.

**⚠ MEDIUM-5 — clean-room для GPL-идей:** «только идеи из GPL (vk-turn-proxy/WDTT)» юридически верно
(протокол не копирайтится), НО исполнитель, читавший GPL-код и пишущий «с нуля» = derivative-риск
(substantial similarity). Для коммерческого продукта: clean-room процесс — один читает GPL и пишет спеку
протокола, ДРУГОЙ реализует не видя GPL-кода. Прописать в под-проекте где заимствуются TURN-идеи.

## Что НЕ делаем (YAGNI / отвергнуто)
- НЕ писать transport с нуля (kulikov0 MIT берём).
- НЕ копировать GPL-код (vk-turn-proxy/WDTT — только идеи).
- НЕ внешний-TURN-relay (мёртв — наш WhitePass на этом умер, [[wb-turn-whitepass-removed]]).
- НЕ Телемост (закрыт).
- НЕ повседневный-VPN позиционирование на старте (5-25 Мбит/с — PoC-класс; решим после).

## Объём / изоляция
- Новый модуль `whitecall/` в корне репо (собственный go.mod, как shadowlink/).
- Точки интеграции с main NixaVPN: SSH-деплой creator, React-админка мониторинг, биллинг — тонкие, через API.
- ShadowLink НЕ трогается (это параллельный продукт для blocklist; whitecall для allowlist).

## Открытые вопросы (для под-проектных спек)
- Экономика creator-VPS пула (стоимость зарубежных exit-узлов на масштабе) — HIGH-5, второй go/no-go gate.
- Throughput-цель: PoC-класс приемлем для какого позиционирования (решить после PoC-данных) — MEDIUM-1,
  задать количественную планку «≥X Мбит/с устойчиво 10 мин на LTE» в PoC-gate.
- DTLS-fp: своя обфускация vs форк pion/dtls (пересечение с FP-темой основного проекта) — MEDIUM-2.
- OK/Salute signaling: проприетарный, нужен реверс (puppeteer-sniffer + webrtc-internals) — отдельная задача в под-проекте 3.

## Операционные риски / NIT (для планирования команды)
- **bus-factor=1 эталона kulikov0** (NIT-4): когда платформа сломает протокол, апстрим-фикс может не прийти —
  чинить transport придётся НАМ с нуля под давлением. Это операционная нагрузка, заложить в планирование
  (поэтому форк, а не runtime-зависимость).
- **Go-toolchain** (NIT-1): kulikov0 на Go 1.26.1 — согласовать версию toolchain в `whitecall/go.mod` при форке.
- **WB guest rate-limit** (NIT-2): guest-токены могут рейт-лимититься по IP/устройству — «ось аккаунтов
  почти не нужна» оптимистично, проверить на PoC.

## Готовность к старту разработки
Эта master-спека — ПОЛНАЯ карта ветви. По команде «начинаем» порядок: под-проект 0 (юр-оценка, сужена) ИЛИ
сразу под-проект 1 (PoC-форк на мобиле, количественный gate). Каждый под-проект → свой brainstorming→spec→
plan→impl. НЕ начинать orchestrator (5) и creator-экономику (4) пока PoC-gate (1) не пройден по данным.
