# Болталка-копилка: DPI-детектор на клиенте + анти-DPI стратегия (2026-06-05)

> Это НЕ спека и НЕ план — копилка идей из свободного обсуждения. По каждому пункту
> отдельно запускаем глубокое исследование → brainstorming → spec → plan, когда дойдут руки.
> Критерий для каждой фичи (слова юзера): «топово, архитектурно круто и будет лучше чем у других».

## Контекст / зафиксированные факты

- **Транспорт: direct к голому origin IP, БЕЗ CDN/CF.** РКН блокирует диапазоны CDN/Cloudflare —
  через них «многое перестаёт работать вообще». QUIC тоже режут (TSPU). Вывод юзера: **то что есть
  (direct + ротация слотов + decoy-сайт) — по идее лучшее что может быть** в текущих условиях РФ.
  Дальше двигаемся не в смене транспорта, а в АДАПТИВНОСТИ. См. memory [[shadowlink-masking-model-2026-06-05]].
- **Маскировка (актуальная модель):** WS binary frames (основной канал) + JSON-аналитика только на
  handshake/cover + decoy-сайт (per-persona React+Vite SPA) для зондов. НЕ «прячемся под GA/Mixpanel»
  как основной канал — это устаревшая формулировка.
- **Угроза:** TSPU замораживает долгие direct-TCP по ВОЗРАСТУ (~130с окно). Лечим ротацией слотов
  под окно. См. [[tspu-age-freeze-window-2026-06-05]] + spec 2026-06-05-tspu-age-window-tuning.

## Направление: ДЕТЕКТОР DPI НА КЛИЕНТЕ (выбрано юзером)

Клиент сам видит, что TSPU начал резать, и реагирует. Основа для детекции уже есть в коде:
- age-cut классификатор (isAgeCut), slot_age_ms при reader error, last_write_age_ms (момент заморозки),
  meltdown counter, anomaly classifier на slot reader errors, cause=age_cut/io_timeout/close_other.

### 4 реакции на обнаруженную атаку (юзер хочет ВСЕ, если выйдет топово)

#### 1. Адаптивно ускорять ротацию (самонастраивающийся порог)
- Клиент измеряет РЕАЛЬНОЕ окно заморозки (медиана slot_age_ms при age-cut за окно) и автоматически
  опускает MaxSlotAge / sticky / staggerOffsetCap ПОД измеренное значение — вместо статичного хардкода
  75s/45s. Если TSPU ужесточил (режет на 90с) — клиент сам ужмётся; если ослабил — расслабится.
- Плюс: нет ручного тюнинга env под каждого провайдера/регион. Самооборона.
- Риск: гистерезис (не дёргаться на шуме), пол (не уехать в слишком частую ротацию → rate-limit).
- Связь: прямое развитие текущего age-tuning фикса.

#### 2. Телеметрия на сервер
- Клиент репортит «меня режут на X с, провайдер Y, регион Z» → сервер агрегирует по всем клиентам →
  видит НОВЫЕ волны блокировок рано (до массовых жалоб), карта DPI по провайдерам/регионам.
- Плюс: коллективная оборона — один клиент поймал ужесточение, остальные превентивно адаптируются
  (сервер раздаёт обновлённые пороги).
- Риск: приватность (что репортим — только тайминги, без контента), объём телеметрии, не стать
  сигнатурой самой по себе.

#### 3. UI-алерт юзеру
- Клиент показывает «На твоём провайдере активна DPI — соединения подрезаются, поэтому медленнее».
- Плюс: прозрачность, юзер понимает причину тормозов, не думает что VPN сломан.
- Риск: не паникёрство, корректная формулировка, не показывать при штатной ротации.
- Самый дешёвый из четырёх — хорошая первая стадия.

#### 4. Авто-failover транспорта
- При устойчивом детекте — переключение на другой режим/порт/SNI/fingerprint на лету.
- Плюс: самый мощный — уход из-под атаки без участия юзера.
- Риск: самый сложный (на что failover-ить, если CDN/QUIC отпали? другой origin IP? другой SNI-пул?
  другой decoy-домен?). Требует пула альтернатив, которые сами не заблокированы.
- Делать ПОСЛЕДНИМ, после 1-3.

### Предлагаемый порядок (от дешёвого к сложному)
1. **UI-алерт** (пассивная детекция + индикатор) — основа детектора, малый риск.
2. **Адаптивная ротация** — развитие age-tuning, прямая польза.
3. **Телеметрия на сервер** — коллективная оборона, нужна серверная агрегация.
4. **Авто-failover** — вершина, нужен пул living-альтернатив.

Каждый пункт = отдельное исследование (peer-инструменты: как Reality/Hysteria2/XTLS/TrustTunnel
детектят и реагируют на DPI) → brainstorming → spec → plan → subagent-driven impl.

### Уточнение по UI-алерту (юзер): делать И в клиенте, И в админке
«чтоб круто и информативно». Клиент — локальный статус юзеру (CLI сейчас, GUI потом). Админка —
агрегат-карта DPI по клиентам/регионам (React admin panel). Два потребителя, оба нужны.

## Тема: FINGERPRINT — что есть и что улучшать

### Текущее состояние (по коду 2026-06-05)
- **Прибит к Chrome 133** (`LockedChromeMajor=133`, skins/browser/fingerprint.go:40). Lockstep на 4
  поверхностях: uTLS JA4, bogdanfinn H2 SETTINGS, User-Agent, sec-ch-ua — все говорят «Chrome 133».
- **Потолок из-за utls:** refraction-networking/utls v1.8.3 не имеет `HelloChrome_135+`. 133 = максимум.
  Бамп требует: utls upstream догнал → coordinated bump LockedChromeMajor + тесты + JA4-фикстура refresh.
- **PQ MLKEM768:** cold-path ClientHello c X25519MLKEM768 (env SHADOWLINK_TLS_PQ, default on); hot-path
  bogdanfinn Chrome_133 без MLKEM — safety-bridge, но JA3/JA4 cipher list совпадает.
- **JA4 запинен** фикстурой client/testdata/ja4/chrome_133_pq.txt.
- **Намеренно НЕ рандомизировать** Chrome 133 — это маскировка под массовый браузер (memory
  [[utls-chrome-fingerprint-maintenance]]). Догонять версию когда utls обновится.

### Идеи на обсуждение/исследование (fingerprint)
- **Догнать Chrome версию:** проверить, не вышел ли utls с HelloChrome_135+/140+ — Chrome 133 стареет,
  свежий мажор = меньше выделяемся в общей массе (большинство юзеров на актуальном Chrome).
- **MLKEM lockstep:** hot-path без MLKEM, cold-path с MLKEM — рассинхрон key_share между путями на одном
  IP/сессии. Потенциальный кластер-сигнал? Исследовать: свести оба пути к одному key_share.
- **Распределение версий vs одна прибитая:** сейчас все клиенты = ровно Chrome 133. Реальная популяция
  браузеров — распределение версий. Один фикс-fingerprint на ВСЕХ юзеров = сам по себе кластер-сигнал
  (все «Chrome 133.0.0.0» с одного провайдера). Спорный вопрос: разнообразить по версиям (риск — рассинхрон
  с UA/H2) ИЛИ держать один (проще, но кластер). ВАЖНО: research-driven, smoke-тест на 2 клиентах перед
  default (memory [[feedback_research_agent_pq_caution.md]]).
- **Связь с детектором DPI:** если детектор увидит, что режут именно по JA3/JA4 (а не по возрасту) —
  failover мог бы менять fingerprint-профиль (Chrome→Firefox→Safari). Сейчас профили есть
  (LockedBogdanfinnChromeProfile и др.), но прибиты к Chrome. Это пересекается с пунктом 4 (auto-failover).

### 🔴 ПРИОРИТЕТ (полевое знание юзера 2026-06-05): fingerprint diversity — серьёзное направление
Юзер ЗНАЕТ по практике (не теория):
1. **TSPU смотрит fingerprint** (100% уверенность юзера).
2. **Одинаковый FP с разных гео/мест на ОДИН origin IP = подозрение** — это кластер-сигнал, который
   TSPU ловит. Сейчас все наши клиенты = ровно `Chrome 133.0.0.0` → на один IP сыплется идентичный
   ClientHello с сотен разных мест → аномалия (реальный сайт видит распределение версий браузеров).
3. **Chrome 133 устарел** — дополнительно выделяет.

**РЕШЕНИЕ (направление, выбрано юзером — развивать серьёзно):**
- Разнообразить fingerprint по клиентам/сессиям как реальная популяция браузеров (распределение версий
  Chrome + возможно доля Firefox/Safari), НЕ один прибитый профиль.
- ОБЯЗАТЕЛЬНО: каждый профиль lockstep по всем 4 поверхностям (uTLS JA4 / bogdanfinn H2 / UA / sec-ch-ua) —
  рассинхрон ХУЖЕ кластера. utls должен иметь нужные HelloXxx профили (ограничение v1.8.3 — потолок 133).
- Догнать актуальный Chrome мажор (проверить свежий utls).
- ВАЖНО (memory [[feedback_research_agent_pq_caution.md]]): research-driven + smoke-тест на 2 клиентах
  ДО default. Распределение версий должно матчить РЕАЛЬНУЮ телеметрию браузеров (StatCounter и т.п.),
  не выдуманное.

**По приоритету:** это направление юзер ставит ВЫШЕ детектора DPI — бьёт в саму основу stealth
(fingerprint = что видит TSPU в первую очередь). Следующее глубокое исследование начинать С ЭТОГО.
Цепочка: research (как TSPU/DPI 2026 кластеризует по FP+IP; peer-инструменты — uTLS rotation, как
Reality/XTLS варьируют; актуальный utls) → brainstorming → spec → plan.

### ФАКТ-ЧЕК utls (проверено 2026-06-05)
- Наша версия: `v1.8.3-0.20260301010127-aa6edf4b11af` (псевдо-версия от 2026-03-01, свежее тега).
- Доступные HelloChrome: 58..120, **131, 133**. Потолок = **133**.
- **Upstream master utls ТОЖЕ потолок 133** (HelloChrome_Auto=133, 135/140 НЕ существуют) — проверено
  через github. «Догнать вверх» через стандартный utls СЕЙЧАС НЕВОЗМОЖНО.
- Юзер: **Firefox/Safari НЕ использовать** — РКН их банит в первую очередь, держится только Chrome.
  → diversity ТОЛЬКО внутри Chrome (разные версии), НЕ межбраузерная. Упрощает lockstep, снимает риск.

### Реалистичные варианты FP-diversity (Chrome-only, потолок 133)
1. **Смешать Chrome 120/131/133** (что есть в utls) в реалистичной пропорции → убирает «100% идентичный
   133» кластер. Но: все три УЖЕ устаревшие (133 — самый свежий доступный), реальная популяция в 2026
   на Chrome 14x. То есть diversity поможет от кластер-сигнала, но НЕ от «устаревший» сигнала.
2. **Форк utls + добавить HelloChrome_14x** (как mieru форкали sing-box, memory decisions-2026-05-08).
   Единственный путь к СВЕЖЕМУ fingerprint. Дорого в поддержке (догонять каждый Chrome вручную: cipher
   list, extensions order, H2 SETTINGS, GREASE). Но это «лучше чем у других» — мало кто форкает utls
   ради свежака. РИСК: неточный форк = УНИКАЛЬНЫЙ fingerprint = хуже чем честный старый 133.
3. **Гибрид:** diversity на 120/131/133 сейчас (быстро) + параллельно форк-исследование на свежий Chrome.

**Открытый вопрос для research:** что для TSPU бОльший сигнал — (а) одинаковый FP с разных гео на 1 IP,
или (б) устаревший FP? Если (а) доминирует — diversity 120/131/133 уже сильно помогает. Если (б) —
нужен форк на свежак. Юзер считает оба фактора реальными → вероятно нужен гибрид.

## Тема: АРХИТЕКТУРА ПУЛА vs DPI (болталка 2026-06-05)

### Зачем пул, а не 1 соединение (зафиксировано)
- Параллелизм: 1 WS = 1 TCP; если TSPU стопорит TCP — встают ВСЕ его стримы. Пул размазывает риск.
- Ротация без обрыва: рез стареющего слота + миграция стримов на свежий слот пула (наш age-fix
  работает ТОЛЬКО благодаря пулу — есть куда мигрировать).
- Маскировка: реальный Chrome держит ~6 параллельных соединений к хосту (HTTP/1.1 cap 6 + поддомены).
  6-8 WS ≈ похоже на браузер.

### 🔴 ПРОБЛЕМА (потенциальный кластер-сигнал, пересекается с FP-темой)
- В полевых логах `alive` доходил до **16** WS (uniform-cells = 2×poolSize при перетряхивании под
  нагрузкой/частой ротации). **Браузер НЕ держит 16 параллельных вечных WS к одному IP.** Для DPI,
  смотрящего на агрегат — аномалия: «16 долгоживущих WebSocket к голому IP с одного клиента».
- **Конфликт с нашим же age-fix:** агрессивная ротация (6s stagger, рез 75s) → больше реконнектов →
  пул раздувается → больше параллельных WS → сильнее торчим. Тонкий trade-off (как sticky vs age-window).
- **Для research:** (1) сколько параллельных соединений реальный Chrome держит к одному origin в 2026
  (HTTP/1.1 vs H2 multiplexing — H2 это 1 conn с мультиплексом!). (2) не лучше ли МЕНЬШЕ слотов с H2-style
  мультиплексом внутри, чем 8-16 WS. (3) кап на max alive (не раздуваться выше browser-realistic ~6-8).

### Масштабируемость (открытые вопросы для нагрузочного исследования)
- Нагрузка на pl1 от ротации: частый рез × N юзеров = реконнект-шторм (CPU handshake X25519 + memory
  per-conn). Сейчас тестим 1 клиента — поведение при 100+ юзерах неизвестно. max_clients=500 на pl1.
- Rate-limit per-IP мы подняли (90/120) — но это per-IP; при 100 юзерах с РАЗНЫХ IP сервер держит
  100×~10 reconnect/min = ~1000/min handshake. Нужен нагрузочный тест pl1.

## 🌟 КЛЮЧЕВАЯ ИДЕЯ: единый арбитр ротации (вместо 4 ручных таймеров) — юзер одобрил

**Наблюдение:** сейчас ротацией управляют 4 НЕЗАВИСИМЫХ таймера, сведённых ВРУЧНУЮ под окно 130с:
`MaxSlotAge` (75s), `DrainHardCap` (30s), `StickyMaxDrainAge` (45s), `staggerStep`+`staggerOffsetCap`
(6s/45s). Каждый — env-флаг, выставленный руками. Стоит TSPU поменять окно — пересводить всё руками.

**Паттерн конфликта (всплыл 3 раза за сессию):** каждая фича честно делает свою работу, но против цели
другой. (1) sticky защищает закачку → держит слот живым → слот замерзает TSPU. (2) пул даёт
отказоустойчивость → 16 параллельных WS → кластер-сигнал. (3) ротация спасает от заморозки → шторм
реконнектов → нагрузка + раздувание. Признак системы, выросшей слоями (Bug#6/8/9/10 + age-freeze) —
каждый слой локально прав, но ГЛОБАЛЬНОГО АРБИТРА нет.

**Решение (одобрено юзором «да, это правильный путь»):** единый компонент, который ИЗМЕРЯЕТ реальное
окно заморозки (медиана slot_age при age-cut) и АВТОМАТИЧЕСКИ сводит все таймеры под него — вместо
ручного баланса env. Это и есть «адаптивная ротация» из детектора DPI, поднятая до архитектурного
принципа. Переход от «набор костылей под known-TSPU» к «система, подстраивающаяся под unknown-TSPU».

**Подход (осторожно — критичный путь, риск Bug#6/8/9/10):** НЕ переписывать 4 таймера сразу. Сначала
клиент ИЗМЕРЯЕТ окно и логирует/репортит (пассивно), потом арбитр начинает СВОДИТЬ производные таймеры
(DrainHardCap/sticky/stagger) от одного измеренного «freeze window», оставив их override-able env как
страховку. MaxSlotAge = freezeWindow × safety (напр. 0.6). Остальные — производные.

## Прочее из болталки
- Текущий фикс age-tuning по полевым тестам: 1ГБ файлы качаются, чат держится, downlink write error=0,
  reader error 21→5, decrypt_fails=0. Остаточный хвост — единичные слоты под нагрузкой чуть за 130с
  (без потерь). Возможно дожать sticky/MaxSlotAge — решается по длинному тесту.
