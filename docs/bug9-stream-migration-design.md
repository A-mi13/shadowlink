# Bug #9 — Дизайн миграции стримов между WS-слотами (ИССЛЕДОВАНИЕ, не реализация)

Дата: 2026-05-31. Статус: ГОТОВО (разбор кода завершён).

Цель: ответить можно ли реализовать прозрачную миграцию активных стримов с умирающего
WS-слота (close 1006 по возрасту, рез middlebox/TSPU к голому origin 104.222.177.67, direct
без CF) на живой слот так, чтобы TCP-соединение приложения НЕ рвалось. Перепроверить
утверждение прошлого ревью что это "архитектурно неустранимо без редизайна".

**TL;DR:** Прошлое ревью ПОДТВЕРЖДАЕТСЯ кодом. Прозрачная миграция активного стрима БЕЗ
обрыва приложения **невозможна по текущей архитектуре** и требует server-side изменения
(вариант A: relay survival по (clientID, streamID)). Это единственный вариант, дающий настоящую
прозрачность; объём L–XL, изменение протокола, риск анти-DPI и сложности. Реалистичный
ближнесрочный максимум — вариант B+C гибрид (pre-emptive client migration по возрасту слота +
честный retry для коротких запросов), который УМЕНЬШАЕТ частоту обрывов, но НЕ гарантирует
прозрачность для долгого стрима, который средняя сессия держит дольше порога.

---

## (A) Как стрим привязан к слоту/сессии СЕЙЧАС (файл:строка)

### Клиентская сторона

1. **Стрим жёстко пинится к слоту при создании.** `client/stream_entry.go:18-30` —
   `streamEntry{slotIdx int; lastWriteNs atomic.Int64}`. Комментарий 15-20: *"slotIdx is set
   once at construction by newStreamEntry and never mutated thereafter"*. Поле `slotIdx`
   неизменяемо.

2. **`AssignStream`** (`client/ws_pool.go:2244-2330`) выбирает наименее загруженный ready-слот
   и сохраняет `streamMap[streamID] = newStreamEntry(minIdx)`. Привязка задаётся ОДИН раз.

3. **Все операции стрима маршрутизируются ТОЛЬКО на его слот:**
   - `WriteMessageForStream` (`ws_pool.go:2457-2476`): читает `e.slotIdx`, пишет на
     `slots[idx].transport`. Принимает slotReady И slotDraining.
   - `WriteControlMessageForStream` (2485-2504), `TryWriteControlMessageForStream` (2510+).
   - `SessionForStream` (2427-2439): возвращает `slots[idx].session`.

4. **КЛЮЧЕВОЕ ОГРАНИЧЕНИЕ — крипто-сессия per-slot, НЕ per-client.**
   `ws_pool.go:2421-2439` (docstring SessionForStream): *"The old 'fallback to first primary's
   session' path was removed ... it produced silent decrypt failures (server keys sessions
   per-slot)"*. И `ws_pool.go:2444-2452`: *"once a stream has been assigned to a slot, its crypto
   session lives on THAT slot's transport ... Falling back to a random ready slot here would route
   the frame through a different crypto session, and the server would fail to decrypt (different
   per-slot session key)"*.

5. **Каждый слот делает СВОЙ handshake → СВОЯ сессия.** `connectSlot`/handshake
   (`ws_pool.go:1695-1746`): `core.NewClientHello(clientID, serverPub)` → `SendHandshake` →
   `core.CompleteHandshake` → `slot.session = session` (1746). У каждого слота свой `session.ID`,
   свои SendKey/RecvKey. Keepalive (1629), FIN (1672) — все на `slot.session`, явный комментарий
   1628: *"Each slot has its own crypto session — must use slot.session, not global client session."*

6. **Смерть слота закрывает per-stream каналы → приложение рвётся.**
   `handleSlotDeath` (`ws_pool.go:3050-3127`): для каждого стрима этого слота
   `p.streamMap.Delete(streamID)` + `close(cl.streamChans[streamID])` (3073-3078). На клиентском
   relay (`proxy/socks5/tcp.go:729-733`) закрытый `incomingCh` → downlink goroutine выходит с
   логом *"downlink done (ch closed)"* → `cancel()` → весь relay рвётся → `conn` (app TCP) закрыт.
   Это и есть 371× "downlink done (ch closed)" из находки.

### Серверная сторона

7. **Tunnel keyed by session.ID (per-slot), не по clientID.** `server/handler.go:68`
   `tunnels map[uint32]*Tunnel`; создаётся `h.tunnels[session.ID] = tunnel` (585). У `Tunnel`
   есть поле `ClientID string` (105) — но оно используется только для cleanup-учёта
   (`OnSessionDestroyed`), НЕ для маршрутизации стримов.

8. **TCP-соединение сервер→destination живёт В scope WS-conn'а и умирает с ним.**
   В WS-пути `runWebSocketSession` (`server/websocket.go:498-966`):
   - `streams := make(map[uint16]*wsStream)` — **локальная переменная** функции (523), НЕ на
     Tunnel. Каждый `wsStream` оборачивает диалнутый `tc net.Conn` (TCP к dest) — `s.Activate(tc)`
     (756).
   - Per-stream relay goroutine привязывает `tc.Close()` к `<-done` (766-784): `done` — это
     локальный канал, закрываемый `closeDone()` когда reader ИЛИ writer WS-conn'а выходит
     (537, 590). Reader выходит при close 1006 (593-614, "WS reader exit").
   - Финал функции (`websocket.go:946-953`): `<-done` → цикл `for _, s := range streams { s.Close() }`
     → **все TCP-к-dest закрываются**.
   - Вывод по вопросу 3: **TCP сервер→dest НЕ переживает смерть WS-слота. Сервер его НЕ держит и
     не может переподключить к новому слоту — он уничтожается синхронно с WS-conn'ом.**

9. **Server-side client-identity ЕСТЬ, но не используется для relay.** `server/ratelimit.go:188-195`
   `OnSessionCreated`: `activeSessions[userID] = append(..., sessionID)` и
   `clientSession[clientID] = sessionID`. Т.е. сервер ЗНАЕТ что несколько сессий принадлежат
   одному clientID. Но это только для device-limit/cleanup. Нет привязки relay/TargetConn к
   clientID — relay живёт под `session.ID` и под scope конкретного WS-conn'а (см. п.8).

10. **Optimistic CONNECT + PendingBuf уже есть** (`handler.go:95-100` StreamConn,
    `websocket.go:662-668` newPendingWSStream). Это инфраструктура буферизации данных ДО
    готовности dest — полезна для варианта A (re-CONNECT может буферизировать догоняющие байты),
    но сама по себе миграцию не делает.

## (B) Возможна ли прозрачная миграция — разбор вопросов 1-5

**Вопрос 1 (привязка стрим→слот):** стрим пинится к слоту один раз (`streamEntry.slotIdx`,
неизменяем), все write/session-операции идут только на этот слот. Физически стрим НЕ может идти
через другой слот без смены `slotIdx` И смены крипто-сессии (другой ключ). См. A.1-A.4.

**Вопрос 2 (stream на уровне протокола):** `streamID` (uint16) — **per-session**, не глобальный.
И на клиенте, и на сервере streamID живёт в рамках ОДНОЙ core.Session (одного WS-conn). Сервер:
`streams map[uint16]*wsStream` локален per-WS-conn (`websocket.go:523`). FlagConnect/FlagData
парсят streamID из payload, который зашифрован per-session ключом. При смерти слота сервер теряет
relay (см. A.8) — подтверждено.

**Вопрос 3 (KEY — переживает ли TCP→dest смерть слота):** **НЕТ.** TCP к dest (`tc`) закрывается
по `<-done` (WS-conn-scoped) в каждой relay-goroutine и в финальном cleanup
(`websocket.go:780-781, 946-953`). Сервер не держит его независимо и не имеет API
"продолжить stream N на новой сессии". Это **определяющий блокер** прозрачной миграции: чтобы
приложение не порвалось, egress-TCP должен пережить смену WS-conn'а — сейчас он не переживает.

**Вопрос 4 (client-identity поверх слотов):** ЕСТЬ на сервере (`activeSessions[userID]`,
`clientSession[clientID]`, `ratelimit.go:188-195`) и на клиенте (один `clientID`, все слоты
хендшейкуют им). НО relay привязан к session.ID, не к clientID. Перенести relay между сессиями
одного clientID СЕЙЧАС невозможно — нет ни хранилища relay по clientID, ни протокольного
сообщения "реассоциируй stream N сессии X на сессию Y".

**Вопрос 5 (handleSlotDeath / pre-emptive):**
- `handleSlotDeath` (`ws_pool.go:3050`) сейчас просто `close(ch)` всем стримам слота → они
  умирают (A.6). Миграции нет.
- Graceful drain (`ws_pool_drain.go:343-713`) — это НЕ миграция. Он: CAS slotReady→slotDraining,
  поднимает РЕЗЕРВНЫЙ слот в свободной ячейке, **НОВЫЕ** стримы (AssignStream) идут на резерв, а
  **СТАРЫЕ остаются на draining-слоте и доигрывают на ЕГО сессии**. Если старый стрим не
  закончился к hard-cap/sticky-backstop → `tearDown` → `handleSlotDeath(deathCauseDrainTeardown)`
  → те же `close(ch)` → обрыв (`drain.go:636`, `3115-3125`). Существующие стримы drain НЕ
  переносит на другой слот — он лишь даёт им доиграть на месте.
- Pre-emptive миграция ДО реза (по возрасту слота) **технически невозможна без server-side
  поддержки**: даже если клиент в age=60с захочет перевести стрим на свежий слот, новый слот =
  новая сессия с новым session.ID; серверный relay (TCP→dest) старого стрима живёт под старой
  сессией и в старом WS-conn'е. Клиент не может "перенести" этот relay — он может только открыть
  НОВЫЙ CONNECT к тому же dest на новом слоте (новый egress-TCP к dest — это разрыв TCP-сессии
  приложения↔dest со стороны dest; для stateful-протоколов = обрыв).

**Итог B:** прозрачная миграция активного стрима **невозможна по текущей архитектуре**. Корневой
блокер — egress-TCP сервер→dest жёстко привязан к жизни одного WS-conn'а (A.8 / вопрос 3). Любой
вариант с настоящей прозрачностью обязан сделать egress-TCP переживающим смену WS-conn'а и
переассоциируемым по client-identity → это server-side редизайн (вариант A). Прошлое ревью верно.

## (C) Варианты A–D с trade-off, объёмом, рисками

### Вариант A — Server-side relay survival (единственный ПРОЗРАЧНЫЙ)

**Идея.** Развязать жизнь egress-TCP (`tc`→dest) от жизни WS-conn'а. Хранить relay'и в
долгоживущем реестре по ключу **(clientID, streamID)**, а не в локальной `streams`-мапе
`runWebSocketSession`. При смерти WS-слота relay НЕ закрывается: входящие/исходящие байты
буферизуются (PendingBuf + bounded downlink-буфер). Клиент на новом слоте (новая сессия того же
clientID) шлёт control-frame `RESUME stream=N` → сервер по (clientID, N) находит живой relay и
переподключает его I/O к новому WS-conn'у/сессии. Downlink, накопленный за окно реконнекта,
дослаивается. Приложению↔dest TCP не рвётся — egress-TCP жив всё время.

**Что нужно:**
- Сервер: реестр `map[clientID]map[streamID]*relay` (или `map[streamID]` под client-scope),
  переживающий WS-conn. Relay-goroutine отвязать от `done` конкретного WS-conn'а; жизнь
  привязать к (a) FIN от клиента, (b) EOF от dest, (c) grace-таймауту без активного WS-conn'а
  (напр. 30–60с — "клиент переезжает"). Bounded-буфер downlink на время отсутствия WS-conn'а
  (риск памяти — нужен лимит + drop-to-FIN при переполнении).
- Протокол: новый control-flag `RESUME` (streamID + доказательство владения). Поскольку у каждой
  сессии свой ключ, клиент должен доказать что он тот же clientID и владеет stream N — иначе
  hijack. Привязать к clientID-аутентификации хендшейка + HMAC/токен стрима.
- seq-num/replay: relay переезжает на НОВУЮ сессию → новый ключ, новые seq. Per-stream порядок
  данных надо сохранить (downlink буфер дослать в порядке) — добавить per-stream sequence поверх
  session-seq, иначе при переезде возможны дыры/дубли. Это самое тонкое место.
- Клиент: при `handleSlotDeath` НЕ закрывать streamChans сразу — пометить стримы слота как
  "migrating", AssignStream их на живой слот, послать RESUME, продолжить relay поверх нового
  слота. Re-CONNECT семантика replaced на RESUME.
- WSAttached-гейт (`handler.go:116-122`, single WS per session) надо переосмыслить — теперь relay
  переживает несколько WS-conn'ов последовательно.

**Trade-off / риски:**
- Прозрачность: ✅ полная (включая долгий тихий стрим агента — главный кейс находки).
- Анти-DPI: RESUME-фрейм неотличим от обычного зашифрованного data-фрейма (всё внутри
  AES-GCM body-prefix) — НЕ создаёт нового wire-signal, если не вводить отдельную длину/тайминг.
  ⚠️ Но переезд = новый хендшейк нового слота РОВНО в момент реза старого → корреляция "старый
  слот close 1006 → через ~Xс новый хендшейк того же IP". Это уже происходит сейчас (reconnect),
  так что не хуже; но если миграция массовая, всплеск хендшейков синхронен с резами → надо
  jitter (как NEW-1).
- Память: реестр живых relay + downlink-буферы на время реконнекта → DoS-поверхность (клиент
  открыл много стримов, исчез — сервер держит TCP+буферы grace-окно). Нужны лимиты на
  clientID, метрики, eviction. Сейчас при WS-смерти всё чистится мгновенно — это свойство теряем.
- Безопасность: RESUME без строгой привязки к clientID = stream hijack. Критично.
- Объём: **L–XL.** Затрагивает server/websocket.go (вынос streams в долгоживущий реестр, отвязка
  от done, grace-lifecycle), server/handler.go (реестр, RESUME-обработка, лимиты), core (новый
  flag + per-stream sequence), client/ws_pool.go + proxy/socks5/tcp.go (migrating-state вместо
  close, RESUME-отправка, re-bind relay). Плюс TDD + race + канарейка. По масштабу ≈ Bug#6+Bug#8
  вместе взятые.
- Совместимость: протокол меняется → нужен флаг и staged deploy сервера-первым (как обычно).

### Вариант B — Pre-emptive client migration (без A — НЕ прозрачен)

**Идея.** Клиент по возрасту слота (напр. age>50–60с, до порога реза ~1–4мин) превентивно
"эвакуирует" стримы: открывает новый слот и переоткрывает стрим к тому же dest на нём.

**Реальность по коду:** без варианта A это сводится к **новому CONNECT** к dest на новой сессии
→ сервер диалит **новый** egress-TCP к dest → со стороны dest старое TCP-соединение приложения
рвётся (новый сокет, другой source). Для stateless коротких HTTP-запросов, ещё не начавших
ответ, — ок (см. C). Для долгого стрима (агент держит один HTTP-ответ/SSE, видео-сокет,
закачка) — это **обрыв**, замаскированный под "плановый". Т.е. B без A = не решает находку
(тихий долгий стрим агента именно и рвётся).

Частичная польза B: graceful drain УЖЕ делает похожее для НОВЫХ стримов (резерв-слот). Расширение
"drain по возрасту раньше" уменьшает шанс что слот срежут с активными стримами на борту, но
sticky-backstop всё равно рвёт те что не доиграли. **Объём S–M** (тюнинг порогов drain + раньше
стартовать drain), но потолок эффекта низкий для целевого кейса.

**Trade-off:** прозрачность ❌ для долгих; анти-DPI — больше хендшейков раньше (нужен jitter);
риск — преждевременные drain'ы повышают reconnect-rate (CF/origin rate-limit, ghost-сессии).

### Вариант C — Мягкая деградация: быстрый reconnect + retry коротких запросов

**Идея.** Не мигрировать, а: (1) сократить backoff реконнекта (сейчас 5–9с — на это время стримы
висят без слота, находка стр.22-27); (2) для идемпотентных/коротких запросов, где ответ ещё НЕ
начал течь, прозрачно повторить CONNECT+запрос на живом слоте (HTTP-level retry).

**Реальность по коду:** retry возможен только ДО получения первого байта downlink
(`connectConfirmed`/первый data во `tcp.go:736-762`). После начала ответа повтор = дубликат/обрыв.
tun2socks (system VPN) вообще не знает семантики запроса — там retry на уровне приложения, не наш.
Так что C покрывает короткие HTTP к новым стримам, НЕ долгий стрим агента.

**Trade-off:** прозрачность ❌ для долгих, ✅ только для коротких idempotent; анти-DPI нейтрально;
объём **S** (backoff-тюнинг + узкий retry-гейт). Честный предел: НЕ закрывает находку, но
уменьшает фоновые обрывы и "no ready slot" окна.

### Вариант D — что ещё найдено в коде

- **D1. Увеличить poolSize / per-slot lifetime jitter** — паллиатив, не миграция. Больше слотов =
  меньше вероятность что ВСЕ срежутся разом, но конкретный стрим всё равно умирает со своим слотом.
- **D2. Резко учащённый keepalive на слотах со стримами** — находка уже показала: рез по ВОЗРАСТУ,
  не по молчанию (обновление 2026-05-31, 58× реза на active слотах). Keepalive НЕ лечит. Отвергнуто
  самой находкой.
- **D3. Принудительная ротация слота по возрасту с pre-CONNECT дубликатом стрима к dest** (hot
  spare на уровне dest) — для большинства dest невозможно (две TCP-сессии к одному dest = два
  разных состояния приложения). Только для специальных идемпотентных загрузок. Не общий.

## (D) РЕКОМЕНДАЦИЯ

**Если цель — буквально "никаких обрывов" для долгого тихого стрима агента (как просил юзер) —
ЕДИНСТВЕННЫЙ путь это Вариант A (server-side relay survival по (clientID, streamID) + RESUME).**
Это совпадает с выводом прошлого ревью: дешевле/локального решения нет, потому что корневой блокер
архитектурный — egress-TCP сервер→dest привязан к жизни одного WS-conn'а (A.8). Любая попытка
"перевесить" стрим на клиенте без переноса серверного relay = новый egress-TCP = обрыв TCP
приложения↔dest. Поэтому B и C физически НЕ дают прозрачности для долгого стрима.

**Что требует A:** долгоживущий per-(clientID,streamID) реестр relay на сервере с grace-окном и
bounded-буфером; новый зашифрованный control-flag RESUME с доказательством владения стримом;
per-stream sequence для бесшовной дослойки downlink; client-side migrating-state вместо close(ch);
лимиты+метрики+eviction против DoS памяти; jitter на хендшейках переезда; staged deploy
сервера-первым + канарейка. Объём **L–XL**, протокол меняется.

**Рекомендованный порядок действий (риск-aware, по урокам Bug#8/Bug#6):**
1. Сначала **измерить долю кейсов, которые A реально спасает vs B/C**: сколько из 371 "ch closed"
   — это долгие стримы > порога реза (которые B не спасёт), а сколько короткие (которые спасает
   дешёвый C). Метрика: возраст стрима и наличие downlink-активности в момент close(ch). Если
   большинство — короткие, дешёвый C+B даёт почти весь выигрыш за S-M.
2. Параллельно дешёвый слой **C+B** (S-M): сократить reconnect backoff на тихих слотах, узкий
   prozрачный retry для pre-first-byte стримов, раньше стартовать graceful drain по возрасту.
   Это снижает фон обрывов и "no ready slot" немедленно, без протокольных рисков.
3. Только если шаг 1 показал, что значимая доля — ДОЛГИЕ стримы (агент/видео/большая закачка), —
   проектировать **A** полноценно (спека → опус-ревью → subagent-driven TDD → канарейка), как
   делали Bug#6/Bug#8. Не клепать: A трогает крипто-сессии, seq-num и DoS-поверхность — три
   области с историей тонких багов в этом проекте.

## (E) Если прозрачная миграция невозможна без большого редизайна — максимум достижимого

Подтверждено: прозрачная миграция активного стрима **невозможна без server-side редизайна
(вариант A, L–XL, изменение протокола)**. Честный максимум БЕЗ A:

1. **Короткие/idempotent стримы (pre-first-byte): прозрачный retry на живом слоте** (вариант C).
   Покрывает HTTP-запросы агента, которые ещё не начали получать ответ, и любые SOCKS-CONNECT,
   срезанные до CONNECT_OK. Объём S. Это уберёт заметную часть "ch closed", где ответ ещё не пошёл.
2. **Сокращение окна без слота** (вариант C): меньший reconnect backoff (сейчас 5–9с) на тихих
   слотах + резерв-слот наготове, чтобы "no ready slot" (находка: 7–11×) почти исчезли.
3. **Pre-emptive drain по возрасту раньше** (вариант B): начинать drain слота в age≈50–60с, чтобы
   к моменту реза на нём было меньше активных стримов. Не спасает уже-идущий долгий стрим, но
   снижает число жертв на рез. Объём S-M, осторожно с reconnect-rate.
4. **Что НЕ поможет (зафиксировать, чтобы не тратить время):** учащённый keepalive (рез по
   возрасту, не молчанию — доказано находкой), увеличение буферов, увеличение poolSize — всё
   паллиативы, конкретный долгий стрим всё равно умирает со своим слотом.

**Граница честности:** долгий тихий стрим AI-агента (один HTTP-ответ/SSE, держится 5+ минут —
дольше порога реза ~1–4мин) БЕЗ варианта A прозрачно сохранить НЕЛЬЗЯ. Его egress-TCP на сервере
умрёт со слотом, и переоткрытие = обрыв со стороны dest. Это ровно тот кейс, на который жаловался
юзер ("на долгих ожиданиях обрывы и не восстанавливается"). Поэтому: либо принять A (редизайн),
либо принять, что этот конкретный кейс остаётся (с уменьшенной, но ненулевой частотой обрывов
после шагов 1–3).
