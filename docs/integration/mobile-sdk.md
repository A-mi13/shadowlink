# ShadowLink Mobile SDK — Integration Guide

Audience: Android/Kotlin and iOS/Swift developers integrating the `mobile/`
gomobile facade. You do not need to read the Go source or the design spec.

Source of truth for this document: `mobile/config.go`, `mobile/session.go`,
`mobile/callbacks.go`, `engine/engine.go`, `client/ws_pool.go` (repo
`github.com/nixavpn/shadowlink`, tag `v0.2.0`). Every API name below was taken
from the Java API generated by `gobind -lang=java` on 2026-08-24, not from
prose.

**Verification legend used throughout**

| Mark | Meaning |
|---|---|
| VERIFIED | Read in the shipped Go source and/or in the generated Java API |
| BUILT | An artifact was actually produced on the dev machine |
| UNVERIFIED | Not built, not measured, not run — stated as unknown, not as fact |

---

## 1. What the SDK is, and what it is not

The SDK gives you **a local SOCKS5 proxy on `127.0.0.1`**, backed by the
ShadowLink transport (WebSocket pool over TLS to a bare origin IP). That is the
whole API boundary.

It does **not**:

- create or manage a TUN device (`VpnService` / `NEPacketTunnelProvider` is yours),
- move packets from TUN into the proxy (you supply tun2socks or equivalent),
- configure DNS,
- protect against DNS or IPv6 leaks,
- observe network changes (you must tell it — see §7),
- persist any identity or state on its own (you supply the directory and the ID).

The Go side deliberately stops at the proxy socket. Everything on the list above
is platform work you must do.

## 2. Quick start (Android / Kotlin)

```kotlin
import mobile.Config
import mobile.EventHandler
import mobile.Logger
import mobile.Mobile
import mobile.Session

class ShadowLinkTunnel(private val ctx: android.content.Context) {

    private var session: Session? = null

    fun start(serverAddr: String, pubKeyHex: String, sni: String) {
        // Global, process-wide. Optional. See §5.3.
        Mobile.setLogLevel("info")
        Mobile.setLogger(object : Logger {
            override fun log(level: String, msg: String) {
                // NOT on the UI thread. Never throw. Never block. See §6.
                android.util.Log.println(android.util.Log.INFO, "shadowlink", "$level $msg")
            }
        })

        val cfg = Mobile.newConfig()          // or: Config()
        cfg.serverAddr = serverAddr           // "1.2.3.4:443" — host:port, required
        cfg.pubKeyHex  = pubKeyHex            // 64 hex chars, required
        cfg.sni        = sni                  // TLS ServerName
        cfg.useTLS     = true
        cfg.clientIDHex = loadOrCreateClientId()   // 32 hex chars, PERSISTED by you — §8.3
        cfg.stateDir    = ctx.filesDir.absolutePath // §8.4
        // cfg.wsPoolSize = 8                 // leave 0 unless you have a measurement

        // Throws on invalid config (bad hex, missing port). Does not touch the network.
        val s = Session(cfg)
        s.setEventHandler(object : EventHandler {
            override fun onStateChange(state: String) { /* §6 rules apply */ }
            override fun onError(msg: String) { }
        })

        // Blocks until the SOCKS5 listener is up (not until the pool is full).
        // Must NOT be called on the UI thread.
        s.start()

        val port = s.socksPort()   // Int, non-zero after a successful start()
        val user = s.socksUser()   // "nix"
        val pass = s.socksPass()   // 32 hex chars, regenerated per Session

        session = s
        startVpnService(port, user, pass)
    }

    fun stop() {
        session?.stop()   // destroys the engine; a later start() builds a new one
        session = null
        Mobile.setLogger(null)   // REQUIRED — see §6.4
    }
}
```

Then wire the proxy into your `VpnService`:

```kotlin
val builder = Builder()
    .setSession("ShadowLink")
    .addAddress("10.0.0.2", 32)
    .addRoute("0.0.0.0", 0)
    .addDnsServer("1.1.1.1")        // MANDATORY — §8.1
    .addDisallowedApplication(packageName)   // don't route ourselves through ourselves
val tunFd = builder.establish()
// Hand tunFd + ("127.0.0.1", port, user, pass) to your tun2socks engine.
```

Register a `ConnectivityManager.NetworkCallback` and call
`session.networkChanged()` from it — see §8.2. Without it the tunnel stalls for
tens of seconds after every Wi-Fi↔LTE switch.

## 4. API reference — `Config`

Fields are plain Kotlin properties (`cfg.serverAddr = …`).

| Field | Type | Required | Semantics |
|---|---|---|---|
| `serverAddr` | `String` | **yes** | `"host:port"`. In production this is a bare origin IP; the domain goes in `sni`. Must parse as host:port. |
| `pubKeyHex` | `String` | **yes** | Server X25519 public key, exactly 64 hex chars (32 bytes). |
| `clientIDHex` | `String` | no, but see §8.3 | Exactly 32 hex chars (16 bytes) if set. Empty ⇒ the engine generates a fresh random UUID **on every `start()`**. Opaque to the SDK. |
| `sni` | `String` | in practice yes | TLS ServerName used when dialing the IP in `serverAddr` (full-direct mode). |
| `cdn` | `String` | no | Legacy URL-format compatibility. Production is direct-to-origin. |
| `useTLS` | `boolean` | yes in production | Disable only in lab setups. |
| `wsPoolSize` | `int` | no | Number of WS pool slots. `0` ⇒ engine default **8** (VERIFIED, `engine/engine.go`). Negative ⇒ validation error. Do not change without a measurement (see §11). |
| `stateDir` | `String` | strongly recommended | App-private directory for persistent fingerprint state (`fp-state.bin`). Empty ⇒ the TLS fingerprint profile is re-picked on every start, which is a detectable drift. |

### 4.1 Methods

```java
void   addBypass(String pattern)         // e.g. "*.example.com"
void   setRouting(String spec) throws Exception
```

`setRouting` takes a JSON string (gomobile cannot pass string slices or nested
structs):

```json
{"bypass":["*.ru","*.рф"],"block":["ads.example"],"force":["*.example.com"]}
```

Only these three keys exist (VERIFIED: `client.RoutingConfig` has exactly
`bypass`, `force`, `block`). An empty/whitespace string clears routing.
Malformed JSON throws immediately, from `setRouting` — not later from `start()`.

Note: the engine **always** merges a built-in bypass list for CIS TLDs
(`*.ru`, `*.рф`, `*.su`, `*.by`, `*.kz`, `*.ua`, `*.am`) on top of yours, and
there is no way to disable it (VERIFIED, `engine/engine.go`). Your rules are
evaluated first and effectively override on conflict.

### 4.2 Validation and exact error messages

Validation runs in the `Session` constructor (`NewSession`), synchronously, and
throws. Messages are Russian in the current build — match on behaviour, not on
text.

| Condition | Message |
|---|---|
| `cfg` is null | `session: config is nil` |
| empty `serverAddr` | `config: ServerAddr не задан` |
| `serverAddr` not `host:port` | `config: ServerAddr должен быть host:port: …` |
| `pubKeyHex` not hex | `config: PubKeyHex не hex: …` |
| `pubKeyHex` wrong length | `config: PubKeyHex должен быть 32 байта (64 hex), получено N` |
| `clientIDHex` not hex | `config: ClientIDHex не hex: …` |
| `clientIDHex` wrong length | `config: ClientIDHex должен быть 16 байт (32 hex), получено N` |
| `wsPoolSize < 0` | `config: WSPoolSize отрицательный: N` |

VERIFIED in `mobile/config.go`.

### 4.3 Config is snapshotted

`Session(cfg)` takes a deep copy. Mutating the `Config` object afterwards has no
effect on that session, including across a `stop()`/`start()` cycle. To change
parameters, build a new `Config` and a new `Session`.

### 4.4 What the facade forces, regardless of your config

`websocket` and `ws_pool` are hard-enabled (VERIFIED, `mobile/config.go`).
`SystemVPN` is hard-disabled — the TUN is yours. This is not a default you can
override, and that is intentional: without the pooled WS transport the data path
falls back to 20 ms polling tickers, which puts a 50 Hz timing signature on the
wire plus one encrypted frame per tick.

## 5. API reference — `Session`

```java
Session(Config cfg) throws Exception   // = Mobile.newSession(cfg)
void   start() throws Exception
void   stop()  throws Exception
String state()
int    socksPort()
String socksUser()
String socksPass()
void   networkChanged()
void   setEventHandler(EventHandler h)
```

### 5.1 Methods

| Method | Blocking? | Contract |
|---|---|---|
| `start()` | **yes** — until the SOCKS5 listener is bound, not until the pool is full | Idempotent in `connecting`/`connected`/`degraded` (returns without doing anything). From `idle` or `failed` it builds a **new** engine. Never call from the UI thread. |
| `stop()` | yes, bounded | Idempotent; safe before the first `start()`; safe to call twice. Destroys the engine. |
| `state()` | **never blocks** | Safe from the UI thread, safe during `start()`. Backed by an atomic, not by the mutex. |
| `socksPort()` | never blocks | `0` before `start()`, during connect, and after `stop()`. The actual kernel-assigned port otherwise. |
| `socksUser()` / `socksPass()` | never blocks | Fixed for the lifetime of the `Session`. Available before `start()`. |
| `networkChanged()` | non-blocking in practice | Safe from the UI thread. No-op before `start()` / after `stop()`. |
| `setEventHandler(h)` | non-blocking | `null` detaches and releases the Java reference. |

`socksPort()` is a *real* ephemeral port: the facade binds `127.0.0.1:0`, because
any fixed port (1080 included) may be taken by another VPN app on the device.
Read it after `start()` returns; do not hardcode.

### 5.2 States and transitions

| State | Meaning |
|---|---|
| `idle` | No engine. Initial state, and the state after `stop()`. |
| `connecting` | `start()` is in flight. |
| `connected` | SOCKS5 listener is up **and** the pool has ≥1 ready slot. |
| `degraded` | The listener is still up, but the pool has had **0 ready slots for ≥15 s**. Traffic is not flowing. |
| `failed` | `start()` failed, or the engine emitted its single fatal error. |

```
idle ──start()──▶ connecting ──ok──▶ connected ◀──┐
  ▲                    │                 │        │ ready slots return
  │                    │ error           │ 0 ready slots ≥15s
  │                    ▼                 ▼        │
  └────stop()──── failed ◀──fatal──── degraded ───┘
                    │
                    └──start()──▶ connecting   (allowed: a new engine is built)
```

VERIFIED details that matter:

- The health watcher polls every **5 s** and declares `degraded` after **15 s**
  of zero ready slots. It only runs while the state is `connected`/`degraded`.
- `degraded` → `connected` happens automatically when a slot comes back.
  `degraded` is not terminal and does **not** require a restart.
- `failed` **is** terminal for that engine, but the `Session` object is
  reusable: calling `start()` from `failed` is explicitly allowed and builds a
  new engine.
- `stop()` always lands in `idle`, from any state.
- Repeated identical states are suppressed — `OnStateChange` fires only on
  actual transitions.

### 5.3 Logging

`setLogger` / `setLogLevel` are **process-global**, not per-session. There is no
per-session log level: the underlying `slog` default is a process global, and the
SDK does not pretend otherwise.

Accepted levels: `info`, `quiet`, `warn`, `error`, `debug`, `trace`.
Unrecognised values fall back to `info` — never an error, so a typo in your
settings will not silence the log.

Level filtering happens **before** the JNI boundary (`bridgeHandler.Enabled`,
`mobile/callbacks.go:234`). At `debug` the core emits thousands of lines per
hour; paying a JNI crossing for lines Java would discard is not acceptable, so
the filter sits in the Go handler.

**For production builds use `warn`.** This is the knob for log volume, and it is
the only one — there is nothing else to configure:

- `setLogLevel("warn")` takes effect immediately and costs nothing per suppressed
  line (no JNI crossing, no string formatting on the Java side).
- The SDK does **not** rotate or cap any log file. There is no `lumberjack`, no
  size limit, no backup count anywhere in `cmd/`, `client/`, or `engine/`
  (VERIFIED by grep, 2026-08-31). Whatever your `Logger` writes to, it grows
  without bound until you do something about it. If you persist logs, rotation is
  yours to implement.
- At `info` the volume is dominated by connection lifecycle, not per-stream
  traffic: per-stream relay completions ("uplink done", the four "downlink done"
  variants, "downlink cancelled", "Split CONNECT OK", and their per-stream twins
  — 8 call sites in `proxy/socks5/tcp.go`) were moved from `Info` to `Debug` on
  2026-08-31. Before that change `info` produced on the order of several lines
  per TCP connection, which on a mobile device with a busy app mix reached
  millions of lines per day (reported by an integrator: ~1.9 M lines in 24 h,
  costing battery and disk). Those lines also carried destination addresses.
- At `debug`/`trace` per-stream events come back, including destinations. See
  §9.3.

Level strings delivered to your `Logger.log(level, msg)` are uppercase:
`TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`. Structured attributes are flattened
into the message as `key=value`.

## 6. Callback contract — read this before implementing `Logger` or `EventHandler`

This is the single most dangerous part of the integration.

### 6.1 Which thread

Callbacks arrive on **arbitrary Go goroutines**. Never the UI thread. If your
implementation touches a `View`, you must `Handler.post` / `runOnUiThread`
yourself, or you get `CalledFromWrongThreadException`.

### 6.2 Never throw

An unhandled Java exception inside a callback is a **JNI abort** — the whole
process dies, and it does not surface as a Go error. gobind does not catch Java
exceptions and the Go side cannot protect you from this. Wrap the body of every
callback in `try { … } catch (Throwable) { }`.

### 6.3 Never block

A blocking callback stalls whatever goroutine invoked it. If that goroutine is a
WS slot reader, the slot stops reading and writing; a silent slot gets cut by the
middlebox. The project's conservative silence threshold is **10 s**
(`middleboxSilentCutFloor`, `client/ws_pool.go` — VERIFIED). A slow UI callback
is therefore a way to break the tunnel, not just a way to drop a log line.

### 6.4 What the Go side already does for you

| Protection | Detail |
|---|---|
| Buffered queue | 256-entry channel between core and JNI (`dispatchQueue`) |
| Single dispatcher goroutine | Exactly one goroutine crosses the language boundary; ordering is preserved |
| Non-blocking send | On overflow the event is **dropped and counted**, never blocked. A slow callback delays only other callbacks, never a slot reader |
| Panic recovery | A panic inside the Go-side shim is recovered and counted |
| Pre-JNI level filter | Below-threshold log records never cross the boundary |

VERIFIED in `mobile/callbacks.go`.

The Go side deliberately trades message loss for tunnel liveness: observability
can be dropped, the product cannot.

### 6.5 What is still yours

1. Do not throw. (§6.2 — Go cannot help here at all.)
2. Do not block. Post to a handler/queue and return immediately.
3. Do not assume delivery. Events **can be dropped** under burst; treat
   `OnStateChange` as a hint and `state()` as the truth.
4. Call `Mobile.setLogger(null)` and `session.setEventHandler(null)` when tearing
   down. The logger reference is a **process-global JNI reference**: leaving it
   set keeps your `Activity`/`Context` alive forever — a textbook Android leak.
5. Do not call back into `Session` from inside a callback in a way that can
   block (e.g. `stop()` from `onError` on the same thread). Post it.

## 7. Lifecycle contract

### 7.1 `start()`

- Blocks. On Android call it from a background thread or coroutine dispatcher.
- Returns as soon as the SOCKS5 listener is bound. **Pool readiness is not
  awaited** — the eight slots fan out in the background (measured fan-out span
  2.4 s; a hung handshake can take up to 10 s). Watch `OnStateChange` for
  readiness; `connected` means ≥1 slot is up.
- Idempotent while already up: a second `start()` in `connecting`/`connected`/
  `degraded` is a no-op. It does **not** create a second engine — that would
  double the number of TLS connections to the origin, which is exactly the
  signal the whole rotation design exists to avoid.
- On failure it closes the half-built engine, sets `failed`, emits `OnError`,
  and throws.

### 7.2 `stop()` destroys the engine

`stop()` is not a pause. It cancels the context, closes the pool, the transport
and the client. The engine object is not reusable, and the SDK does not try to
reuse it: **a later `start()` constructs a brand-new engine.** The `Session`
object itself is reusable indefinitely.

Practical consequences:

- `socksPort()` returns `0` after `stop()`, and the next `start()` will almost
  certainly return a **different** port. Re-read it every time.
- `socksUser()`/`socksPass()` do **not** change across `stop()`/`start()` on the
  same `Session` — they are generated once, in the constructor.
- `stop()` holds the same lock as `start()` on purpose, so a
  `stop()`-then-immediately-`start()` sequence (background/foreground) cannot
  overlap two engines.

### 7.3 Backgrounding and process death

- Backgrounding alone changes nothing on the Go side. Android Doze does: the
  rotation and keepalive loops are ordinary goroutines and stop being scheduled,
  so slot ages overrun their budget. Behaviour after a long Doze window is
  UNVERIFIED on device — no field measurement exists for mobile.
- Clock jumps (NTP correction after a long sleep) are not detected. The rotation
  watchdog uses wall-clock nanoseconds, the reader uses a monotonic source; after
  a correction these two disagree. UNVERIFIED impact; no detector exists in the
  code.
- If the OS kills your process without `stop()`, nothing on the Go side runs:
  the pool never sends its session-FIN, and up to `wsPoolSize` **ghost sessions**
  linger on the server until its idle timeout. The server's default session
  timeout is **90 s** (VERIFIED, `server/config.go` `DefaultConfig`), so ghosts
  clear on their own within roughly that window. Call `stop()` from
  `onRevoke()`/`onDestroy()` whenever you get the chance — but do not rely on it.

## 8. What you must implement — the Go side does not

### 8.1 DNS leak protection — mandatory

The SDK contains **no DNS handling at all**. The desktop CLI solves DNS leaks
with a split-DNS forwarder (`client/dnsproxy` + `tunnel.go`), and that code is
deliberately **not** in the mobile dependency tree (VERIFIED by a test that fails
the build if it ever appears).

Therefore, on Android, if you do not call `Builder.addDnsServer(...)`, system DNS
resolution goes around your tunnel. On iOS the equivalent is `NEDNSSettings` on
the tunnel network settings.

This is a missing feature at the SDK boundary, not a bug — but if you skip it,
your product leaks DNS.

### 8.2 `networkChanged()` — mandatory

Call `session.networkChanged()` whenever the OS reports a network change.

```kotlin
val cm = getSystemService(ConnectivityManager::class.java)
cm.registerDefaultNetworkCallback(object : ConnectivityManager.NetworkCallback() {
    override fun onAvailable(network: Network)      { session?.networkChanged() }
    override fun onLost(network: Network)           { session?.networkChanged() }
    override fun onCapabilitiesChanged(n: Network, c: NetworkCapabilities) { /* optional */ }
})
```

iOS: `NWPathMonitor.pathUpdateHandler`.

Why it is not optional: after a Wi-Fi↔LTE switch, all pool slots hold TCP
connections bound to the **old** local address. They do not fail — they **hang**
until the TCP timeout, because nothing sends an RST. Death is noticed only by a
read error or a keepalive timeout, and the reconnect backoff degenerates to
exactly 60 s once the attempt counter reaches 4. Net effect: the tunnel is dead
for tens of seconds while the OS knew about the change immediately.

What `networkChanged()` does (VERIFIED, `client/ws_pool.go`): arms the
post-meltdown spread gate, wakes slots sitting in backoff, and tears down every
live slot so they reconnect — spread out, not as a thundering herd. It
deliberately does **not** reset the backoff ladder when the last failure was a
rate-limit, so it cannot be used to bypass the client's own backoff.

Over-calling is safe (it is idempotent per slot and no-op outside a connection),
but do not call it on a timer — each call tears down live slots.

### 8.3 Persist `clientIDHex`

Generate 16 random bytes **once**, hex-encode them, store them in app-private
storage, and pass the same value on every launch.

```kotlin
fun loadOrCreateClientId(): String =
    prefs.getString("client_id", null) ?: run {
        val b = ByteArray(16).also { java.security.SecureRandom().nextBytes(it) }
        b.joinToString("") { "%02x".format(it) }.also { prefs.edit().putString("client_id", it).apply() }
    }
```

If you leave it empty, the engine generates a fresh UUID on **every** `start()` —
a new client identity every time the app returns from background.

Use a **random** value, not something derived from a user account. The handshake
has no signature; the client ID's unpredictability is part of what stops a MITM
from completing the exchange. A predictable account-derived ID would weaken
server authentication. Treat it as an opaque random token.

### 8.4 Provide `stateDir`

Pass an app-private path (`context.filesDir`). It is where the TLS fingerprint
profile persists. Without it, the profile is re-selected on every launch, and a
fingerprint that drifts between launches is itself a signal.

### 8.5 Everything about the TUN

Creating the interface, routes, MTU, per-app rules, excluding your own package
from the tunnel, and pumping packets from the TUN fd into the SOCKS5 proxy — all
yours. The SDK never sees a packet.

## 9. Security notes

### 9.1 The SOCKS5 port needs the credentials — and you must use them

`socksUser()`/`socksPass()` are generated inside the SDK: user `nix`, password 16
random bytes hex-encoded, fresh per `Session`, never settable from outside (so
nobody can configure a weak or empty one). They do not survive a process restart.

**On Android, a listening `127.0.0.1:PORT` is reachable by any app on the
device.** Without SOCKS5 authentication, any installed app could route its
traffic through the user's tunnel. This is an accepted consequence of the SOCKS5
API boundary, and the credentials are the mitigation. Configure your tun2socks
with them; do not build an unauthenticated path to that port.

Do not log the password, do not put it in an `Intent` extra that leaves your
process, and do not expose it through a `ContentProvider` or exported service.

### 9.2 The `sl://` key is server access

The server public key plus address is what grants access to the server. Anyone
holding it can use the server. Do not ship it hardcoded in the APK/IPA where
avoidable — fetch it at runtime over an authenticated channel and keep it in
app-private storage. In the current production configuration there is no
per-client authentication that would limit an extracted key.

### 9.3 Logging

At `debug`/`trace` the core logs connection details. Do not ship a release build
that routes those to a persistent file or a remote crash reporter.

### 10.1 Guard tests

```bash
go test ./mobile/                       # unit tests
go test -tags gomobileguard ./mobile/   # requires the `gobind` binary on PATH
```

The `gomobileguard` test runs `gobind` and asserts that `Session`, `Config`,
`Logger`, `EventHandler`, `socksPort` and `networkChanged` are all present in the
generated Java — gobind drops unsupported types with a *warning*, not an error, so
a silently missing method is a real failure mode. It is behind a build tag on
purpose: a test that skips when the tool is missing would be green forever and
guard nothing.

Two dependency guards run in the normal test pass: the mobile tree must not pull
`leakguard`, `tun2socks/v2/engine` (gVisor), or `xray-core`, and the tun2socks
package count must not exceed its measured ceiling.

| 4 | **No throughput benchmark through the loopback SOCKS5 path.** The desktop client bypasses the loopback socket entirely via an in-process dialer; mobile does not, so it pays real socket copies and syscalls per packet. Every field measurement this project has (cut windows, timing phase, exposure) was taken on the in-process desktop path and does **not** transfer automatically. | UNMEASURED |
| 5 | **iOS requires the Go code to live inside the network extension.** The extension is a separate process; `127.0.0.1:PORT` in the host app is not reachable as a way to tunnel system traffic. The whole memory budget in #2 is the extension's budget. | Architectural, VERIFIED from platform semantics |
| 6 | **No stats/metrics API.** `state()` and `OnStateChange` are the entire observability surface. There is no counter snapshot, no throughput reading, no per-slot view. | VERIFIED |
| 7 | **No automatic reconnect at the SDK layer, by design.** The transport reconnects internally and indefinitely. Do not add your own retry loop on top of `start()`: a second engine means double the TLS connections to the origin. | VERIFIED |
| 8 | **Doze / long sleep / clock-jump behaviour is unverified on device.** See §7.3. | UNVERIFIED |
| 9 | **IPv6 policy is undefined.** `serverAddr` is a bare IP; if it is IPv4-only and the carrier network is IPv6-only, the connection will not establish. The desktop leak guard that suppressed IPv6 is not in the mobile tree. Untested. | UNVERIFIED |
| 10 | Error messages from validation and from `start()` are in Russian. Do not surface them to end users; map on behaviour. | VERIFIED |
| 11 | **The `.aar`/`.xcframework` cannot coexist with another gomobile-bound framework in the same process.** Two bound modules mean two Go runtimes sharing one `seq` reference table; the process dies on the first allocation. Requires a single `gomobile bind` over both packages. | REPORTED by integrator, §12.1 |
| 12 | **No log file rotation or size cap.** `setLogLevel` is the only volume control; persistence and rotation are entirely the platform's. | VERIFIED, §5.3 |

## 12. Troubleshooting

| Symptom | Likely cause | What to check |
|---|---|---|
| `state()` stays `connecting` | `start()` is still blocked in handshake, or you are polling from a thread that started it. `start()` blocks until the listener binds — it does not return early. | Confirm `start()` is on a background thread and has actually returned. A hung handshake can take up to ~10 s. |
| `start()` throws immediately, no network activity | Config validation. | See §4.2. Most common: `pubKeyHex` not 64 chars, `serverAddr` missing `:port`. |
| `state()` goes `degraded` | Pool has had zero ready slots for ≥15 s. Listener is alive, traffic is not flowing. | Network reachability to the origin; whether you missed a `networkChanged()` call; server availability. `degraded` recovers on its own if slots come back. |
| `socksPort() == 0` after `start()` | `start()` did not succeed, or `stop()` already ran, or you read it before `start()` returned. | Check `state()`; check whether `start()` threw. Never cache the port across a `stop()`/`start()`. |
| Tunnel dead ~30–60 s after switching Wi-Fi↔LTE, then recovers | `networkChanged()` is not wired up. | §8.2. This is the single most common integration miss. |
| Process dies with no Go panic and no Java stack trace you recognise | JNI abort from a Java exception thrown inside `Logger.log` / `OnStateChange` / `OnError`. | §6.2. Wrap every callback body in `try/catch(Throwable)`. Reproduce by deliberately throwing in a callback. |
| Tunnel goes silent under heavy UI load, slots get cut | A blocking callback stalled a slot reader. | §6.3. Callbacks must return immediately — post to a handler. |
| `Activity` leaks / `Context` never collected | `Mobile.setLogger(...)` still holds a JNI reference to an object capturing the Activity. | §6.4 item 4. Call `Mobile.setLogger(null)` and `setEventHandler(null)` on teardown. |
| Second `start()` "does nothing" | Correct behaviour — `start()` is idempotent while up. | Call `stop()` first if you intend to rebuild with different parameters. |
| Traffic works but DNS resolves outside the tunnel | No DNS handling in the SDK. | §8.1 — `Builder.addDnsServer` / `NEDNSSettings`. |
| Another app on the device can use the proxy | You configured the proxy without credentials. | §9.1 — always pass `socksUser()`/`socksPass()`. |
| Server-side sessions accumulate after crashes | Process killed without `stop()`; session-FIN never sent. | §7.3. They expire on the server's idle timeout (default 90 s). Call `stop()` from `onRevoke()`/`onDestroy()`. |
| Missing `Session` / `Config` methods in the generated Java | gobind silently dropped an unsupported type. | Run `go test -tags gomobileguard ./mobile/`. |
| NDK rejects the build | `-androidapi 21` was omitted. | §10. |
| `fatal error: bad sweepgen in refill` on the very first facade call | Two gomobile-bound frameworks linked into one process. | §12.1 — this is a link-time problem, not a bug in the call that crashed. |

### 12.1 Two gomobile frameworks in one process — `bad sweepgen in refill`

REPORTED BY AN INTEGRATOR (NixaVPN client team, iOS/macOS, 2026-08-31),
reproduced on their side. This is **not** a measurement of ours — we have never
built an iOS framework (§11 #1) — but the mechanism is specific enough, and the
cost was high enough (two days), that it belongs here.

**Symptom.** The process dies on the first memory allocation inside the first
facade call, with no Go panic you can catch:

```
fatal error: bad sweepgen in refill

runtime.(*mcache).refill → runtime.mallocgc → runtime.newobject
github.com/nixavpn/shadowlink/mobile.NewConfig  (mobile/config.go:81)
```

`NewConfig` is incidental — it is simply the first thing that allocates. Any
other entry point would crash the same way.

**Cause.** `gomobile bind` emits **static** frameworks. Link two separately-bound
gomobile modules into one process — for example sing-box's `libbox` alongside
`shadowlink/mobile` — and the linker keeps a **single** copy of the `seq`
reference-table symbols (`_IncGoRef`, `_DestroyRef`). Those belong to a specific
Go runtime; each bound module ships its own. The surviving copy hands one
runtime's allocator state to the other, and the first `mallocgc` trips the
consistency check.

**Fix.** One `gomobile bind` invocation covering both packages, so there is one
runtime and one `seq`:

```bash
gomobile bind -target=ios/arm64 -o Combined.xcframework ./wrapper/
```

where `./wrapper/` is a Go package that imports both modules and re-exports the
API surface each side needs. Their working setup is exactly this: a shared
wrapper module bound once. Partial measures do not work — linking the two
frameworks separately fails regardless of order, and there is no build flag that
splits the symbols.
