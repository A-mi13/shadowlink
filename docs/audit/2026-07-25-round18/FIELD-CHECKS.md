# Проверка 1 (шаг 4b): работает ли body-marker на проде

**Зачем.** От этого зависит, можно ли удалять заголовок `X-SL-RL` — прямую
сигнатуру ShadowLink для активного зонда (находка H-1). Body-marker
(Schema.org JSON-LD) — второй, wire-neutral носитель того же сигнала. Если он
работает, заголовок можно убрать. Если нет — удаление лишит клиента **обоих**
носителей: он перестанет распознавать rate-limit и уйдёт в экспоненциальный
backoff вместо фиксированного кулдауна, что бьёт по ёмкости сильнее, чем
заголовок — по скрытности.

**Почему нельзя проверить из репозитория.** HTML-шаблоны decoy живут только на
сервере (`-decoy /var/www/decoy`), в git их нет. Body-marker физически
внедряется лишь в шаблон, содержащий baseline: `<script
type="application/ld+json">` с `identifier.propertyID="rl-state"` и полем
`value` **ровно** нужной ширины (подстановка байт-в-байт, чтобы
`Content-Length` не менялся).

## 1.1. Прямая проверка шаблона (самое быстрое)

На сервере:

```bash
grep -o 'propertyID"[^,]*' /var/www/decoy/index.html
grep -c 'application/ld+json' /var/www/decoy/index.html
```

- Есть `propertyID":"rl-state"` → baseline на месте, переходите к 1.3.
- Пусто → **baseline нет, заголовок удалять нельзя**, сначала обновить шаблоны.

## 1.2. Проверка через новый fail-fast (шаг 4a уже в коде)

С этого раунда `-decoy-snapshot-strict` по умолчанию **true**: сервер не
стартует с шаблонами без baseline. Проверка сводится к попытке запуска:

```bash
systemctl restart shadowlink && systemctl status shadowlink --no-pager | head -20
journalctl -u shadowlink -n 30 --no-pager | grep -i snapshot
```

- Сервер поднялся → baseline есть.
- `decoy snapshot loading failed — сервер не стартует (fail-fast)` → baseline
  нет. **Не оставляйте прод лежать**: временно запустите с
  `-decoy-snapshot-strict=false`, затем обновите шаблоны.

> Это поведение — намеренное следствие шага 4a. Раньше сервер тихо
> деградировал в header-only, и состояние «body-marker не работает» было
> незаметным.

## 1.3. Подтверждение метриками (доказательство, что носитель реально едет)

```bash
curl -s -H "X-Mgmt-Key: <MGMT_KEY>" \
  http://127.0.0.1:<MGMT_PORT>/metrics | grep ratelimit_emitted
```

Смотрите два счётчика:

| Счётчик | Значение | Вывод |
|---|---|---|
| `..._emitted_by_body_total` | растёт | ✅ body-marker работает |
| `..._emitted_by_body_missing_total` | растёт | ❌ снапшота нет, режим header-only |

Оба по нулям — значит rate-limit просто не срабатывал; чтобы получить данные,
вызовите его искусственно (см. 1.4).

## 1.4. Активная проверка: вызвать rate-limit и посмотреть ответ

Порог `ws_upgrade` — burst 18. Девятнадцатый запрос уйдёт в rate-limit-ветку:

```bash
for i in $(seq 1 25); do
  curl -sk -o /dev/null -D - "https://<ORIGIN>/socket.io/" \
    -H "Host: <ВАШ_ДОМЕН>" \
    -H "Upgrade: websocket" -H "Connection: Upgrade" \
    -H "Sec-WebSocket-Version: 13" \
    -H "Sec-WebSocket-Key: $(head -c16 /dev/urandom | base64)" \
    | grep -i "^x-sl-rl\|^HTTP/"
done
```

Затем — тело последнего ответа:

```bash
curl -sk "https://<ORIGIN>/socket.io/" -H "Host: <ВАШ_ДОМЕН>" \
  -H "Upgrade: websocket" -H "Connection: Upgrade" \
  -H "Sec-WebSocket-Version: 13" \
  -H "Sec-WebSocket-Key: $(head -c16 /dev/urandom | base64)" \
  | grep -o 'rl-state[^<]*' | head -3
```

Критерий: в теле присутствует `rl-state` с непустым `value` → body-marker
доезжает до клиента.

**Заодно проверьте фикс C-2** (пустое тело = оракул):

```bash
curl -sk -o /dev/null -w "status=%{http_code} size=%{size_download}\n" \
  "https://<ORIGIN>/socket.io/" -H "Host: <ВАШ_ДОМЕН>" -H "Upgrade: websocket" \
  -H "Connection: Upgrade" -H "Sec-WebSocket-Version: 13" \
  -H "Sec-WebSocket-Key: $(head -c16 /dev/urandom | base64)"
```

`size_download=0` при `status=200` — регрессия C-2, немедленно сообщите.
Ожидается непустой размер.

## Решение по шагу 4c

- 1.1/1.2 подтвердили baseline **и** 1.3/1.4 показали растущий
  `_by_body_total` → сообщите, удаляю `X-SL-RL` и `HeaderCarrier`.
- Иначе → сначала обновление шаблонов decoy, заголовок остаётся.

# Проверка 2 (P0): режет TSPU по возрасту или по объёму?

**Зачем.** Это самая важная незакрытая задача раунда. Вся тайминговая
подсистема (`_MAX_SLOT_AGE=75s`, `_AGE_CUT_MIN_AGE=45s`, stagger 6s, cap 45s,
`DRAIN_HARD_CAP=30s`) настроена на окно «~130–190 с по возрасту», **которое не
подтверждено ни одним источником**. Публичный корпус (net4people#490) описывает
триггер по **объёму** — ~16–20 КБ server→client в рамках одного TCP. Наша цифра
похожа на перенос замера GFW Китая (USENIX Sec 2023) — автор habr-статьи, откуда
она вероятно пришла, сам это дисклеймит. ACM IMC 2022 добавляет, что ТСПУ
поведенчески неоднородна по регионам.

Расхождение порогов, если корпус прав: **16–20 КБ против наших 256 MiB** —
четыре порядка.

**Обязательное условие:** выполнять из российской сети, через оператора, где
рез реально наблюдается. С зарубежной машины результат бессмысленен.

## 2.1. Тест на возраст: долгое молчание, затем передача

Гипотеза «режет по возрасту» предсказывает: соединение, простоявшее 200+ с,
умрёт даже без трафика.

```bash
# Слот открывается и молчит 240с, затем пробуем передать данные.
python3 - <<'EOF'
import socket, ssl, time
ORIGIN, DOMAIN = "<ORIGIN>", "<ВАШ_ДОМЕН>"
ctx = ssl.create_default_context(); ctx.check_hostname=False; ctx.verify_mode=ssl.CERT_NONE
s = socket.create_connection((ORIGIN, 443), timeout=15)
t = ctx.wrap_socket(s, server_hostname=DOMAIN)
print("TLS установлен, молчим 240с...", flush=True)
time.sleep(240)
try:
    t.send(b"GET / HTTP/1.1\r\nHost: %s\r\nConnection: close\r\n\r\n" % DOMAIN.encode())
    t.settimeout(20)
    data = t.recv(4096)
    print("ПРОШЛО после 240с молчания, получено", len(data), "байт")
    print("=> рез НЕ по возрасту простоя")
except Exception as e:
    print("ОБОРВАЛОСЬ:", type(e).__name__, e)
    print("=> возможен рез по возрасту — повторите 3-5 раз для надёжности")
EOF
```

## 2.2. Тест на объём: качаем нарастающими порциями, ищем порог

Гипотеза «режет по объёму» предсказывает обрыв после ~16–20 КБ **вниз** в одном
TCP, независимо от времени.

```bash
# Тянем один большой ответ и смотрим, на каком байте встанет.
curl -sk --no-buffer -o /dev/null -w "\nполучено=%{size_download} время=%{time_total}\n" \
  --max-time 120 "https://<ORIGIN>/<путь-отдающий-много-данных>" \
  -H "Host: <ВАШ_ДОМЕН>"
```

Осмысленнее — снять кривую: запросить 8 КБ, 16 КБ, 32 КБ, 64 КБ, 256 КБ, 1 МБ в
**отдельных** соединениях и записать, где начинаются обрывы.

```bash
for KB in 8 16 24 32 64 128 256 1024; do
  echo -n "${KB}KB: "
  curl -sk -o /dev/null --max-time 60 \
    -w "size=%{size_download} code=%{http_code} t=%{time_total}\n" \
    "https://<ORIGIN>/<эндпоинт>?bytes=$((KB*1024))" -H "Host: <ВАШ_ДОМЕН>"
done
```

**Критерий:** резкая граница между «прошло» и «встало» на 16–24 КБ подтверждает
байтовую модель. Отсутствие границы при росте до мегабайт — опровергает.

## 2.3. Контроль: тот же тест на «чистый» IP

Чтобы отделить ТСПУ от обычных сетевых проблем, повторите 2.1 и 2.2 против
сервера, который заведомо не под резом (или из зарубежной сети). Различие в
поведении — и есть эффект ТСПУ.

## 2.4. Что снять из клиентских логов при реальном обрыве

```bash
# На клиенте с -log debug:
grep -E "slot_age_ms|last_write_age_ms|down_bytes|close 1006" <лог> | tail -40
```

Ключ к различению — сопоставление трёх полей на момент смерти:

| Что видно | Вывод |
|---|---|
| `slot_age_ms` ≈ одинаков при разных `down_bytes` | рез по **возрасту** |
| `down_bytes` ≈ одинаков при разных `slot_age_ms` | рез по **объёму** |
| `last_write_age_ms` мал (слот активен) | рез **не** по тишине |

Историческая база для сравнения (из `SALVAGE.md` §7): 126× close 1006, по
`slot_age_ms` 66× на 2–4 мин, 94× при `down_bytes` < 50 КБ, и полевой случай
`slot=11 slot_age_ms=132756 last_write_age_ms=15436`. Обратите внимание: 94×
при `down_bytes` < 50 КБ **совместимо и с байтовой моделью** — именно поэтому
нужен контролируемый замер, а не пересмотр старых логов.

## Что делать с результатом

- **Рез по объёму** → ротация по возрасту не нужна в текущем виде. Тогда:
  per-slot байтовый лимит (~16–20 КБ вместо 256 MiB), а число соединений на
  origin IP падает с ~28/час до единиц — что **одновременно** обезоруживает
  host-profiling (FOCI 2026, см. `RESEARCH.md` §8). Один фикс закрывает две
  угрозы.
- **Рез по возрасту** → константы валидны, но нужно решать конфликт: ротация
  спасает от age-cut и кормит counting-детектор. Это архитектурный выбор, а не
  тюнинг.
- **Неоднородно по операторам** (ожидаемо по ACM IMC 2022) → зашитая глобально
  константа неверна в принципе, нужна адаптация по наблюдаемому поведению.

# Проверка 3 (попутно): connections-per-origin-IP-per-hour

Нужна для оценки против host-profiling. Важно: детектор считает соединения **на
сервер**, а не на клиента — при N пользователях на одном origin счёт умножается
на N.

```bash
# На сервере: уникальные TCP-соединения к :443 за час.
ss -tn state established '( sport = :443 )' | wc -l   # мгновенный срез
# Точнее — из nginx access.log за час:
awk -v d="$(date -d '1 hour ago' '+%d/%b/%Y:%H')" '$4 ~ d' /var/log/nginx/access.log \
  | awk '{print $1}' | sort -u | wc -l    # уникальных клиентских IP
grep -c "" /var/log/nginx/access.log      # всего запросов
```

Сопоставлять с τ и w из FOCI 2026 — **но сначала надо достать сам PDF и выписать
фактические значения**: агент их не верифицировал, а «~28 conn/час» это
арифметика `3600/130`, а не цифра из статьи (см. `RESEARCH.md` §8).
