Две задачи, которые нельзя выполнить из репозитория: нужен живой сервер и

Обозначения: `<ORIGIN>` — IP прод-сервера, `<MGMT_PORT>` — порт management API

# Проверка 1 (шаг 4b): работает ли body-marker на проде

**Зачем.** От этого зависит, можно ли удалять заголовок `X-SL-RL` — прямую
сигнатуру ShadowLink для активного зонда (находка H-1). Body-marker
(Schema.org JSON-LD) — второй, wire-neutral носитель того же сигнала. Если он
работает, заголовок можно убрать. Если нет — удаление лишит клиента **обоих**
носителей: он перестанет распознавать rate-limit и уйдёт в экспоненциальный
backoff вместо фиксированного кулдауна, что бьёт по ёмкости сильнее, чем
заголовок — по скрытности.

**Почему нельзя проверить из репозитория.** HTML-шаблоны decoy живут только на
сервере (`-decoy /var/www/decoy`), в git их нет. Body-marker физически
внедряется лишь в шаблон, содержащий baseline: `<script
type="application/ld+json">` с `identifier.propertyID="rl-state"` и полем
`value` **ровно** нужной ширины (подстановка байт-в-байт, чтобы
`Content-Length` не менялся).

## 1.1. Прямая проверка шаблона (самое быстрое)

На сервере:

```bash
grep -o 'propertyID"[^,]*' /var/www/decoy/index.html
grep -c 'application/ld+json' /var/www/decoy/index.html
```

- Есть `propertyID":"rl-state"` → baseline на месте, переходите к 1.3.
- Пусто → **baseline нет, заголовок удалять нельзя**, сначала обновить шаблоны.

## 1.2. Проверка через новый fail-fast (шаг 4a уже в коде)

С этого раунда `-decoy-snapshot-strict` по умолчанию **true**: сервер не
стартует с шаблонами без baseline. Проверка сводится к попытке запуска:

```bash
systemctl restart shadowlink && systemctl status shadowlink --no-pager | head -20
journalctl -u shadowlink -n 30 --no-pager | grep -i snapshot
```

- Сервер поднялся → baseline есть.
- `decoy snapshot loading failed — сервер не стартует (fail-fast)` → baseline
  нет. **Не оставляйте прод лежать**: временно запустите с
  `-decoy-snapshot-strict=false`, затем обновите шаблоны.

> Это поведение — намеренное следствие шага 4a. Раньше сервер тихо
> деградировал в header-only, и состояние «body-marker не работает» было
> незаметным.

## 1.3. Подтверждение метриками (доказательство, что носитель реально едет)

```bash
curl -s -H "X-Mgmt-Key: <MGMT_KEY>" \
  http://127.0.0.1:<MGMT_PORT>/metrics | grep ratelimit_emitted
```

Смотрите два счётчика:

| Счётчик | Значение | Вывод |
|---|---|---|
| `..._emitted_by_body_total` | растёт | ✅ body-marker работает |
| `..._emitted_by_body_missing_total` | растёт | ❌ снапшота нет, режим header-only |

Оба по нулям — значит rate-limit просто не срабатывал; чтобы получить данные,
вызовите его искусственно (см. 1.4).

## 1.4. Активная проверка: вызвать rate-limit и посмотреть ответ

Порог `ws_upgrade` — burst 18. Девятнадцатый запрос уйдёт в rate-limit-ветку:

```bash
for i in $(seq 1 25); do
  curl -sk -o /dev/null -D - "https://<ORIGIN>/socket.io/" \
    -H "Host: <ВАШ_ДОМЕН>" \
    -H "Upgrade: websocket" -H "Connection: Upgrade" \
    -H "Sec-WebSocket-Version: 13" \
    -H "Sec-WebSocket-Key: $(head -c16 /dev/urandom | base64)" \
    | grep -i "^x-sl-rl\|^HTTP/"
done
```

Затем — тело последнего ответа:

```bash
curl -sk "https://<ORIGIN>/socket.io/" -H "Host: <ВАШ_ДОМЕН>" \
  -H "Upgrade: websocket" -H "Connection: Upgrade" \
  -H "Sec-WebSocket-Version: 13" \
  -H "Sec-WebSocket-Key: $(head -c16 /dev/urandom | base64)" \
  | grep -o 'rl-state[^<]*' | head -3
```

Критерий: в теле присутствует `rl-state` с непустым `value` → body-marker
доезжает до клиента.

**Заодно проверьте фикс C-2** (пустое тело = оракул):

```bash
curl -sk -o /dev/null -w "status=%{http_code} size=%{size_download}\n" \
  "https://<ORIGIN>/socket.io/" -H "Host: <ВАШ_ДОМЕН>" -H "Upgrade: websocket" \
  -H "Connection: Upgrade" -H "Sec-WebSocket-Version: 13" \
  -H "Sec-WebSocket-Key: $(head -c16 /dev/urandom | base64)"
```

`size_download=0` при `status=200` — регрессия C-2, немедленно сообщите.
Ожидается непустой размер.

## Решение по шагу 4c

- 1.1/1.2 подтвердили baseline **и** 1.3/1.4 показали растущий
  `_by_body_total` → сообщите, удаляю `X-SL-RL` и `HeaderCarrier`.
- Иначе → сначала обновление шаблонов decoy, заголовок остаётся.

# Проверка 2 (P0): ПЕРЕСМОТРЕНА 2026-07-31 — замер не решает задачу

> **Постановка изменена.** Ниже сохранены команды замера — они полезны как
> разовая диагностика, — но **как P0 задача переформулирована**: вместо «измерить
> и зашить правильное число» → «сделать так, чтобы клиент выводил порог сам».
>
> **Почему замер не решает.** Наш же research (`RESEARCH.md`, ACM IMC 2022,
> peer-reviewed) говорит: ТСПУ **поведенчески неоднородна по регионам и
> операторам**. Значит идеально выполненный замер даёт число для ОДНОГО AS в ОДИН
> момент времени. У другого пользователя с другим провайдером порог другой; через
> месяц он другой и здесь. Мы бы заменили одну недоказанную константу
> (130–190 с, вероятно перенесённую с GFW) на другую — измеренную, но всё равно
> нашу, не пользовательскую. И она начала бы врать молча: ровно тот класс
> дефекта, который раунд 18 и вылавливал (комментарий утверждает инвариант, код
> его не держит).
>
> **Что замер всё-таки даёт** — и это стоит отделить от «выбрать значение»: он
> отвечает, какая **ось** является триггером (возраст / объём / что-то третье).
> Это не тюнинг, а выбор того, ЧТО измерять в адаптивном контуре: если рез по
> объёму (~16–20 КБ, net4people#490), а мы крутим возраст, адаптация будет
> подстраивать константу, не влияющую на исход. Но узнать это можно и без
> выделенной поездки в РФ-сеть: клиент наблюдает обрывы в поле постоянно —
> достаточно записывать при смерти слота три поля вместе и смотреть, что
> кластеризуется у порога. См. §2.4 ниже (та же процедура, но как штатная
> телеметрия, а не ручной разбор логов).

## Новая постановка P0: адаптивный контур вместо константы

**Цель:** порог ротации выводится из наблюдаемого поведения СЕТИ ПОЛЬЗОВАТЕЛЯ,
per-AS, локально на устройстве. Никакого глобального числа.

**Шаги:**

1. **Телеметрия смерти слота** — ✅ **РЕАЛИЗОВАНО 2026-07-31.**
   Пакет `client/slotobs`: кольцевой буфер на 512 наблюдений
   `(AgeMs, DownBytes, LastWriteAgeMs, CloseKind, Mature)`, запись в точке смерти
   (`ws_pool.go`, рядом с тем же лог-сайтом), экспорт распределения в Prometheus.
   Раньше данные шли только в лог-строку: перцентили посчитать нельзя, история
   между запусками теряется.

   **Что смотреть на КЛИЕНТЕ — только лог.** Обнаружено при сборке: клиентский
   Prometheus-экспортёр `WritePromMetrics` **не вызывается нигде** в `cmd/`,
   поэтому линковщик его выбрасывает и `/metrics` у клиента не существует вовсе
   (в бинаре нет ни одной серии, включая старый `shadowlink_drain_inflight`).
   Единственный рабочий канал — `StartStatsLogger`, поэтому сводка идёт туда:

   ```bash
   # Клиент запущен с -log debug (connect-vpn-DEBUG.bat):
   grep "slot death distribution" <лог> | tail -5
   ```
   Строка появляется раз в 5 с, но **только начиная с 12 наблюдений** — ниже
   этого CV является шумом, и печатать его значило бы приглашать считать порог по
   двум точкам. Поле `tighter_axis` даёт подсказку (`age` / `down_bytes` /
   `inconclusive`), но это hint, а не вердикт — рядом всегда есть `samples`,
   `cv_age`, `cv_down_bytes` для самостоятельной оценки.

   **Prometheus-серии оставлены** (`emitSlotDeathDistribution` в
   `WritePromMetrics`) — они заработают, если/когда у клиента появится
   metrics-endpoint. На сервере экспортёр живой и доступен через management API.
   | Серия | Смысл |
   |---|---|
   | `_samples` | сколько смертей в выборке (нужно ≥ несколько десятков) |
   | `_age_ms{quantile=...}` | возраст слота при смерти — p10/p50/p90 |
   | `_down_bytes{quantile=...}` | объём вниз при смерти; сравнить с ~16–20 КБ |
   | `_cv{axis="age"}` vs `_cv{axis="down_bytes"}` | **главный сигнал**: та ось, где CV **ниже**, и есть ось реза |
   | `_by_close_kind{kind=...}` | отделяет teardown посредником (`close_other`/`reset_by_peer`) от нашего таймаута (`io_timeout`) |

   **Как читать CV:** жёсткий порог даёт кластер на своей оси и разброс на чужой.
   На синтетике различение подтверждено: рез по возрасту → `AgeCV≈0.005` против
   `BytesCV≈1.73` (разница 300×), рез по объёму — зеркально.

   **Границы:** наблюдение НИЧЕГО не решает — ротацией по-прежнему управляют
   `maxSlotAge`/`ageCutMinAge`. Поле `Mature` записывается, но доверять ему
   нельзя: это ВЫВОД проверяемого порога. Данные не покидают устройство (только
   тайминги, счётчики байт и метка формы закрытия; ни адресов, ни имён хостов).
   Персистентность между запусками — шаг 5, отдельное решение.
2. **Вывод оси** — ✅ **РЕАЛИЗОВАНО 2026-07-31** (`Recorder.Infer()` в
   `client/slotobs/infer.go`). Возвращает `Verdict{Axis, Threshold, Samples,
   Rejected, Reason}`; **умеет отвечать «не знаю»** (`AxisUnknown`) при малой
   выборке, слабом разделении осей или слишком большом разбросе у выбранной оси.
   Порог = 80% от p10 наблюдённых смертей — ротировать надо раньше самой ранней
   смерти, а не по медиане. Отсев шума (`age=0`, `closed_local`, `io_timeout`)
   публикуется в `Rejected`, а не делается молча. Логируется отдельной строкой
   `slot death inference (advisory, not applied)` — **ничего не применяет**.

   > **Зачем отсев:** в первой полевой сводке три смерти с `age=0`
   > (моментальный `io_timeout` при подключении — не рез) подняли CV возраста с
   > **0.18 до 0.4546** и почти замаскировали 12-кратное разделение осей.
   > Инференс «который всегда что-то возвращает» выдал бы на этих данных
   > уверенный, но неверный ответ.

## РЕЗУЛЬТАТ ЗАМЕРА 2026-07-31 (первая полевая сессия, 17 мин, 19 age-cut)

**Ось реза — ВОЗРАСТ.** Проверено телеметрией, не гипотеза:

| Метрика | Значение |
|---|---|
| CV возраста | **0.180** |
| CV байтов | **2.202** |
| Разделение | ось возраста тише в **12 раз** |
| Окно смертей | **85.3 s … 154.7 s**, медиана 110.8 s |
| Объём при смерти | 0 КБ … **11.2 МБ** (разброс на 4 порядка) |

**Что это опровергает:**

1. **Гипотеза «рез по объёму ~16–20 КБ»** (net4people#490) — для этой сети
   **не подтверждается**. Смерти происходили и на 0 КБ, и на 11.2 МБ; объём
   на исход не влияет.
2. **Окно «130–190 с»** — **неверно**. Реальная нижняя граница **85.3 с**, то
   есть на 45 с раньше. Прежний тюнинг (75 s + sticky 45 s = 120 s) считался
   безопасным относительно 130 с, но фактически **14 смертей из 19 случились
   раньше 120 с** — внутри нашего же worst-case teardown.

**Наблюдаемое следствие в логе:** 36 срабатываний `sticky backstop teardown`,
136 принудительно оборванных стримов, `inflight_cap_deferred_total=59`.

**Что исправлено по этому замеру:**

`SHADOWLINK_STICKY_MAX_DRAIN_AGE` **45 s → 15 s** (worst-case 120 s → 90 s), в
обоих `.bat` и в дефолте кода (`client.DefaultStickyMaxDrainAge`, раньше было
**10 минут** — а во втором `.bat` sticky вообще не задавался, то есть обычный
режим работал с 10-минутным удержанием и `hard_cap=90s` → worst 165 s).

**Почему урезан sticky, а не `MAX_SLOT_AGE`:** снижение `MAX_SLOT_AGE` до 60 s и
ниже поднимает число соединений на origin IP (75 s → ~384/час, 50 s → ~576/час) и
усиливает host-profiling (FOCI 2026, `RESEARCH.md` §8). Лечить age-cut ценой
counting-детектора нельзя.

**Почему урезать sticky безопасно:** миграция стрима работает — в той же сессии
**320 успешных переездов, 0 отказов**, и лишь **5** реальных потерь данных
(`downlink write error`). Удержание стареющего слота почти ничего не спасает, а
под рез подставляет.

**Честное ограничение:** 90 s всё ещё выше 85.3 s. Положительного запаса при
`MAX_SLOT_AGE=75s` достичь нельзя — это компромисс до шага 3.

### Уточнение по второму прогону (2026-07-31, 65 мин, 92 age-cut)

Выборка выросла с 19 до **92**, вывод устойчив:

**Найдена ошибка в первой правке — sticky не применялся.** `deadline` дренажа

хотя в логе писалось `sticky_outcome=age_backstop`, будто sticky сработал.

Исправлено: `DRAIN_HARD_CAP` тоже опущен до **15 s** в обоих `.bat`. Теперь
worst-case действительно 75+15 = **90 s**. Согласованность сторожится тестом
`TestStickyDrainBudget_HardCapNotBelowSticky`.

**Почему 15 s достаточно:** из 263 дренажей второго прогона **200 завершились за
0 s**, дольше 15 s — единицы. Остаток уезжает миграцией.

3. **Адаптация порога.** Ротировать слот ДО наблюдаемого порога с запасом
   (ориентир: 60–70% от p10 наблюдаемых смертей). Порог плавает вместе с сетью.
4. **Гистерезис.** Растёт частота обрывов → сжимать порог; долго чисто →
   осторожно расширять. Это же снимает конфликт с counting-детектором: при
   отсутствии реза ротация замедляется сама, соединений на origin IP становится
   меньше — то, о чём предупреждает FOCI 2026 (`RESEARCH.md` §8). Сейчас
   ~28 conn/час — следствие константы, а не необходимости.
5. **Персистентность** — сохранять выведенный профиль между запусками, чтобы не
   переобучаться на каждом старте.

**Риски, которые надо закрыть при проектировании:**

- **Обучение на живом трафике.** Первые слоты умирают, чтобы дать выборку.
  Старт должен быть консервативным (от заведомо безопасного низкого порога
  вверх), а не «начать широко и сжиматься».
- **Атрибуция.** Обрыв ≠ ТСПУ: мобильная сеть, NAT, перегрузка VPS дают те же
  1006. Без отделения шума контур будет сжимать порог впустую → нужен контроль
  против заведомо «чистого» endpoint'а.
- **Наблюдаемость.** Контур обязан сообщать текущий выведенный порог и на чём он
  основан. Иначе получим адаптацию, про которую нельзя сказать, работает ли она
  — болезнь `BackpressureCheck` (H-15).
- **Это архитектурное изменение, не тюнинг.** Тайминговая подсистема держится на
  согласованных числах (75s + capped stagger → худший слот 123s < 130s).
  Проектировать целиком, а не подменять одну константу функцией.

**Что сохраняет ценность из замера ниже:** разовая проверка оси (2.1 против 2.2)
на одном операторе — как sanity-check против того, что покажет телеметрия.
Обязательное условие для неё прежнее: **из российской сети**, где рез реально
наблюдается; с зарубежной машины результат бессмыслен.

## 2.1. Тест на возраст: долгое молчание, затем передача

Гипотеза «режет по возрасту» предсказывает: соединение, простоявшее 200+ с,
умрёт даже без трафика.

```bash
# Слот открывается и молчит 240с, затем пробуем передать данные.
python3 - <<'EOF'
import socket, ssl, time
ORIGIN, DOMAIN = "<ORIGIN>", "<ВАШ_ДОМЕН>"
ctx = ssl.create_default_context(); ctx.check_hostname=False; ctx.verify_mode=ssl.CERT_NONE
s = socket.create_connection((ORIGIN, 443), timeout=15)
t = ctx.wrap_socket(s, server_hostname=DOMAIN)
print("TLS установлен, молчим 240с...", flush=True)
time.sleep(240)
try:
    t.send(b"GET / HTTP/1.1\r\nHost: %s\r\nConnection: close\r\n\r\n" % DOMAIN.encode())
    t.settimeout(20)
    data = t.recv(4096)
    print("ПРОШЛО после 240с молчания, получено", len(data), "байт")
    print("=> рез НЕ по возрасту простоя")
except Exception as e:
    print("ОБОРВАЛОСЬ:", type(e).__name__, e)
    print("=> возможен рез по возрасту — повторите 3-5 раз для надёжности")
EOF
```

## 2.2. Тест на объём: качаем нарастающими порциями, ищем порог

Гипотеза «режет по объёму» предсказывает обрыв после ~16–20 КБ **вниз** в одном
TCP, независимо от времени.

```bash
# Тянем один большой ответ и смотрим, на каком байте встанет.
curl -sk --no-buffer -o /dev/null -w "\nполучено=%{size_download} время=%{time_total}\n" \
  --max-time 120 "https://<ORIGIN>/<путь-отдающий-много-данных>" \
  -H "Host: <ВАШ_ДОМЕН>"
```

Осмысленнее — снять кривую: запросить 8 КБ, 16 КБ, 32 КБ, 64 КБ, 256 КБ, 1 МБ в
**отдельных** соединениях и записать, где начинаются обрывы.

```bash
for KB in 8 16 24 32 64 128 256 1024; do
  echo -n "${KB}KB: "
  curl -sk -o /dev/null --max-time 60 \
    -w "size=%{size_download} code=%{http_code} t=%{time_total}\n" \
    "https://<ORIGIN>/<эндпоинт>?bytes=$((KB*1024))" -H "Host: <ВАШ_ДОМЕН>"
done
```

**Критерий:** резкая граница между «прошло» и «встало» на 16–24 КБ подтверждает
байтовую модель. Отсутствие границы при росте до мегабайт — опровергает.

## 2.3. Контроль: тот же тест на «чистый» IP

Чтобы отделить ТСПУ от обычных сетевых проблем, повторите 2.1 и 2.2 против
сервера, который заведомо не под резом (или из зарубежной сети). Различие в
поведении — и есть эффект ТСПУ.

## 2.4. Что снять из клиентских логов при реальном обрыве

```bash
# На клиенте с -log debug:
grep -E "slot_age_ms|last_write_age_ms|down_bytes|close 1006" <лог> | tail -40
```

Ключ к различению — сопоставление трёх полей на момент смерти:

| Что видно | Вывод |
|---|---|
| `slot_age_ms` ≈ одинаков при разных `down_bytes` | рез по **возрасту** |
| `down_bytes` ≈ одинаков при разных `slot_age_ms` | рез по **объёму** |
| `last_write_age_ms` мал (слот активен) | рез **не** по тишине |

Историческая база для сравнения (из `SALVAGE.md` §7): 126× close 1006, по
`slot_age_ms` 66× на 2–4 мин, 94× при `down_bytes` < 50 КБ, и полевой случай
`slot=11 slot_age_ms=132756 last_write_age_ms=15436`. Обратите внимание: 94×
при `down_bytes` < 50 КБ **совместимо и с байтовой моделью** — именно поэтому
нужен контролируемый замер, а не пересмотр старых логов.

## Что делать с результатом

- **Рез по объёму** → ротация по возрасту не нужна в текущем виде. Тогда:
  per-slot байтовый лимит (~16–20 КБ вместо 256 MiB), а число соединений на
  origin IP падает с ~28/час до единиц — что **одновременно** обезоруживает
  host-profiling (FOCI 2026, см. `RESEARCH.md` §8). Один фикс закрывает две
  угрозы.
- **Рез по возрасту** → константы валидны, но нужно решать конфликт: ротация
  спасает от age-cut и кормит counting-детектор. Это архитектурный выбор, а не
  тюнинг.
- **Неоднородно по операторам** (ожидаемо по ACM IMC 2022) → зашитая глобально
  константа неверна в принципе, нужна адаптация по наблюдаемому поведению.

# На сервере: уникальные TCP-соединения к :443 за час.

# Результаты полевых замеров 2026-08-07

Три сессии за день на одном AS. Ниже — что измерено и что из этого следует.
Числа валидны для ОДНОГО оператора: ТСПУ неоднородна (ACM IMC 2022), переносить
их на другую сеть нельзя — переносимо только правило, не значение.

## Что измерено

| | сессия 1 (14:54) | сессия 2 (18:40) | сессия 3 (20:50) |
|---|---|---|---|
| длительность | 2ч49м | 11м32с | 14м32с |
| наблюдений | 222 | 23 | 11 (ниже порога лога) |
| age p10 / p50 / p90 | 84.1 / 97.6 / 118.0 s | 83.5 / 100.3 / 126.0 s | — |
| CV возраста / байтов | 0.26 / 8.73 | 0.28 / 2.16 | — |

| ротаций age / byte_budget | — | 52 / 12 | 93 / 5 |

**Ось реза — ВОЗРАСТ**, подтверждено дважды независимо: CV возраста в 33 и в
7.8 раза плотнее, чем по байтам. Смерти происходят и при 0 КБ переданных,
поэтому объёмный триггер из net4people#490 (~16–20 КБ) на этом AS **не
воспроизводится**.

**Окно реза — 82–126 s**, а не 130–190 s, на которые был затюнен весь
тайминговый контур. Прежняя цифра ничем не подтверждена (см. RESEARCH.md).

## Найденные дефекты (все исправлены)

### 1. worst_case_teardown врал в 1.6 раза

`stats.go` считал `adaptedAge + stickyMaxDrainAge` и был прав только по
совпадению: в поле стояли `hard_cap == sticky == 15s`. Выпадали `stagger`
(до +48 s) и тик watchdog (+5 s), а из двух teardown-пределов брался не тот —
дедлайн стоит на `drainHardCap`.

Цена: при пороге 69 s лог показывал 84 s, реальность для ячеек idx 8..15 —
134 s при p10 смертей 84 s. Восемь ячеек из шестнадцати физически не доживали
до собственной плановой ротации. Это читалось как «ТСПУ агрессивнее, чем
думали», а не как арифметическая ошибка у нас.

→ `WSPoolTransport.worstCaseTeardown()` — единственный источник истины.

### 2. Восемь ячеек ротировались синхронно

При `staggerStep=6s` и `staggerOffsetCap=45s` лестница `min(idx*step, cap)`
упирается в потолок с idx=8, поэтому idx 8..15 получают ОДИНАКОВУЮ базу 45 s.
Stagger существует ровно затем, чтобы этого не было.

→ Конфиг `step=1s, cap=15s`: лестница `15*1s` укладывается в cap, кламп не
срабатывает ни для одной ячейки — 16 различных значений вместо 9.
**Замер сессии 3 подтвердил: `no free cell` 9 → 0, тройные пачки ротаций
исчезли.** Дефицит ячеек был следствием синхронности, а не размера пула.

### 3. sticky-механизм не исполнялся ни разу

Дедлайн дренажа ставится на `drainHardCap`, ветка `drainAge >= sticky`
проверяется только по его срабатывании. При `sticky <= hard_cap` продление
недостижимо — и **равенство ломает так же, как «меньше»**. Лог при этом писал
`sticky_outcome=age_backstop`, то есть механизм выглядел работающим.

Улика: `sticky_active=0` во всех health-строках при 8 teardown с
`sticky_outcome`; `drain_duration` принимал ровно два значения — 15 s и 0 s.

→ `sticky=25s > hard_cap=15s`. Сессии 2 и 3: `sticky_active` до 4,
`drain_duration=25s`. Механизм ожил.

### 4. filterNoise пропускал доцензурные наблюдения

Фильтр резал только `AgeMs<=0`, поэтому `close 1000 (normal)` при старте слота
(`AgeMs=2`, `CloseKind="close_other"`) проходил и становился минимумом.
В логе: `age_min_ms=2` в 67 строках из 74, `margin_to_age_min=-2m24s` — WARN о
превышении бюджета срабатывал ВСЕГДА и не значил ничего.

Эффект шире порчи минимума: два таких наблюдения раздували CV возраста
настолько, что оси переставали разделяться и `Infer` возвращал `AxisUnknown`.
**Контур молчал при достаточных данных.**

→ `InferWithMinAge(ageCutFloor)` + счётчик `RejectionStats.TooYoung`.

### 5. drainRevertBackoff отсутствовал в бюджете

При `no free cell` слот возвращается в `slotReady` и ждёт 30 s, продолжая
стареть. 9 таких событий за 11 минут — путь рабочий. Бюджет был занижен на
30 s, то есть больше, чем весь выигрыш от правки stagger.

→ Пятое слагаемое `defer_backoff`.

## Открытое: бюджет всё ещё отрицательный

После всех правок (расчёт, не замер):

```
base 66 + stagger 15.5 + sweep 5 + defer 30 + tear 25 = 141.5 s
против age_min ~82 s → запас −59 s
```

Дальнейшие шаги плана считались и **отвергнуты как неэффективные**:

| правка | worst-case | запас |
|---|---|---|
| teardown 25 → 15 s | 131.5 s | −49 s |
| + `thresholdSafetyFraction` 0.8 → 0.55 | 111.4 s | −29 s |

Резать `fraction` до 0.55 — это ~1250 conn/час ради −29 s вместо −59 s. Плохой
размен, и он лечит не то слагаемое: после правки №5 доминирует
`drainRevertBackoff=30s`.

**Правильная цель следующего раунда — устранить причину `no free cell`, а не
крутить пороги.** Сессия 3 показала, что это уже частично сделано (9 → 0), и
если результат устойчив, `defer` можно убрать из бюджета — тогда остаток
закрывается дёшево:

```
base 66 + stagger 15.5 + sweep 5 + tear 15 = 101.5 s   запас −19 s
```

Дополнительно ждёт проверки `drainTargetOverAged` (`ws_pool_drain.go`): он
берёт `2 × p.maxSlotAge` СКОНФИГУРИРОВАННЫЙ (150 s), а слоты умирают на
82–126 s. Tier-2 эвикция, похоже, недостижима в проде — мёртвый код.

## Не подтверждено замером

Поля `rejected_too_young`, `age_min_clean`, `defer_backoff` в поле **не
наблюдались**: сессия 3 набрала 11 смертей при пороге логирования 12
(`minSlotDeathSamplesToLog`). Тесты их покрывают, но поле — не тест. Нужна
сессия на 20–25 минут активного трафика.

## Побочные наблюдения

- **Байтовая ось — не то, чем кажется.** При 5.6 МБ/с бюджет (4–46 MiB)
  выбирается за 0.75–8.7 s, а floor `byteBudgetMinRotationInterval = 10s`
  больше. Фактический триггер `reason=byte_budget` — таймер 10 s, а не объём.
  Наблюдённые `down_bytes` 126–140 МБ выше максимально возможного бюджета в
  2.6 раза: это дренящийся слот, а не триггер.
- **Выборка `slotobs` цензурирована**: `Record` вызывается только на ошибке
  чтения, плановые ротации не попадают. Долю «срезано посредником» из
  `by_close_kind` вывести нельзя, p10 смещён вверх.
- **Миграция работает отлично**: стрим 19 МБ / 4678 uploads пережил ~8 смен
  слота; стрим жил 2ч41м при медианной жизни слота ~98 s. `decrypt_fails=0` во
  всех трёх сессиях.
- **nginx не при чём.** Гипотеза «рез делает наш же `proxy_read_timeout 60s`»
  проверена на проде и опровергнута: в конфиге стоят явные 86400 s, а
  `upstream timed out` — 0 записей. Плюс сервер шлёт WS-ping каждые 22.5–90 s.
