# ShadowLink Protocol — Reference

Steganographic VPN. Go 1.25, `module github.com/nixavpn/shadowlink`. Отдельный
проект (`D:\shadowlink`) со своим go.mod и git — **вне дерева NixaVPN**.
Противник — **TSPU** (DPI РКН); из этого растут все архитектурные решения.

## Hard rules

1. **НЕ предлагать CDN / Cloudflare / domain fronting.** Прод = DIRECT к голому
   origin IP. ⚠ Обоснование уточнено 2026-08-07: прежнее «РКН режет диапазоны CDN
   целиком» — форумное, peer-reviewed подтверждения нет. Более сильный довод —
   ACM IMC 2022: ТСПУ стоит **inline на краю каждого ISP**, а не на IX, поэтому
   природа origin не меняет того, что решение принимается на первом хопе от
   абонента. Domain fronting отдельно мёртв с 2018 — крупные CDN его отключили.
2. **НЕ рандомизировать TLS fingerprint.** Только Chrome. Рандомный FP уникален,
   а уникальность и есть сигнал — это довод самодостаточный, замера не требует.
   ⚠ Тезис «Firefox/Safari РКН банит первыми» — форумный и **оспорен**
   (Xray-core#6293, 2026-06: обратная рекомендация); не считать доказанным.
   ⚠ Chrome 133 — это **потолок uTLS**, а не выбор: профилей выше в библиотеке
   нет. Значит отпечаток неизбежно дрейфует относительно живого Chrome. Починить
   выбором версии нельзя; ранний сигнал — доля Chrome 133 в реальном трафике.
3. **Горячий путь = WebSocket binary frames.** JSON-envelope только на handshake
   POST + cover.
4. **nginx обязателен** — Go `net/http` шлёт non-browser HTTP/2 SETTINGS (JA3-риск).
5. **Серверный бинарь — единственная копия** `bin/shadowlink-server-linux` здесь.
   Вторая копия однажды дала silent «binary identical, skipping upload».
6. **Windows-dev: `-race` недоступен** (нет gcc). Зелёный локальный прогон ≠ нет гонки.
7. **Коммиты и push делает пользователь.** Не коммитить без явной просьбы.
8. Тайминговые константы — не менять «на глаз». ⚠ Окно ~130–190 с **НЕ
   подтверждено** и, по замеру 2026-08-07, **неверно**: наблюдаемое окно на
   рабочем AS — **84–118 с** (p10 84.1 / p50 97.6 / p90 118.0, n=222). Ось реза —
   **возраст**: CV 0.26 против 8.73 по байтам (в 33 раза плотнее); умирают и
   слоты с 0 КБ, поэтому триггер по объёму из net4people#490 на этом AS **не
   воспроизводится**. ⚠ И **глобальная константа неверна в принципе**:
   ACM IMC 2022 — ТСПУ неоднородна по регионам и операторам. Курс — адаптация
   per-AS на клиенте (`client/slotobs`).
   **Считать бюджет только через `WSPoolTransport.worstCaseTeardown()`.** Он
   складывает `base + stagger + sweep + deferred + teardown_cap`, где `sweep` с
   2026-08-14 = тик + подтиковое размазывание фазы. До 2026-08-07 лог считал
   `base + sticky` и врал в 1.6 раза: выпадал `staggerOffsetCap` (до +48 с), из-за
   чего 8 ячеек из 16 имели порог ротации 114 с при p10 смертей 84 с и физически
   не доживали до собственной ротации. Никогда не складывать слагаемые по месту.
   ⚠ Выборка `slotobs` **цензурирована**: `Record` вызывается только на ошибке
   чтения (`ws_pool.go`), плановые ротации в неё не попадают. Поэтому доля
   «срезано посредником» из `by_close_kind` не выводится, а p10 смещён вверх.
9. **Возрасты смертей описывают НАШ порог, а не цензора** (аудит 2026-08-13,
   лог `nixavpn-DEBUG-20260813-083912`). 9 резов легли в 82.6–84.0 с (ширина
   1.4 с, CV 0.005) — соблазн прочесть это как «окно сжалось». Восстановление
   времён жизни 870 плановых ротаций опровергло: **337 слотов прожили дольше
   самого позднего реза и были сняты нами штатно**, до 90 с дожили 12, max
   104.7 с. Стены на 84 с нет; узость полосы = узость наших порогов (79.7 и
   85.2 с). Смерти детерминированы stagger: slot 0–5 (79.7 с) — **0** смертей
   на 613 ротаций, slot 6–9 (85.2 с) — **9** на 244.
   → Перед любым выводом об окне восстанавливать времена жизни **плановых**
   ротаций (`reader started` → `teardown`), а не только резы. Предупреждение
   уже стоит в `client/stats.go:1446` и `client/slotobs/planned.go:19`.
   ⚠ `cause=age_cut` — **ярлык, не наблюдение**: `isAgeCut()`
   (`client/ws_pool.go:1313`) метит любую терминальную ошибку старше
   `ageCutMinAge`, тип ошибки не смотрится. «Все смерти — age_cut» тавтологично.
   ⚠ «Ladder stagger дремлет, реальные offsets ~4.7 и ~10.2 с» — **причина
   названа неверно** (замер 2026-08-14). Лестница не дремлет: offsets реально
   равны `idx ± 0.5 с`, из 16 значений используется 9–12. Два режима в логе —
   следствие **квантования `rotationWatchdogTick = 5 с`**: порог проверяется
   только на тике, поэтому 4.7 и 9.7 — это не offsets, а порог, округлённый
   вверх до сетки тика; offsets 0…4 с неразличимы, 5…9 с неразличимы. Модель
   подтверждена на двух прогонах (base 70 → 73.8/79.6 с; base 75 → 79.7/84.7 с).
   Вывод «8 ячеек из 16 с порогом 114 с» (п. 8) всё равно не воспроизводится.
   ⚠ **Фаза свипа уходила на wire, и лечится она НЕ величиной периода, а его
   непостоянством.** Замер 08-13: все 588 age-ротаций в одной фазе 5-секундной
   сетки (σ 0.0001 с), 92.2 % TCP-connect'ов в одном односекундном окне.
   Комментарий про размазанный FFT-пик описывал механизм, который **не
   исполнялся**: stagger-джиттер прибавляется к порогу, а порог проверяется лишь
   на тике. Две попытки и их итог:
   1. ручка «джиттер на момент дренажа» через `nextDrainAttemptNs` — **откачена**:
      её читает только свип, который сам просыпается по тому же тикеру, поэтому
      отсрочка короче тика переносила дренаж ровно на следующий тик, в ту же фазу;
   2. срезка `rotationWatchdogTick` 5 с → 500 мс — **помогла частично**: линия на
      0.2 Гц убита (vector strength 1.0000 → 0.0096), но пик **переехал на 2 Гц**
      (R на периоде 500 мс = 0.8657). Уменьшение периода воспроизводило бы тот же
      результат на следующем масштабе;
   3. **`time.Timer` с перевзводом на `tick + uniform[0, tick)`**
      (`nextWatchdogWakeup()`) — решётки не остаётся **у этого цикла**. Джиттер
      сэмплируется заново каждый взвод (один сэмпл на сеанс = решётка с другим
      шагом).
   ✅ **ЗАМЕРЕНО 2026-08-14 (прогон 161915, 4 ч): фаза развязана ЦЕЛИКОМ**, включая
   момент закрытия — прогноз «развязано наполовину» оказался пессимистичным.
   `R` по всем событиям и периодам на уровне шума (`1/√n` = 0.025):

   | Событие @ 0.5 с | база (тик 5 с) | 500 мс без джиттера | **Timer+джиттер** |
   |---|---|---|---|
   | `reader started` | 0.5892 | 0.6023 | **0.0330** |
   | `drain started` | 0.9541 | 0.8900 | **0.0464** |
   | close (`natural finish`) | 0.9655 | 0.8933 | **0.0447** |

   Слепой скан 0.05–6.0 с шагом 5 мс: max `R` = 0.063 — линий нет во всём диапазоне.
   **Механизм, из-за которого close тоже развязался: ЯКОРЬ.** Сетка дренажа жива
   на 100% — `R((close − drain_start) mod 500мс) = 1.0000`, 1525/1525 событий в
   одном 50-мс бине, — но её фаза наследуется от `startDrain`, а тот приходит из
   джиттерованного свипа. Правка `drainPollInterval` **не нужна**; это
   зависимость, а не свобода: возврат свипа к `time.NewTicker` немедленно проявит
   решётку 500 мс в моментах close без единой правки в коде дренажа.
   → Критерий фазы — **`R < 0.2` на периоде тика**, а НЕ «доля в модальном окне
   сетки 5 с»: та падает автоматически при любом тике меньше секунды, то есть
   измеряет нашу ручку, а не наблюдаемость.
   ⚠ Замером НЕ снято: медиана `close − start` = 0.500 с ровно — пара «новое TLS →
   close через полсекунды» жёстко коррелирована по **интервалу**. Это шаблон, а не
   периодичность. И `R` считается по меткам ЛОГА, а не по SYN/FIN на проводе:
   остаточная линия тоньше ~10 мс этим методом не видна.
   ⚠ Прочие незащищённые источники периодичности на wire, найденные тем же
   ревью и **не тронутые**: `proxy/socks5/tcp.go:124` и `udp.go:384` — poll-циклы
   с жёсткими 20 мс и реальной отправкой байтов (грубейшая решётка в проекте, 50
   Гц); `client/ws_pool.go` `Connect` fan-out — детерминированная лестница
   `idx * staggerDelay`; `connmanager.go:417` — `AfterFunc(2 с)` после каждой
   ротации даёт устойчивую пару (new TLS, +2.000 с close). Правка watchdog их не
   касается — не считать фазу закрытым вопросом.
   ⚠ `worstCaseTeardown()` в проде = **142.5 с** (70 + 15.5 + 2 + 30 + 25), где
   слагаемое `sweep` = **`sweepWorstCase()` = 4 × tick** — ЕДИНСТВЕННЫЙ источник,
   не складывать по месту. Четыре тика, потому что пробуждений в худшем пути два
   (обнаружение + повтор после отсрочки гейта), а каждое длится до `tick + jitter`
   = 2 × tick. Формула ошибалась дважды за один день: `1×tick` (не учтено второе
   пробуждение) → `2×tick` (не учтён джиттер). В накладных `stagger` лишь 21 %, а
   `deferred 30 + tear 25` — 73 %; `drainRevertBackoff` в прод-прогоне не
   наблюдался ни разу. Сжимать бюджет через stagger/cap — неверная точка.
   → Окно измерено 2026-08-14 **по экспозиции** (форма, не смещённая
   цензурированием): **0 резов на 52 808 с экспозиции ниже 80 с**, далее плато
   4–7e⁻³ 1/с до 105 с. Это не отвесная стена, а ступень.
   ⚠ Величина — **офлайн-реконструкция по логу**, клиент такую показать не может:
   при ринге плановых даже в 4096 записей экспозиция ниже 80 с ограничена его
   ёмкостью. Не искать 52 808 в `slot death hazard`. И «ожидалось бы ~190 резов»
   получено при hazard'е PROBE (~1.78 %/проход), а не прода (6.94 %) — при
   прод-цифре ожидалось бы ~760; знак вывода от этого только усиливается.
   Замер: `docs/plans/2026-08-13-age-wall-probe.md`.
10. **`SHADOWLINK_STAGGER_OFFSET_CAP` — no-op, пока `(2·poolSize − 1)·step ≤ cap`.**
   Кламп требует строгого `base > cap`; при `poolSize=8, step=1s` максимум
   `idx=15` даёт ровно `15 с`, поэтому при `cap=15s` он не срабатывает **ни на
   одной** ячейке. ⚠ Условие, а не свойство: `poolSize` конфигурируем
   (`WSPoolSize`), и при `poolSize ≥ 9` кламп оживает — иначе это была бы ровно
   та «глобальная константа, неверная в принципе», от которой предостерегает
   правило 8. При текущем проде правка 15 → 10 с связала бы только `idx 11…15`,
   чья занятость в поле — **0.16 %**, а после квантования тиком меняла бы корзину
   лишь у `idx=15` → **ноль соединений за прогон**. Причина заходов в полосу
   80–85 с — offsets 5…9 с у ячеек 5–9 плюс квантование, не cap. Вопрос закрыт
   2026-08-14 (независимая проверка); поднимать заново только с замером.

11. **Периодического healer'а ёмкости в пуле НЕТ** — каждая цепочка
   `reconnectLoop` одноразова, единственный вызов на старте это начальный connect.
   Поэтому обрыв цепочки = **потеря ячейки навсегда**. Так и было до 2026-08-14:
   `placeholder freed` → `reconnecting slot N` → дренаж забрал ту же ячейку →
   `reconnect short-circuited` → `empty` 8→9→10→11, `mean alive` 7.21→5.80 за 2 ч.
   На конце цепочки — пул на полу storm-brake, отклонённые ротации и резы
   посредника (3 из 4 в том прогоне). Исправлено: guard отказывается от ЯЧЕЙКИ, но
   восполняет ЁМКОСТЬ на свободной (`claimFreeCellForHealing`, предел
   `maxHealingRetargets`). ⚠ Лечение обязано быть УСЛОВНЫМ: лишнее TLS-соединение
   к origin — это P0 (policing по числу соединений), поэтому поднимать «на всякий
   случай» нельзя. Смотреть `healing_retargets_total` / `healing_gave_up_total`.
   ⚠ **`connectSlot` перезаписывает ячейку УСЛОВНО** (`cellIsOverwritable`,
   добавлено ревью 2026-08-14). `claimFreeCellForHealing` намеренно не ставит
   placeholder — иначе тот висел бы «здоровым» через весь backoff и глушил бы
   повторное лечение, а при `ctx.Done()` утёк бы вечным `slotConnecting`. Но из
   этого следует окно, в которое ячейку успевает занять `claimFreeSlot`, и
   первоначальная оценка «цена — лишнее одно соединение» **неверна**: перезапись
   живой ячейки осиротила бы TLS-соединение (все `Close()` идут через
   `slotAt(idx)`, то есть уже по новому указателю) и её `slotReader`
   (`shouldExitReader` сравнивает `generation` СВОЕГО объекта, а бампается
   `generation` нового), после чего этот ридер на своей ошибке чтения позвал бы
   `handleSlotDeath` **по индексу** и убил бы свежий слот. Защита — у писателя, а
   не в оценке вероятности: `slotReady`/`slotDraining` не перезаписываются,
   возвращается `ErrCellOccupied`; `nil`/`slotDead`/`slotConnecting`-placeholder —
   можно (на последнем держится штатная замена при дренаже). ⚠ `ErrCellOccupied`
   **не считать отказом origin**: ни лестница backoff, ни
   `reserveConnectFailures`, ни `AgeCutReconnectFail` к нему не относятся.
12. **Sticky — главный и почти единственный источник хвоста возрастов** (замер
   2026-08-14, прогон 161915, 4 ч). После закрытия утечки ячеек и обнуления
   отложек capacity-floor других значимых источников не осталось: sticky даёт
   **77 % экспозиции за 82 с** (196.8 с из 254 с), **12 из 17** соединений старше
   85 с, max 102.6 с.
   ⚠ **`drain_duration` в ветке `age_backstop` — константа и о риске молчит**: все
   50 teardown'ов прогона дали ровно `25s`, потому что каждый упёрся в
   `stickyMaxDrainAge`, ни один не завершился раньше. Читать **`slot_age`** —
   полный возраст TCP на момент разрыва (добавлено там же). Механизм: дренаж по
   `byte_budget` (38 из 50) стартует в ЛЮБОМ возрасте — p50 34.2 с, p90 74.2 с,
   max 77.6 с, — и sticky добавляет ровно +25 с сверху, поэтому потолок жизни
   = `старт дренажа + 25 с` (наблюдаемый max 102.6 с сходится с 77.6 + 25).
   → Вред пока НЕ наступил: при 49.2 с/ч экспозиции и hazard 80-85 с ≈ 14.4e⁻³ 1/с
   ожидается ~1 рез за 4-часовой прогон, наблюдалось 0. Константу поэтому НЕ
   трогали (hard rule 8), вместо неё завели `sticky_exposure_over_82s_ms` —
   единственный оставшийся канал, по которому резы вернутся. Порог 82 с, а не 80 с:
   плановые ротации массово проходят через 80.2 с и забили бы счётчик штатной
   работой.
   ⚠ Рост sticky 3.0/ч → 12.5/ч между прогонами объясняется нагрузкой (трафик
   1502 → 3116 МБ), но нормировка на объём снимает это лишь частично
   (`sticky/ГБ` 6.1 → 16.4) — чистый A/B требует одинакового профиля трафика.

## Architecture

```
App → SOCKS5 → Client → uTLS (Chrome 133) → direct origin IP :443
    → nginx (TLS term) → 127.0.0.1:10443 → Server → Internet
```
Routing (`server/handler.go`): `POST`+`application/json` → VPN-сессия ·
`Upgrade: websocket` → WS transport · всё прочее → decoy SPA.

Crypto: X25519 ECDH → HKDF-SHA256 → AES-256-GCM, forward secrecy, replay
protection. Стеганография на HTTP-уровне, не TLS-уровне.

## Isolation rules

- Весь ShadowLink-код — в этом репозитории. Docs/specs — `docs/`. Тесты
  colocated (`*_test.go`).
- В дерево NixaVPN идут только integration points (deploy orchestrator, config
  assembler, admin handlers). Путь резолвится через `internal/slpath` / env
  **`SHADOWLINK_DIR`** — хардкода пути быть не должно.
